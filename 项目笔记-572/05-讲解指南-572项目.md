## 2. 项目背景（1分钟）

**面试官可能接着问："这个项目要解决什么问题？"**

### 2.1 业务背景

> 这个项目的核心定位是**工艺设计一体化**——把产品设计、工艺设计、生产制造这三段流程打通，而不是做一个传统的文档管理系统。
>
> 企业原来的痛点很具体：
> - **设计端**：工程师用 CATIA 做三维设计，图纸和模型存在本地，版本靠手工命名
> - **工艺端**：工艺人员根据设计图纸编制 PBOM（工艺BOM），但这个环节全靠线下沟通，设计改了工艺不知道
> - **审批端**：工艺文档审批走纸质签单，签完送到档案室归档，查询困难
> - **生产端**：MES 系统需要 PBOM 数据才能排产，但数据传递靠 Excel 手工导出
>
> **核心矛盾就一个：数据流是断的。** 设计不通工艺，工艺不通生产。所以我们做这个平台，本质在做**数据链路的连接**。

### 2.2 技术选型原因

> 选 3DEXPERIENCE 有几个原因：
> - 跟现有的 CATIA 设计工具同源，数据打通没障碍
> - 平台本身提供了完整的对象模型和生命周期管理
> - 有完善的二次开发接口（JPO / Spinner / REST）
>
> 但平台原生功能不能直接满足我们"审批走若依、生产走 MES"的需求，
> 所以核心工作其实是**扩展和集成**。

### 2.3 项目范围

> 项目覆盖的**工艺设计一体化**业务范围：
>
```
[CATIA 设计] ──→ [工艺设计一体化平台] ──→ [MES 生产执行]
      │                     │                     │
      │              ┌──────┼──────┐              │
      │              ▼      ▼      ▼              │
      │         PBOM管理  文档管理  变更管理        │
      │              │      │      │              │
      │              └──────┼──────┘              │
      │                     ▼                     │
      │               [若依审批流程]               │
      │                     │                     │
      └─────────────────────┼─────────────────────┘
                           ▼
                     [ERP/SAP/归档至兰考]
```
>
> 六大业务模块：
> - **文档管理**：技术文档、图样、工艺文件的创建→审批→归档→发布全生命周期
> - **变更管理**：ECR/ECO/EO——工程更改的发起→评估→执行→关闭
> - **物料/BOM 管理**：PBOM（工艺BOM）的创建、编辑、版本管理、向 MES 分发
> - **审批流程**：对接若依流程引擎，所有工艺文档的审批线上化
> - **供应商管理**：供应商准入、评估、数据导出
> - **仓储申请管理**：生产物料的库存申请与审批
>
> 外加 7 个外部系统集成。

**示范逻辑：**
- 先暴露痛点（混乱+不可追溯）
- 再说选择（为什么是 3DE）
- 最后说范围（让面试官知道规模）

## 3. 核心架构（3分钟）

**这部分是重头戏，建议画图辅助讲解。** 你可以在白板上画。

### 3.1 四层架构（先画整体框架）

```
┌─────────────────────────────────────────────┐
│  展现层                                      │
│  3DE 原生界面 + 自定义 Widget + 若依前端      │
├─────────────────────────────────────────────┤
│  接入层                                      │
│  3DPassport SSO + REST API 网关 + postmethod│
├─────────────────────────────────────────────┤
│  业务层                                      │
│  187 个 JPO（Java Program Object）          │
│  文档/变更/BOM/流程/供应商/仓储               │
├─────────────────────────────────────────────┤
│  持久层                                      │
│  3DE 矩阵数据库 + 若依 MySQL + Oracle + SFTP │
└─────────────────────────────────────────────┘
```

**讲解话术：**

> 整体架构分四层。
>
> **展现层**，我们有 3DE 原生界面、自己开发的 Widget 小组件、还有若依前端的流程管理界面。Widget 用的是 AMD + Vue 3 的架构，通过 WAFData 这个 3DE 提供的通信工具调后端。
>
> **接入层**，所有的外部请求通过 3DPassport 做统一认证，然后走 REST API 网关。我们设计了一个通用路由叫 postmethod，通过参数指定调哪个 JPO 的哪个方法，新增接口不用改路由代码。
>
> **业务层**是核心，187 个 JPO 文件，约 23 万行 Java 代码。每个 JPO 对应一个工艺设计一体化的业务模块——比如工艺BOM管理（PBOM）、工程变更（ECO/ECR/EO）、文档签审、MES数据推送等。这些 JPO 串联起来就构成了"设计→工艺→审批→生产"的完整数据链。
>
> **持久层**，3DE 自身用矩阵数据库存业务对象，若依用 MySQL 存流程数据，还有一些外部数据通过 Oracle 中间表同步。

### 3.2 数据流（画关键链路）

> 我重点讲一条核心数据流——**文档审批**，这条链路最能体现整个架构的设计思路。
>
> 用户在 Widget 上创建文档，填入属性、上传文件，前端通过 WAFData 调 postmethod 路由，路由反射调用对应的 JPO。JPO 在服务端创建 Document 对象、关联 PBOM、签入文件，然后通过 HttpClient 调若依接口发起审批流程。
>
> 若依的 Activiti 流程引擎驱动审批节点，每个 Service Task 通过 delegateExpression 配置的 Bean 名称回调 3DE，执行签审操作。审批完成后，再回调 3DE 完成文件归档。
>
> 这个设计的关键决策是：**把审批流程外置到若依，3DE 专注做 PLM 数据管理**。好处是流程引擎的维护和扩展都不影响 3DE 核心业务。

**画图技巧：**
- 在中间画 3DE，左边画用户（Widget），右边画若依
- 箭头：Widget → postmethod → JPO → HttpClient → 若依
- 强调"服务端代理"——JPO 在服务端发 HTTP，不存在浏览器跨域问题

### 3.3 扩展体系（三层）

> 我们的扩展体系分三层。
>
> **最底层是 Spinner 配置**，60 多个 XLS 文件定义了所有业务对象的类型、属性、关系、生命周期策略、触发器。比如创建一个"技术文档"类型，就在 Spinner 配置里定义它的属性、策略、表格、表单。这一层做的是**数据建模**。
>
> **中间层是 JPO**，187 个 Java 文件，负责业务逻辑。每个 JPO 对应一个功能模块，通过 DomainObject API、MQL 或者 HttpClient 来实现具体逻辑。这一层做的是**逻辑实现**。
>
> **最上层是 Widget/JSP/REST**，负责跟用户和外部系统交互。这一层做的是**接入**。
>
> 这三层是松耦合的：改 Spinner 配置不需要改代码，改 JPO 逻辑不需要动前端，新增 REST 接口通过通用路由可以不重启服务。

**面试官可能追问：**"Spinner 配置不会改一次就要重新导入一次吗？"

> 是的，Spinner 配置修改后需要通过 SpinnerAgent 批量导入。但我们做了个在线配置工具（SpinnerConfigTool），可以在浏览器里编辑 TSV 配置文件、预览效果、批量导出，不用每次都去服务器操作。

## 4. 我的角色与贡献（2分钟）

**这部分要有真实感，不要只说"我负责了XX"，要带效果。**

### 4.1 我做了什么

> **架构层面：**
> - 设计了 JPO 代理模式的通信方案——前端 Widget 不直接调外部接口，而是通过 WAFData 调 postmethod 路由，由 JPO 在服务端代理请求。解决了 HTTS 环境调 HTTP 接口的跨域问题。
> - 参与制定了 Spinner 配置 + JPO + Widget 三层扩展的开发规范，后续新模块都按这个模板来做。
>
> **核心模块开发：**
> - 文档管理模块：文档创建/属性设置/文件签入/自动发起流程的全链路实现
> - 审批流程集成：3DE ↔ 若依的双向通信、签审回调、异步日志与重推机制
> - 外部系统对接：MES/ERP/EL 等多个系统的接口开发
>
> **工具与效率：**
> - 开发了 SpinnerConfigTool 在线配置工具，减少了运维人员反复导入导出配置的工作
> - 开发了 API 调试工具（LAMC_ApiDebugger），应用顾问不用装 Postman 直接在 3DE 里测接口
> - 整理了完整的项目代码索引和接口文档，新人上手时间明显缩短

### 4.2 具体难点与解决方案（挑 2-3 个讲）

> **难点一：跨域问题**
>
> 知识工程接口是 HTTP 的，3DE 是 HTTPS 的，浏览器不让调。而且中间还涉及 WDSC 签名鉴权，AK/SK 不能暴露在前端。
>
> **方案：** JPO 代理模式——Widget 调同域的 postmethod 路由，JPO 在服务端做 HTTP 请求 + 签名计算，拿到结果透传给前端。服务端没有跨域限制。
>
> **难点二：审批流程跨系统**
>
> 3DE 和若依是两套独立的系统，审批流程要跨系统跑——从 3DE 发起，在若依审批，再回调 3DE。而且操作要原子化，失败了要能重试。
>
> **方案：** 异步调用 + 接口日志 + 批量重推。每次调用记录到 ApiLog 表，失败了可以查日志、单条重发、批量重推（4 秒间隔限制），而且用 requestId 做了幂等防重。
>
> **难点三：日志组件不可维护**
>
> 之前有一个日志组件，但它是 webpack 打包后的 bundle，要改功能得解包重打包，很不方便。
>
> **方案：** 基于标准 AMD + Vue 3 架构重写成源码开放的 Widget，不需要打包，直接改 .js 文件就能生效。同时把通信方式从浏览器直接调若依接口改成通过 JPO 代理，解决了跨域问题。

## 5. 技术亮点问答（5分钟）

**这一节是面试中真正拉分的部分。** 面试官不会只听你复述做了什么，他会追问技术细节。

### Q1："JPO 是什么？跟普通 Java 类有什么区别？"

> JPO 是 3DE 平台的一个概念——Java Program Object。本质上就是一个普通 Java 类，但部署方式特殊。
>
> 跟普通 Java 类的区别在于：
> 1. 部署到 3DE 服务器的 CAS 组件中，通过 MQL 的 `add program` 命令注册到系统。
> 2. 方法签名有固定格式——`public String xxx(Context ctx, String[] args)`，框架会自动注入上下文和参数。
> 3. 调用方式独特——通过 `JPO.invoke(context, "JPO名", null, "方法名", args, String.class)` 反射调用。
> 4. 最大的特点是热部署——修改 JPO 源码后，编译替换 .class 文件，不需要重启 3DSpace 服务。

**为什么这样设计？** 3DE 的架构里，JPO 运行在 CAS 容器中，通过 RMI 跟主应用通信。这个设计让 JPO 可以热加载，对生产环境的运维来说非常友好。

### Q2："WAFData 是什么？跟 axios 有什么区别？"

> WAFData 是 3DE 平台自带的一个 AJAX 请求工具。它比 axios 或 fetch 多了一个关键能力——**自动处理 3DE 的认证体系**。
>
> 3DE 的认证机制比较复杂：前端首先要通过 CAS 或者 3DPassport 拿到票据，每次请求都要带上 SecurityContext 等认证头。如果用 axios，你得自己实现这一套登录认证逻辑。
>
> WAFData 的 `authenticatedRequest` 方法把这些都封装好了，你只需要写 URL 和参数，认证相关的事情框架帮你做了。
>
> 简单说，3DE 平台内开发用 WAFData，平台外的应用（比如若依前端）用 axios。

### Q3："postmethod 路由是怎么实现通用调用的？"

（这个问题是考察你对框架机制的理解）

> postmethod 是一个 JAX-RS REST 接口，核心代码其实很简单，就几行：
>
> ```java
> @POST @Path("postmethod")
> public Response postMethod(HttpServletRequest req,
>     @QueryParam("JPO") String jpo,
>     @QueryParam("Method") String method, String param) {
>     Context context = getAuthenticatedContext(req, false);
>     String result = JPO.invoke(context, jpo, null, method,
>         new String[]{param}, String.class);
>     return Response.ok(result).build();
> }
> ```
>
> 它做了三件事：
> 1. 从 HTTP 请求中解析出 3DE 的认证上下文
> 2. 通过 JPO.invoke 反射调用目标 JPO 的目标方法
> 3. 把 JPO 返回值包装成 HTTP 响应
>
> 之所以能做到"通用"，是因为 JPO.invoke 本身就是动态调用的——只要传 JPO 名和方法名，它就能反射找到对应的类和方法。所以 postmethod 只起了一个**路由转发**的作用，实际业务逻辑全在 JPO 里。

### Q4："你们怎么保证跨系统操作的一致性？"

（这里考察你的分布式系统理解）

> 我们采用的是**最终一致性**方案，没有用分布式事务。
>
> 核心思路是：
> 1. 每个接口调用都记录到 ApiLog 表（请求内容、响应内容、状态、耗时）
> 2. 调用失败不会回滚——3DE 侧的事务是独立的，调用若依失败不会影响 3DE 的数据创建
> 3. 异常的调用可以通过 ApiLog 查询到，然后手动或批量重推
> 4. 关键的提升/签字操作做了幂等——用 requestId 去重，同一个请求重复调用不会产生副作用
>
> 为什么不用分布式事务？因为 3DE 和若依是异构系统，3DE 用的是它自己的矩阵数据库，若依是 MySQL，没法做跨库的 2PC。而且业务上允许短时间的最终一致——比如审批签了字还没归档，这个窗口期是可以接受的。

### Q5："这个项目你最有成就感的是什么？"

（这个问题看起来软，但很关键，考察你的思考深度）

> 最有成就感的有两件事：
>
> 第一件是**制定了一套可复用的 Widget 开发模板**。之前团队写小组件，每个人风格不一样，有的用 webpack 打包，有的直接写原生 JS，出了问题谁都看不懂。我参考了项目里一个成熟的组件（LAMC_CreateDocument），提炼出了一套标准模板——AMD + Vue 3 + ElementPlus + JPO 代理模式，所有新组件都按这个模板做。现在无论是内网修改还是新功能扩展，都清晰很多。
>
> 第二件是**接口文档的体系化**。之前新同事接手项目，光搞清楚有哪些接口、怎么调就要好几天。我把 07.java 里 40 多个 REST 接口全部提取出来，按功能模块分类，标注了请求/响应格式、参数说明、调用链路。
>
> 这两件事情从技术层面看可能没那么"高大上"，但它们直接降低了团队的沟通成本和上手时间，我觉得这就是架构工作的价值所在。

## 6. 踩过的坑（2分钟）

**面试官喜欢听"踩坑"——因为能看出你的真实经验。**

### 坑一：时间格式化踩坑

> 日志组件里有一个时间展示的功能。后端返回的时间格式是 `"2025-08-11 18:46:08"`（空格分隔），前端用 `new Date()` 解析。在 Chrome 上没问题，但 Firefox 和 Safari 解析带空格的日期会返回 Invalid Date。
>
> 排查过程发现是浏览器兼容性问题——ISO 8601 标准要求时间要用 `T` 分隔而不是空格。修复方式是把空格统一替换成 `T` 再解析。
>
> 更深层的问题是，之前代码在 fetchLogs 时预格式化了时间字段，存储了格式化后的字符串。后来渲染时又格式化一次，导致双重格式化。修复时把预格式化去掉，存原始值，渲染时统一格式化。

**这个坑能体现什么：** 跨浏览器兼容意识、数据流设计的严谨性（不要在多个地方做同一件事）。

### 坑二：JPO 参数传递问题

> 有个 Trigger 方法，需要传 5 个参数。第一次写的时候我直接用了 JPO.invoke 的 String[] 传参。后来需求变更要加第 6 个参数，得改 JPO 方法签名和所有调用处，很麻烦。
>
> 后来改成统一传 JSON 字符串，JPO 里用 `JSONObject.parseObject(args[0])` 解析。这样新增参数只需要改 JSON 的 key，不需要改方法签名。
>
> 这个改进后来推广到了所有新 JPO 的参数传递规范里。

**体现什么：** 接口设计的扩展性意识、简单重构带来的维护成本降低。

### 坑三：跨域问题不是 CORS 能解决的

> 接到需求要把知识工程查询做成 Widget。知识工程服务的地址是 `http://192.169.10.150:8088`，但 3DE 是 HTTPS 环境。
>
> 开始想用 CORS 解决，但发现即使服务端配了 CORS，HTTPS 页面请求 HTTP 接口这种"混合内容"问题浏览器直接禁止，CORS 都救不了。
>
> 最终方案是在 3DE 服务端写一个 JPO 做代理转发。Widget 调 3DE 的同域 HTTPS API，JPO 在服务端用 HttpClient 发起 HTTP 请求。

**体现什么：** 理解浏览器安全策略的边界、能跳出"前端思维"用架构手段解决问题。

### 8.2 运维面试专项：3DE 部署架构与配置

**这一节专为面试运维岗位或架构师岗位准备，从基础设施层面讲清楚 3DE 怎么部署的。**

---

#### Q1："3DE 是怎么部署的？有几个节点？"

> 3DE 不是单体应用，它由多个 Web 应用组成，部署在 TomEE（Tomcat 增强版）上。典型部署包含以下几个节点：
>
> **核心节点：**
> - **3DPassport** — SSO 单点登录服务。负责认证，用户登录先走这里。
> - **3DSpace** — 主 PLM 应用。承载所有业务逻辑、REST 接口、JPO 调用、Widget 前端。也是我们二次开发主要部署的位置。
> - **3DDashboard** — 仪表盘/报表应用。展示统计图表、任务看板等。
>
> **若依集群（Docker 容器化）：**
> - ruoyi-nginx — 前端反向代理，承载 Vue 前端静态资源
> - ruoyi-gateway — Spring Cloud Gateway，统一网关入口
> - ruoyi-auth — 认证中心
> - ruoyi-modules-system — 系统管理模块
> - ruoyi-modules-danny — 572 项目自定义模块（核心扩展）
> - ruoyi-modules-usersynch — 用户同步模块
> - ruoyi-modules-file — 文件服务
> - ruoyi-redis — Redis 缓存
> - ruoyi-mysql — MySQL 数据库
> - ruoyi-nacos — 注册中心和配置中心
>
> **外部依赖：**
> - MES 系统 :8093（SOAP）
> - ERP/SAP 系统 :9999（SOAP）
> - 标准规范系统 :8088（REST）
> - QMS 质量系统（外部）
> - SFTP 文件服务器

**面试官追问："3DSpace 和 3DPassport 之间是怎么通信的？"**

> 3DPassport 负责认证，3DSpace 负责业务。用户登录时先重定向到 3DPassport，拿到票据后带着票据访问 3DSpace。3DSpace 验证票据有效性后创建会话。
>
> 另外还有一个 CAS（Common Application Server）组件，它是 3DSpace 内部的一个独立 servlet，跑在同一个 TomEE 下，负责执行 JPO。JPO 编译后的 .class 文件部署在 CAS 的 classpath 下，通过 RMI 跟主应用通信。

---

#### Q2："3DSpace 的 JVM 参数怎么配的？"

> 3DSpace 的 JVM 参数主要在两个地方配置：
>
> **enovia.ini**（核心配置）：
> ```ini
> [MATRIX]
> # JVM 最大堆内存
> MX_JAVA_OPTIONS=-Xmx4096m
> # 系统内存限制（物理机或容器的可用内存上限）
> MX_MEMORY_SYSTEM_LIMIT=8192m
> # 连接池大小
> MX_CONNECTION_POOL_SIZE=30
> # 查询分页大小
> MX_QUERY_PAGE_SIZE=10000
> # 会话超时（分钟）
> MX_SESSION_TIMEOUT=60
> # 事务超时后自动中断
> MX_ABORT_DANGLING_TRANSACTION=true
> # 字符集
> MX_CHARSET=UTF8
> # 日志路径
> MX_TRACE_FILE_PATH=C:\DassaultSystemes\R2020x\3DSpace\logs
> ```
>
> **TomEE 的 setenv 脚本**（Tomcat 层参数），比如 CATALINA_OPTS 里可以配：
> - `-Xms` / `-Xmx` 堆内存
> - `-XX:MetaspaceSize` 元空间
> - `-Djava.rmi.server.hostname` 如果开了 RMI
>
> **经验值：**
> - 3DSpace JVM 堆一般给 4G（`-Xmx4096m`），物理机至少 8G
> - 连接池 30 够用，如果并发高可以调到 50-100
> - 查询分页默认 10000，如果 PR 表数据量大可以改小

---

#### Q3："3DE 用什么应用服务器？"

> 3DE 用的是 **TomEE**——Tomcat 的增强版，跟标准 Tomcat 的区别是它预装了 Java EE 全套特性（JAX-RS、JPA、CDI 等），而这些正是 3DE REST 接口和 ModelerBase 注册机制依赖的。
>
> 如果换成普通 Tomcat，3DE 的 REST 接口跑不起来，因为缺少 JAX-RS (Jersey/CXF) 的实现。
>
> 所以 3DE 官方对 3DSpace 和 3DPassport 都使用 TomEE，而不是标准 Tomcat。

---

#### Q4："3DE 的端口分配是怎样的？"

> 从我们项目的防火墙开端口清单可以看出来：
>
> | 端口 | 用途 | 所属系统 |
> |------|------|---------|
> | 80 | HTTP 反向代理 | Nginx / 3DE |
> | 8080 | 3DPassport SSO 服务 | TomEE |
> | 8087 | 若依网关入口 | Spring Cloud Gateway |
> | 8848 | Nacos 注册中心 | 若依 |
> | 9848/9849 | Nacos gRPC 端口 | 若依 |
> | 6379 | Redis 缓存 | 若依 |
> | 3306 | MySQL 数据库 | 若依 |
> | 9100-9300 | 若依各微服务模块 | 若依 |
>
> **流程：** 用户通过 80 → Nginx → 静态资源直出，API 请求反代到后端。如果是 3DE 的业务，走 8080（3DPassport 认证）→ 3DSpace（业务）；如果是流程相关的，走 8087（若依网关）→ 若依各模块。

---

#### Q5："3DE 的 JSP 修改后怎么生效？需要重启吗？"

> 不需要重启。3DE 默认有 JSP 热生效机制。但需要确认 web.xml 里配了 `development=true` 参数，并且 `modificationTestInterval` 设置了检查间隔（默认 4 秒）。
>
> 生产环境上如果发现改了 JSP 没生效，往往是这个 development 参数被关了。改回 true 即可，不需要重启 TomEE。
>
> 同理，JPO 修改编译后也是热生效的，替换 .class 文件就行，不需要重启。

---

#### Q6："你们怎么配置定时任务和索引维护？"

> 我们有三类定时任务：
>
> **Linux crontab 脚本：**
> - `restartRuoyi.sh` — 每分钟检查若依服务状态，挂了自动重启
> - `updateLoginLog.sh` — 每天记录登录日志
> - `refreshAttributes.sh` — 每小时刷新 3DE 属性
>
> **3DE 内置的定时任务：**
> - 通过 `schedule` 命令配置，可以用 MQL 查询和修改
> - 典型的如增量索引：`mql schedule incrementalIndex start`
>
> **若依内建的 XXL-Job：**
> - 用于定时数据同步，比如每天同步用户、定时推送数据到 MES
>
> **索引维护关键点：**
> - 索引服务器有证书，证书过期后增量索引会停，表现为搜索不到新增的数据。这时候需要更新证书或重建索引。
> - 全量索引重建脚本：`mql rebuildindex all`

---

#### Q7："3DE 的 enovia.ini 里那些 URL 配置是什么意思？"

> enovia.ini 底部有一组 URL 配置，它们定义了 3DE 各子服务的访问地址：
>
> ```ini
> PASSPORT_URL=https://20x.3de.com/3dpassport     # SSO 登录页
> DASHBOARD_URL=https://20x.3de.com/3ddashboard    # 仪表盘
> ENOVIA_URL=https://20x.3de.com                   # 3DSpace 业务入口
> SEARCH_URL=https://20x.3de.com/federated         # 全文搜索服务
> SWYM_URL=https://20x.3de.com/3dswym              # 社交协作
> NOTIFICATION_URL=https://20x.3de.com/3dnotification # 通知服务
> SERVICE_URL=https://20x.3de.com/3dspace           # 服务调用入口
> ```
>
> 这些 URL 必须跟实际部署的域名和端口一致，否则会出现"点了一个按钮跳到 404"的问题。迁移环境时，这是第一个要改的配置。**如果面试里问"3DE 改域名改哪些配置"——就答这些 URL。**

---

#### Q8："3DE 扩容怎么办？能水平扩展吗？"

> 3DSpace 可以水平扩展——部署多个 TomEE 实例，前面挂负载均衡（Nginx/Haproxy）。但这只是无状态层面的扩展。
>
> 真正的瓶颈通常在矩阵数据库层，它是单点的。虽然 3DE 有 MatrixDB 集群方案，但实施成本较高，我们项目没有做。
>
> 实践中，如果遇到性能瓶颈，我们优先做的是：
> 1. 检查 `MX_CONNECTION_POOL_SIZE` 是否够用
> 2. 检查 `MX_JAVA_OPTIONS` 的堆内存
> 3. 优化慢的 MQL 查询（加索引、限制查询范围）
> 4. 若依侧做微服务水平扩展（docker-compose up 多实例）

> 总结下来，3DE 运维的核心是 **四件事**：
>
> 1. **JVM 和连接池** —— enovia.ini 里的内存和并发参数
> 2. **多子服务 URL** ——各服务的地址配置，迁移环境时第一个要改的
> 3. **JSP/JPO 热生效** ——开发模式和生产模式的区别
> 4. **索引维护** ——证书过期导致搜不到数据是常见问题
