> **目标：** 把达索 MQL 封装成 agent 可调用的工具，并解决"非标知识"的沉淀问题
> **状态：** 设计完成，待落地（明天动手：写 skill + 整理达索知识）

## 一、需求全景

```
【第1层】远程通道   ← 不用开发，用 OpenClaw nodes 配对
    agent(本机) ── nodes.invoke ──> 服务器（装 OpenClaw node）

【第2层】MQL 执行器  ← 写脚本，放服务器上
    scripts/run-mql.ps1 或 .sh
      └─ 调用服务器上的 MQL.exe / .sh，捕获输出

【第3层】知识层      ← 非标语法知识，滚动积累（真正的难点）
```

**关键前提（待确认）：**
- agent 机器 ≠ 服务器机器 → 必须走远程通道（`nodes` / `file_fetch` / `file_write`）
- MQL 是 exe 或 .sh，执行后会打开 DOS 窗口
- ⚠️ **核心待验证问题：能否拿到它的输出？**
  - 测试方法：`MQL.exe -c "help" > test.txt` 或 `echo "exit" | MQL.exe > test.txt`
  - 有输出 → 能做（简单，走管道/PTY）
  - 无输出但弹窗 → 是独立 GUI 进程，需换方案

## 二、⭐ 核心设计原则：双 Skill 解耦（职责分离）

**一个 skill 只干一件事，"生成"与"执行"彻底解耦。**

```
【Skill 1】mql-runner        ← 危险层 / 基础设施 / 稳定 / 可复用
  职责：接收 MQL 语句 → 通过远程通道执行 → 返回结构化结果
  包含：远程调用、输出解析、只读限制、超时、审计
  不含：任何 MQL 语法知识、任何业务判断

【Skill 2】mql-writer        ← 知识层 / 随业务演进
  职责：业务意图 → 生成正确的 MQL 语句
  包含：MQL 语法规则、常见查询模板、表/字段结构知识
  不含：任何执行逻辑

【可选 Skill 3】具体业务编排    ← 业务层 / 多变（先不拆，等真需要）
  如 bom-diagnosis：调 writer 生成 → 调 runner 执行 → 分析结果
```

### 为什么必须分开（三条理由）

1. **复用性**：runner 是通用执行器，任何需要执行 MQL 的场景都能复用；writer 随业务变
2. **安全边界**：runner 是唯一接触生产库的口子 → 集中做只读限制、限流、审计、异常处理
3. **可测试/可替换**：runner 可独立测试；换服务器/换查询引擎只动 runner

### 边界铁律
- **执行器绝不能懂业务**
- **生成器绝不能碰执行**
- **上层可以多变，runner 只有一个**

### ⚠️ 别过度拆分
现在"生成 + 执行"两片正好。别提前拆第三个 —— 等真遇到复杂业务编排再抽。

### 边界细化（易错点）
- **结果解析放 runner**：解析与 MQL 输出格式强相关，且每个调用方都要，放执行器里
- **MQL 语法知识放 writer**（或 writer 引用 `references/`），**绝不放 runner**

## 三、⭐ 非标知识的处理（本设计的真正价值）

### 问题定性
MQL 语法是**非标知识**：官方无新版本文档，靠自己摸索 + AI 逆向达索部署工具获取片段，仍不够。
→ 这是**所有"无权威文档的私有系统"**（老 ERP、内部框架、闭源 SDK）的共同难题。

### 核心认知：知识不可能一次写全，只能"滚动积累"

### 目录结构（把"确定的"和"猜的"分开存）
```
mql-writer/
├── SKILL.md                       ← 流程（怎么用这些知识）
└── references/
    ├── syntax-core.md             ← 已验证的核心语法（稳定层，谨慎改）
    ├── syntax-verified.md         ← 验证过的语句样本（只增不减）⭐
    ├── syntax-guess.md            ← 猜测/未验证（必须标"未验证"）⚠️
    └── patterns.md                ← 常见查询模板/套路
```

| 文件 | 内容 | 规则 |
|------|------|------|
| `syntax-core.md` | 反复验证过、稳定可用的 | 只添加，谨慎修改 |
| `syntax-verified.md` | "这条语句我跑通了"的真实样本 | **每次跑通就追加一条** ⭐ |
| `syntax-guess.md` | AI 逆向/推测、未实测的 | **必须标来源 + "未验证"** ⚠️ |
| `patterns.md` | "查 BOM 树要怎么写"这类套路 | 随业务积累 |

### ⭐ 知识飞轮：执行即验证，边用边攒
```
用户提需求
   ↓
mql-writer 生成语句（可能从 guess 里猜的）
   ↓
mql-runner 执行
   ↓
┌─ 成功 → 把这条语句追加到 syntax-verified.md ⭐
└─ 失败 → 记录错误（语法错/上下文依赖），修正 guess 或 core
```
> **执行器 = 知识采集器。用得越多，验证过的语法越全，猜测部分越少。**

### AI 逆向知识的处理原则
- 逆向得到的 = **线索，不是事实**
- 必须标注：来源 + 日期 + 置信度
- **绝不混进 core** —— 逆向的"看着像真的，实际可能是错的"（版本差异、上下文依赖）
```markdown
## 未验证语法（来源：逆向 xxx.exe，2026-xx-xx）
⚠️ 以下均未经实测，使用前必须先在小范围验证
- 语句A：逆向推测格式为 ...（置信度：中）
```

## 四、通用套路（可迁移到其他非标知识场景）

```
① 分层存放：core（稳）/ verified（实测）/ guess（未验证）
② 明确标记：每条知识标注 来源 + 置信度
③ 执行反哺：跑通入 verified，失败记原因
④ 不做一次性大而全，滚动积累
⑤ 上层编排不变，知识层单独演进
```
**适用：** 老 ERP 报表语法 / 内部框架 API / 闭源工具命令 / 客户自定义系统……

## 附：设计讨论中的关键判断记录

1. **执行器用 `exec` + 脚本实现，不需要写 OpenClaw 插件**（插件只用于原生工具/团队共用场景）
2. **远程通道用 OpenClaw `nodes` 配对，不需要自己开发**
3. **双 skill 解耦**：runner（基础设施/稳定）+ writer（知识封装/演进）
4. **知识库三分法**：core / verified / guess，明确标记置信度
5. **执行反哺机制**：跑通即入 verified，形成知识飞轮
6. **别过度拆分**：先两片，等复杂业务出现再抽第三个
