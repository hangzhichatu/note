
# 理论汇总
## 关于 Float/Double 精度问题
* 你的回答：
    IEEE 754 标准下，浮点数是二进制的，0.1/0.2 是无限循环小数，存储被截断。0.1+0.2 有舍入误差。千万级聚合后误差放大，导致对账不平。
    
* 专家级别的回答:
    1. 误差的"非确定性" 与 "不可累加性"：
        * 他不仅仅是 0.1+0.2 ！=0.3 它还不满足交换律 (A+B)+C ！=A+(B+C)
        *  后果：在分布式计算（如 MapReduce/Spark）中，数据分片顺序是不确定的。今天跑的结果可能是 100.00，明天因为调度顺序变了，结果变成 99.999999。这种“**结果不稳定**”比单纯的“算错”更可怕，因为它会让测试人员无法复现 Bug，让自动化对账脚本今天通过、明天报错。

    2. “大数吃小数”现象 (Loss of Significance) **丢失精度**
        * 当两个数量级差异巨大的浮点数相加时（例如 1,000,000.00 + 0.01），小数的有效位可能会直接被丢弃，因为浮点数的尾数位数有限（Double 只有 53 位有效二进制位）
        * 场景：在金融流水中，既有亿级的累计余额，又有几分钱的手续费。用 Double 累加，那几分钱可能直接“消失”了，导致账实不符。
    3. 比较操作陷阱: 
        * 不能直接对比你不能直接用 == 判断两个 Double 是否相等。必须引入一个 epsilon (如 1e-9) 来判断 abs(a-b) < epsilo
        * 风险：这个 epsilon 设多少？设大了会把真实的 1 分钱差异漏掉；设小了又会把浮点误差误报为差异。这是一个无法调优的死胡同。
* 专家级别的表述:
    “严禁使用 Float/Double 的核心原因不仅是精度丢失，更是运算的非确定性和有效位截断。
    * 第一，IEEE 754 导致十进制小数（如 0.1）在二进制下无限循环，存储时必然截断，产生固有误差。
    * 第二，浮点运算不满足结合律，在分布式并行计算中，由于数据分片和计算顺序的不确定性，会导致同一份数据每次跑出的结果都不一样，这对要求‘绝对一致’的金融对账是致命的。
    * 第三，存在大数吃小数现象，当金额跨度大时，小额交易（如手续费）的有效位会被丢弃。
    * 因此，金融系统必须使用定点数（Decimal）或整数（Long/BigInt，以分为单位），利用 CPU 的整数运算单元保证绝对的精确性和可重复性。”
