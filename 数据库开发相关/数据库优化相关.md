## 数据库配置优化

* 内存分配
  innodb_buffer_pool_size  缓存数据和索引，建议设为物理内存的50%~75%（专用DB服务器）
* 日志与刷盘
  `innodb_log_file_size`
  `innodb_flush_log_at_trx_commit`
  控制事务日志大小和刷盘策略；若允许少量数据丢失风险，可设为 2 提升写性能
* 链接管理
  `max_connections` 最大连接数
  `wait_timeout` 链接超时时间
* 查询缓存 旧版本中可缓存 SELECT 结果，但高并发下易失效，一般不推荐 现在一般使用redis缓存
* 临时表/排序
  `tmp_table_size`
  `sort_buffer_size`
  控制内存中临时表和排序空间，避免频繁磁盘 I/O
* 并发控制
  innodb_thread_concurrency
  控制 InnoDB 并发线程数，防止 CPU 过载
* 怎么说:
  **我们会根据业务负载调整关键参数。比如在 OLTP 场景下，优先调大** `innodb_buffer_pool_size` **减少磁盘读；对于写密集型服务，适当调大 redo log 并将** `innodb_flush_log_at_trx_commit=2` **来提升吞吐。同时通过监控（如 Prometheus + Grafana）观察缓冲池命中率、慢查询数等指标，持续调优**

## SQL语句优化（Query层面优化）

### 善用索引

* WHERE 、JOIN 、ORDER BY 、GROUP BY 字段考虑索引
* 避免在索引列上使用函数表达式:
  **❌** `WHERE YEAR(create_time) = 2025`
  ✅ `WHERE create_time BETWEEN '2025-01-01' AND '2025-12-31'`
* 使用 `EXPLAIN` 分析执行计划，关注:
  `type`（最好为 `ref` **或** `range`，避免 `ALL`）
  `key` 是否命中索引
  `rows` 扫描行数是否过多
* 避免SELECT *
  只查询需要的字段，而不是全部的字
* 分页优化
* 避免隐式类型转换
  字符串字段使用数字查询会导致索引失效
* 慎用子查询，优先JOIN
  因为子查询可能会执行多次而JOIN通常可以优化为一次扫描
* 批量操作代替循环单条
  插入/更新尽量采用 `INSERT INTO ... VALUES (...), (...), ...` **或** `ON DUPLICATE KEY UPDATE`。
* 如何说:
  我会先通过慢查询日志定位瓶颈 SQL，用 EXPLAIN 看执行计划。比如发现全表扫描，就检查 WHERE 条件是否命中索引；如果是深度分页，就改用游标分页。同时坚持‘只查必要字段’、‘避免函数包裹索引列’等原则。在复杂报表场景，还会考虑预计算或物化视图

## Java 等应用代码的最佳实践（Application 层面优化）

### 使用链接池

* **不要每次请求都新建连接！**
* **推荐：HikariCP（高性能）、Druid（带监控）**
* **合理配置：**
  * `maximumPoolSize`：根据 DB 承载能力设定（如 20～50）
  * `connectionTimeout`、`idleTimeout`：避免连接泄漏

### 批处理(batch)

* **插入/更新大量数据时，用** `addBatch()` **+** `executeBatch()`
* **示例（JDBC）

  ```java
  try (PreparedStatement ps = conn.prepareStatement("INSERT INTO users(name) VALUES(?)")) {
      for (String name : names) {
          ps.setString(1, name);
          ps.addBatch();
      }
      ps.executeBatch(); // 一次网络往返
  }
  ```

### 合理使用ORM，避免N+1问题

* **Hibernate / MyBatis 中：**
  * **❌ 循环内查关联对象 → N+1**
  * **✅ 用 JOIN FETCH（Hibernate）或** `<collection>` **一次性加载（MyBatis）**
* **开启 SQL 日志（如** `logging.level.org.hibernate.SQL=debug`）便于排查
