## ACID的实现

* MySQL 事务的实现，尤其是其核心的 ACID 特性，主要依赖于 InnoDB 存储引擎提供的两套关键机制：`日志系统`和`并发控制（锁与 MVCC版本控制）`。

## 原子性 (Atomicity) 的实现
* 简单回答一下原子性，就是一个操作，要么都做，要么都不做，不会发生操作做了一半就停止的事情，为了实现这一点，需要做的是操作回滚，而这个的核心机制是**Uodo Log(回滚日志)** 当 InnoDB 执行一个修改操作（如 `UPDATE`、`INSERT`、`DELETE`）时，它会先在 `Undo Log` 中记录一条与原始操作相反的“反向操作”。 
* 例如：你执行了一条 `UPDATE accounts SET balance = balance - 100 WHERE id = 1;`，`Undo Log` 会记录一条类似 `UPDATE accounts SET balance = balance + 100 WHERE id = 1;` 的日志。
回滚时：如果事务中途失败或你主动执行 ROLLBACK，InnoDB 就会读取 Undo Log 中的反向操作并执行，将数据恢复到事务开始前的状态，从而保证了操作的“全有或全无”。



## 持久性 (Durability) 的实现

* 回顾一下持久性持久性保证一个事务一旦提交，它对数据库中数据的改变就是永久性的，即使数据库发生故障也不会丢失。
* 核心实现机制 `Redo Log` (重做日志) Redo Log 是 InnoDB 引擎独有的物理日志。它的核心思想是“预写式日志”（Write-Ahead Logging）。
      * 先写日志：当事务修改数据时，InnoDB 会先将这个修改操作记录到 Redo Log 中，这个过程是顺序写入磁盘，速度非常快。  
      * 再写数据：之后，系统会在后台找一个合适的时机，再将数据从内存（Buffer Pool）刷新到磁盘的数据文件中，这个过程是随机 I/O，相对较慢。  
      * 崩溃恢复：如果在数据还没刷到磁盘时数据库就崩溃了，重启后，InnoDB 会读取 Redo Log，将已经提交但尚未写入数据文件的修改重新执行一遍（重做），从而保证数据的持久性。  
      * 补充：Redo Log 与 Binlog 的协同为了保证 InnoDB 引擎层的数据和 MySQL Server 层的 Binlog（用于主从复制和数据恢复）的一致性，MySQL 采用了“两阶段提交”。事务提交时，会先写 Redo Log 并标记为 PREPARE 状态，然后再写 Binlog，最后才将 Redo Log 标记为 COMMIT 状态。  


## 隔离性 (Isolation) 的实现

* 回顾一下隔离性 隔离性保证多个事务并发执行时，彼此之间不会互相干扰。这是实现最复杂的部分，`MySQL` 通过 锁 (Lock) 和 `MVCC` (多版本并发控制) 两种机制共同实现。  
      * 核心机制：MVCC (多版本并发控制) + 锁 (Lock)MVCC 通过在每行记录后面保存两个隐藏的列（一个保存行的创建版本号，一个保存行的删除版本号）来实现。配合 Undo Log，它可以快速读取到数据的历史版本。不同的事务隔离级别，MVCC 和锁的配合方式也不同   
      * 读未提交 (`Read Uncommitted`)  实现：几乎不使用 MVCC，直接读取数据最新的值，无论其是否被提交。 问题：会导致脏读，即读到其他事务未提交的修改。
      * 读已提交 (`Read Committed, RC`) 实现：每次执行 SELECT 查询时，都会生成一个新的 Read View（快照），只能看到已经提交的事务所做的修改。问题：解决了脏读，但会导致不可重复读，即在一个事务内，两次查询同一数据可能得到不同结果  
      * 可重复读 (`Repeatable Read, RR`)实现：这是 InnoDB 的默认隔离级别。它在事务第一次执行 SELECT 时生成一个 Read View，并在整个事务期间复用这个快照。因此，事务内多次读取的结果总是一致的。问题：解决了脏读和不可重复读。但对于幻读（其他事务插入了符合查询条件的新行），MVCC 无法完全解决。因此，InnoDB 会结合 Next-Key Lock (临键锁) 来防止其他事务在查询范围内插入新数据，从而在很大程度上避免了幻读。  
      * 串行化 (`Serializable`) 实现：最高级别，通过强制事务串行执行来避免所有并发问题。它会对所有读取的数据都加上共享锁，导致读写操作互相阻塞，性能极差，基本不使用。  

## 一致性 (Consistency)
* 一致性是事务的最终目标，它不是一个独立的机制，而是原子性、隔离性和持久性共同作用的结果。它保证事务执行前后，数据库都从一个合法的、满足所有约束（如主键唯一、外键关联、字段非空等）的状态，转换到另一个合法的状态。
