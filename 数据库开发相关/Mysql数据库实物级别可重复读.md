## 核心机制：MVCC 是如何做到“可重复读”的？

* 在事务第一次执行 SELECT 时生成一个 Read View，并在整个事务期间复用”，这是 MVCC（多版本并发控制）的灵魂。可以想象Read View “拍照片” 时机：在 可重复读（RR） 级别下，这张照片是在你事务中第一次发起普通查询（SELECT）的那一瞬间拍下的。规则：这张照片里记录了当时所有“正在活跃（未提交）”的事务 ID 列表


* 场景详解: 
      * 事务 A 开启，拍了“照片”（Read View），此时数据是 v1。
      * 事务 B 开启，把数据改成了 v2，并提交。
      * 事务 C 开启，把数据改成了 v3，并提交。
      * 事务 A 再次查询数据。
      * 结果：事务 A 拿着自己手里的旧“照片”去比对，发现 v2 和 v3 的修改者 ID 都不在照片的“已提交白名单”里（或者在活跃列表里），所以事务 A 视而不见，依然通过 Undo Log 回溯读取到了 v1。  
      * 结论：只要事务 A 不提交、不重启，它手里的“照片”就不换，所以它看到的世界永远是静止的。这就完美解决了不可重复读。


## 为什么 MVCC 搞不定“幻读”？

因为 MVCC 只管“普通查询”（快照读），它管不了“当前读”。
* 概念解释: 快照读：SELECT * FROM table WHERE id > 10;（不加锁，读历史版本）。MVCC 能完美解决这种场景下的幻读。
* 概念解释：当前读：SELECT * FROM table WHERE id > 10 FOR UPDATE; 或者 UPDATE table SET ... WHERE id > 10;。这种操作必须读取最新的数据，并且要加锁。
* 概念解释：幻读： 假设事务 A 查询 id > 10 的记录，发现有 5 条。此时，事务 B 插入了一条 id = 15 的记录并提交。如果事务 A 再次进行当前读（比如想更新 id > 10 的所有行），如果不加锁，事务 A 就会看到这条突然冒出来的 id = 15 的记录。这就叫幻读。  


## 解决幻读的工具Next-Key Lock（临键锁）
InnoDB 的锁不仅仅是锁住行（`Record Lock`），它还能锁住间隙（`Gap Lock`）。
* `Record Lock`：锁住具体的某一行（比如 id=10）。  
* `Gap Lock`：锁住两个索引记录之间的空隙（比如 id=10 到 id=20 之间）。  
* `Next-Key Lock` = `Record Lock` + `Gap Lock`。它锁住一个范围，并且包含边界。  


## 总结：MySQL RR 级别的“双重人格”


| 操作类型 | SQL 示例 | 使用的机制 | 能否看到别人的修改/插入？ | 结果 |  
| :--- | :--- | :--- | :--- | :--- |  
| 普通查询 (快照读) | `SELECT * FROM t ...` | MVCC (Read View) | 不能 (看到的是事务开始时的快照) | 彻底解决 幻读 |  
| 加锁查询/更新 (当前读) | `SELECT ... FOR UPDATE`<br>`UPDATE ...` | Next-Key Lock | 不能 (别人插不进来，你也读不到未提交的) | 基本解决 幻读 |  

一句话总结：MySQL 的 RR 级别，读的时候靠 MVCC 维持“时光静止”，写（或加锁读）的时候靠 Next-Key Lock 构筑“铜墙铁壁”，两者配合，才实现了接近完美的隔离性。
