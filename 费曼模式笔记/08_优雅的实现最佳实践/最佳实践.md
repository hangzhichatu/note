## 面向接口编程（解耦的终极奥义）
* 一句话说明白就是，在具体的业务代码中，有些可能会发生拓展的，或者类型存在泛型的情况的对象（比如服务场景里面的客户类型对象），我们业务代码里面不直接写死要使用哪个类型的对象，而是定义抽象接口，让需要替换的类实现该接口，这样就实现了固定的业务逻辑和多样的细节方法之间的解耦
* 核心逻辑：代码里不要写死“我是谁”，而要写“我能干什么”。
* 一句话总结：针对抽象（接口）写代码，不要针对具体实现写代码，这样换实现类时不用改原来的代码

## 参数化行为（把代码当数据用）
* 费曼类比：就像“洗衣机模式”。洗衣机（主逻辑）不用改，你只需要选“羊毛模式”或“快洗模式”（参数化的行为/Lambda），它就能干不同的活。
* 核心逻辑：把一段逻辑（比如打折算法）封装起来，像传数字一样传给方法。 这个逻辑可以是实现了同一个接口的不同具体类，它有同名的方法或者之际就是Lambda表达式
* 一句话总结：别为了换个小逻辑专门写个类，直接把逻辑（Lambda）传进去，用完即走。

* 这个也可以说是 用“**函数式接口**”代替“**策略模式**” ：
      *  优化场景演示: 
         * 学过策略模式，为了解耦，你需要： 定义一个接口 `PayStrategy`。 写三个类 `AlipayStrategy`, `WechatStrategy`, `UnionPayStrategy` 如果逻辑很简单，这三个类会显得非常臃肿（为了醋包了顿饺子）
          * 利用 Java 8 的 Lambda 表达式 和 函数式接口。你可以把“策略”直接当成一个参数传进去，而不需要专门定义一个类
          * java实现:传统写法（啰嗦）：
  
```java
// 定义接口
interface DiscountStrategy { double calc(double price); }
// 定义类
class VipStrategy implements DiscountStrategy { ... }
// 调用
context.setStrategy(new VipStrategy());
```
* java实现高手写法（巧思）：
```java
// 直接把“行为”作为参数传递
public void checkout(double price, java.util.function.Function<Double, Double> discountRule) {
    double finalPrice = discountRule.apply(price);
    // ...
}

// 调用时，直接写逻辑，不用定义类
checkout(100.0, price -> price * 0.8); // 直接传 Lambda   
```
    
## 用“包装类”实现“防御式编程”
* 对对象进行判空导致的层级很深（类似下面的内容）
```java
if (user != null) {
    if (user.getAddress() != null) {
        if (user.getAddress().getCity() != null) {
            return user.getAddress().getCity();
        }
    }
}
return "Unknown";
```

* 使用 Optional 或者 自定义包装类 来包裹数据。
```java
// 使用 Optional 链式调用
return Optional.ofNullable(user)
               .map(User::getAddress)
               .map(Address::getCity)
               .orElse("Unknown");
```

## 更进阶的巧思（领域模型）：
* 不要暴露原始数据类型，而是使用应用类型，在初始化的时候就对传入数据做校验。
* 这样做的好处，传入数据如果有问题，不会在具体的业务代码部分报错，而是在初始化对象的时候就会报错了
* 代码示范
```java
// 坏代码
public void send(String email) { ... } // 调用者可能传 "abc" (非法邮箱)

// 好代码
public void send(Email email) { ... } // 调用者必须 new Email("abc@xx.com")，构造时就会校验
```
* 核心思想：“**让非法状态无法被表示**”。通过包装，把**校验逻辑收拢在构造方法**里，业务代码里就不需要写 if 校验了

## 用“记录类”代替“参数列表” --参数内聚（拒绝长参数列表）
```java
public void createUser(String name, String email, String phone, int age, String addr, String city, String zip) { ... }
```
`createUser("Tom", "a@b.com", ...)` 这些参数多到爆炸，也不好记忆 以下的内容才是更好的实践  
```java
// 定义一个不可变的数据载体
public record UserContext(String name, String email, int age) {}

// 方法签名瞬间清爽
public void createUser(UserContext context) { ... }
```
核心思想：“内聚”。把属于同一个概念的数据捆绑在一起。这不仅是为了好看，更是为了以后扩展——如果要加个 password 字段，你只需要改 UserContext，不需要改所有调用 createUser 的地方
