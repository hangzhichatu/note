## Part 1：运行时数据区

### 线程私有 vs 线程共享

| 区域 | 归属 | 主要用途 | 会 OOM 吗 |
|------|------|---------|-----------|
| **堆（Heap）** | 共享 | 存对象实例，GC 主要区域 | ✅ 可 OOM |
| **虚拟机栈（VM Stack）** | 私有 | 存栈帧（局部变量表/操作数栈等） | ✅ 可 OOM（也 StackOverflow）|
| **本地方法栈** | 私有 | native 方法调用 | ✅ |
| **方法区（Metaspace）** | 共享 | 类的元信息、常量池（JDK8 起） | ✅ 可 OOM |
| **程序计数器（PC）** | 私有 | 当前执行字节码行号 | **❌ 唯一不会 OOM** |

**关键点：**
- JDK 8：方法区用 **Metaspace（元空间）** 替代永久代 PermGen，存**类的元信息**（不在堆，用本地内存）
- 程序计数器是唯一不会 OutOfMemoryError 的区域，且线程私有
- 栈 OOM 是 StackOverflowError（递归过深），堆 OOM 是 OutOfMemoryError

### 堆的划分（物理结构）
```
堆 Heap
├── 新生代 Young（默认 1/3）
│   ├── Eden（8）
│   ├── Survivor 0（1）
│   └── Survivor 1（1）    ← 默认 Eden:S0:S1 = 8:1:1（-XX:SurvivorRatio=8）
└── 老年代 Old（默认 2/3）
```

## Part 2：对象的一生（创建 + 布局 + 访问）

### 对象创建流程（简版）
```
类加载检查 → 分配内存 → 内存初始化(默认值0/null) → 设置对象头 → 执行构造方法<init>
```

### 对象内存布局（3 部分）
```
对象头（Mark Word + 类型指针）
实例数据（字段值）
对齐填充（padding，8 字节对齐）
```

**对象头 Mark Word 内容（与对象状态相关）：**
- 未加锁/未重 hash：存**identity hashcode（哈希码）**
- 锁状态：偏向锁标记 / 轻量锁指向锁记录 / 重量锁指向 monitor
- GC 分代年龄
- 类型指针（Klass Pointer）：指向该对象属于哪个类
- 数组对象额外存**数组长度**

### 对象访问定位（2 种）
| 方式 | 原理 | 优点 |
|------|------|------|
| **句柄** | 栈→句柄池→对象 | GC 移动对象不用改引用 |
| **直接指针**（HotSpot 默认）| 栈→对象（含类型指针）| 快，少一次间接寻址 |

## Part 3：对象死亡判定（GC Roots）

### 可达性分析
从 **GC Roots** 出发，可达的对象存活，不可达可回收。

### GC Roots 包括（面试背）：
- ✅ 虚拟机栈（栈帧本地变量表）引用的对象
- ✅ 方法区**静态属性（static）**引用的对象
- ✅ 方法区**常量**引用的对象
- ✅ 本地方法栈 JNI 引用的对象
- ❌ 堆中任意对象**不是** GC Roots

### 4 种引用类型（按强度）：
| 类型 | 回收时机 | 用途 |
|------|---------|------|
| 强引用 | 永不回收（除非不可达）| 常规 new |
| 软引用 | 内存不足时回收 | 缓存 |
| 弱引用 | 下次 GC 就回收 | 缓存（WeakHashMap）|
| 虚引用 | 随时可能回收，无法取对象 | 对象回收跟踪 |

## Part 4：三大基础 GC 算法

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **标记-清除** Mark-Sweep | 标记可达→清未标记 | 简单 | **内存碎片**、效率不稳 |
| **标记-复制** Mark-Copy | 存活复制到另一块→清原块 | **无碎片**、存活少时快 | **浪费一半内存** |
| **标记-整理** Mark-Compact | 标记后存活移到一端→清边界外 | 无碎片、不浪费 | 移动成本高 |

**选择逻辑（核心）：**
- 存活率低 → 复制算法（复制的对象少，成本低）
- 存活率高 → 整理算法（复制会复制一大堆，移动反可接受 + 消碎片）

## Part 5：分代回收（动态过程）

### 为什么分代？
> 对象"朝生夕灭"：绝大多数用完即死，少数长寿。分代 = 按存活率分开，各自用最合适算法。

### 对象的一生流程
```
新对象 → Eden
   │
   ├─ Minor GC：复制算法，存活对象 S0↔S1 倒腾，年龄++
   │
   ├─ 晋升老年代的条件（三选一）：
   │   ├─ 年龄 ≥ 15（默认 MaxTenuringThreshold）
   │   ├─ 大对象（超 PretenureSizeThreshold）直接进老年代
   │   └─ 动态年龄：Survivor 中同龄对象总和超 Survivor 一半，≥该年龄的直接晋升
   │
   └─ 老年代空间不足 → Major/Full GC（标记-整理或标记-清除）
```

### ⚠️ 关键理解
- **为什么要两个 Survivor**：复制算法需要**空区接收**。一个 Survivor 会"搬两趟/新旧混"；两个交替当空区才能高效运转
- **为什么年龄晋升（不一开始进老年代）**：新生代小+存活率低→Minor GC 又快又便宜（"火葬场"）；让短命对象死在新生代，避免塞满老年代触发昂贵的 Full GC。年龄阈值当"筛选器"，证明长寿才晋升
- **Minor GC**：新生代，复制算法，快
- **Full/Major GC**：老年代，标记-整理，STW 长，尽量少触发

**面试金句：**
> "新生代存活率低用复制算法（Eden+S0+S1，8:1:1）；老年代存活率高用标记-整理。分代核心 = 存活率不同分开，各自选最合适算法。"

## Part 6：GC 收集器（重点 G1）

### 传统收集器（分代物理分离）
- **CMS**（老年代）：并发标记-清除，追求低停顿，但**有碎片**、可能 Concurrent Mode Failure
- Serial/Parallel：STW 停顿长

### G1（Garbage First，JDK9+ 默认）
**两大核心设计（面试必答）：**
1. **停顿可预期**：通过 `-XX:MaxGCPauseMillis`（默认 200ms）控制 STW 停顿时间
2. **Region 取代物理隔离**：堆分成 ~2048 个小块 Region，新生代/老年代是**逻辑概念**、由 Region 动态组成，无物理边界

**Region 机制：**
- 每个 Region 动态扮演：Eden / Survivor / Old / **Humongous（大对象区，超 Region 一半）**

**回收特色：增量回收 + 价值排序**
- 每次 GC 只回收**一部分 Region**
- 按"垃圾最多、回收最快"排序（**Garbage First 垃圾优先**，名字由来）
- → 在有限停顿内回收尽可能多的垃圾

**跨 Region 引用：** 用 **Remembered Set（记忆集/RS）+ 卡表** 记录外部引用，GC 不全堆扫

**G1 的两类 GC：**
| 类型 | 回收对象 | 特点 |
|------|---------|------|
| Young GC | 只回收 Young Region | 复制，STW 但快 |
| Mixed GC | Young + 部分价值高的 Old Region | 渐进清老年代 |

**面试金句：**
> "G1 把堆分成 Region，新生代/老年代逻辑分代、物理混存。通过控制回收 Region 数量和垃圾优先排序，让停顿可预期（MaxGCPauseMillis），在指定停顿内多回收垃圾。跨 Region 用 RS 记忆集避免全堆扫。"

## Part 7：类加载机制 + 双亲委派

### 类加载 5 阶段（顺序必背）
```
加载 Loading → 验证 Verification → 准备 Preparation → 解析 Resolution → 初始化 Initialization
```

| 阶段 | 做什么 |
|------|--------|
| **加载** | 读字节流，转成方法区运行时结构 + Class 对象（唯一可自定义）|
| **验证** | 安全检查，确保字节流符合规范 |
| **准备** | 静态变量分配内存 + **设默认值**（0/null/false，非代码赋值）⚠️ final 常量此处就设真值 |
| **解析** | 常量池符号引用 → 直接引用（可延迟）|
| **初始化** | 执行 `<clinit>`（静态变量赋值 + 静态代码块）；new/访问静态/反射/主类触发 |

### 三个内置类加载器（顶到底）
```
Bootstrap（JAVA_HOME/lib 核心库 rt.jar，C++ 实现）
   ↑ 委派
Extension（lib/ext 扩展库）
   ↑ 委派
Application（classpath 我们写的类）
   ↑ 委派
自定义 ClassLoader
```

### 双亲委派模型（核心流程）
> 请求**先向上委派给父加载器**，一路到 Bootstrap；**父加载不了才回落**让子加载器自己尝试。

```java
// ClassLoader.loadClass 默认逻辑（双亲委派的代码实现）
protected Class<?> loadClass(String name, boolean resolve) {
    Class<?> c = findLoadedClass(name);      // 1. 查是否已加载
    if (c == null) {
        if (parent != null) c = parent.loadClass(name, false);  // 2. 委派父
        else c = findBootstrapClassOrNull(name);
        if (c == null) c = findClass(name);  // 3. 父不行，自己加载
    }
}
```

### ✅ 双亲委派解决的核心问题（面试必答）
1. **安全**：防止核心库被篡改（你写 `java.lang.String` 冒充？委派到 Bootstrap 加载真正的 String，假的永远不被加载）
2. **类的唯一性 / 避免重复加载**：保证同名类全局只有一份。⚠️ 不同加载器加载的同一类 = **两个不同的 Class 对象**（`instanceof` 为 false），浪费空间且混乱

### ⚠️ 打破双亲委派（高频追问）
**类唯一性 = 类全限定名 + 加载它的加载器** 共同决定。

**打破方式一：重写 `loadClass()`**（改委派流程）
- 默认双亲委派逻辑全在 `loadClass()` 里
- 重写它改变方向（如**先自己加载，找不到再委派父**）→ 代表 **Tomcat**（热部署、Web 应用隔离）
- ⚠️ 普通自定义加载器**只重写 `findClass()`**（父加载失败才自己加载）→ **不打破**，是正确扩展方式

**打破方式二：线程上下文类加载器（TCCL）+ SPI**
- **TCCL**：每个线程持有的上下文类加载器，默认 Application，可 `setContextClassLoader` 改，是个**可设置的"后门"**
- **问题**：双亲委派只能**向上**，Bootstrap 层的核心类（如 JDBC `DriverManager`）无法**向下**加载 classpath 的第三方实现（MySQL 驱动）
- **解决**：DriverManager 用 `ServiceLoader.load(Driver.class, Thread.currentThread().getContextClassLoader())` 借 **TCCL（Application）** 反向加载驱动
- 代表：**JDBC / SPI / JNDI / 日志 / Tomcat**（各 Web 应用独立 TCCL）

**两种打破方式对比：**
| | 重写 loadClass | TCCL |
|--|--------------|------|
| 方式 | 改委派流程本身 | 换一个加载器（绕过默认委派）|
| 代表 | Tomcat | JDBC/SPI |
| 本质 | 改"加载流程方向" | 提供"后门加载器" |

**面试金句（TCCL）：**
> "TCCL 是线程持有的上下文类加载器，默认应用类加载器，相当于可设置的高权限后门。双亲委派只能向上，导致 Bootstrap 核心类无法向下加载第三方实现，于是借 TCCL 拿到应用加载器反向加载驱动（JDBC），打破双亲委派。TCCL 是'换加载器'，重写 loadClass 是'改委派流程'。"
