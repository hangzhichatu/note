## 一、对象的创建：5 步（顺序不能错）

> ⚠️ 面试现场常见错误：漏掉「内存置零」的时机、把「设置对象头」放在构造方法之后。

```
① 类加载检查
   检查常量池能否定位到类的符号引用 + 该类是否已加载/验证/准备/解析/初始化
   没有 → 触发完整的类加载过程

② 分配内存
   从堆中划出一块确定大小的内存
   两种方式：
     · 指针碰撞 —— 堆地址规整（Serial / ParNew，带压缩）
     · 空闲列表 —— 堆地址不规整（CMS，标记-清除产生碎片）
   ⭐ 并发安全：CAS 重试（失败重试）或 TLAB（本地线程分配缓冲，默认开启）

③ 内存空间置零
   把分配到的空间全部置零
   → 保证实例字段不赋初值也能用（数值=0，布尔=false，引用=null）
   ⭐ 是「零值」不是「默认值」；此时对象头还没设置

④ 设置对象头
   Mark Word：哈希码 / GC 分代年龄 / 锁状态标志 / 偏向线程 ID / epoch
   类型指针：指向方法区的类元数据（Class 对象）
   ⭐ 到这里，对象对 JVM 来说「已诞生」，但 <init> 还没执行
      → 这就是「对象逸出 / 半初始化对象」的根本原因

⑤ 执行 <init>（构造方法）
   按代码赋真实初值 + 执行构造体内的语句
```

### ⭐ 面试金句（一句顶十句）
> **「第③步的零值和第⑤步的真实初值是两回事 —— 第④步之后对象就已经"可见"了，但<init>还没跑，这就是为什么会有"半初始化对象逸出"，也是 DCL 单例为什么必须 volatile。」**

### 对象的内存布局（顺带）
```
| 对象头 (Header) | 实例数据 (Instance Data) | 对齐填充 (Padding) |
    Mark Word + 类型指针        真实字段              补齐 8 字节倍数
```

### 对象访问定位（两种）
- **句柄**：栈 → 句柄池 → 对象实例/类型数据（稳定，对象移动只改句柄）
- **直接指针**：栈 → 对象（HotSpot 默认，快，少一次间接寻址）

## 二、对象分配：什么时候进老年代（4 条路径）

> ⚠️ 面试现场常见错误：只答「年龄到了」，漏掉最常被追的「动态年龄判定」。

### 路径 1：年龄达标
- 对象每熬过一次 Minor GC，年龄 +1
- 达到 `-XX:MaxTenuringThreshold`（默认 **15**；CMS 默认 **6**）→ 晋升

### ⭐ 路径 2：动态年龄判定（最高频追点！）
- **不是死等 15 岁**
- Survivor 中**相同年龄的所有对象大小之和 > Survivor 空间一半**时
- **年龄 ≥ 该年龄的对象直接晋升老年代**（不需要等到 MaxTenuringThreshold）
- **这才是真实晋升的主因**

### 路径 3：大对象直接进老年代
- 由 `-XX:PretenureSizeThreshold` 控制
- 目的：避免大对象在 Eden/Survivor 间反复复制
- ⭐ 只对 Serial / ParNew 有效，**G1 不认这个参数**

### 路径 4：空间分配担保（Survivor 放不下）
- Minor GC 后存活对象**塞不进 Survivor** → **直接进老年代**

### 补充
- **老年代空间不足 → 触发 Full GC**
- `System.gc()` 只是「建议」，不保证立即执行
- 分配策略：**对象优先在 Eden 分配**（Eden:S0:S1 = 8:1:1，默认比例）

## 三、跨代引用：卡表 + 写屏障

### 问题
Minor GC 要扫描新生代——但**老年代对象可能引用新生代对象**（跨代引用）。
如果为此扫描整个老年代 → Minor GC 就失去意义了。

### 方案
- **卡表（Card Table）**：把老年代分成一个个「卡页」（通常 512 字节），用**一个字节标记该卡页是否含跨代引用**
- **写屏障（Write Barrier）**：当**老年代对象引用新生代对象时**触发，把对应卡页标记为「dirty」
- Minor GC 时**只扫描 dirty 的卡页**，不用扫整个老年代

### ⭐ 一句话
> **「卡表是一种空间换时间的"记忆集"，写屏障负责维护它 —— 目的是让 Minor GC 不必扫描整个老年代。」**

## 四、对象死亡判定

### 4.1 可达性分析（主流）
- 从一组 **GC Roots** 出发，沿引用链遍历，**不可达的对象**判定为可回收
- （引用计数法：无法解决循环引用，Java 不用）

### ⭐ GC Roots 完整 5 条（易漏后两条）
1. **虚拟机栈（栈帧局部变量表）中引用的对象** ← 最核心
2. **方法区中类静态属性引用的对象**
3. **方法区中常量引用的对象**（如字符串常量池）
4. **本地方法栈中 JNI 引用的对象**（Native 方法持有）
5. **活动线程 / `Class` 对象 / 系统类加载器 / `synchronized` 锁对象**

### 4.2 finalize()（对象「复活」）
- 不可达对象先进 **F-Queue**，由低优先级 **Finalizer 线程**执行 `finalize()`
- 若在 `finalize()` 中**重新建立引用链**（如 `this` 赋给静态变量）→ **逃过本次回收（复活）**
- ⭐ **只能救一次**：第二次不可达时直接回收，不再执行 `finalize()`

### 4.3 为什么实战弃用 finalize()
| 问题 | 说明 |
|------|------|
| 时间不确定 | 可能迟迟不执行，甚至根本不执行（JVM 退出） |
| 异常被吞 | finalize 里抛异常不影响主流程，问题被掩盖 |
| 拖慢 GC | Finalizer 线程优先级低，可能导致对象堆积 |
- **JDK9 起 `@Deprecated`**；推荐 **`Cleaner`** 或 **`try-with-resources`**
- ⭐ **金句**：「靠 finalize 释放资源（关流/关连接）是错的，应该用 try-finally / try-with-resources。」

## 五、引用类型（4 种）

| 类型 | 回收时机 | 典型用途 |
|------|---------|---------|
| **强引用** | 永不回收（只要引用链在） | 普通 new |
| **软引用** `SoftReference` | **内存不足时**才回收 | 缓存（内存敏感） |
| **弱引用** `WeakReference` | **下次 GC 必回收** | ⭐ **ThreadLocal 的 key**；WeakHashMap |
| **虚引用** `PhantomReference` | 无法通过它访问对象；回收时收到通知 | 管理**直接内存**（NIO 的 DirectByteBuffer） |

⭐ **ThreadLocal 内存泄漏**：
- `ThreadLocalMap` 的 **key 是弱引用**（ThreadLocal 对象），但 **value 是强引用**
- 外部不再引用 ThreadLocal 之后 → key 被回收，但 **value 还在 Map 里**（Map 由 Thread 持有，线程池里的线程长存活）
- → **必须在用完后 `remove()`**，否则 key=null 的 entry 会一直占着 value

## 六、GC 分代设计动机（串联本文）

```
大部分对象朝生夕灭（弱分代假说）
  ↓
新生代对象存活率低
  ↓
用「复制算法」—— 只复制少量存活对象，成本 ≈ 存活对象大小，且无碎片
  ↓
老年代对象存活率高
  ↓
复制算法要复制的太多、还得额外预留一半空间 → 不划算
  ↓
改用「标记-清除」（CMS，低停顿但有碎片）
  或「标记-整理」（Serial Old / Parallel Old，无碎片但需移动对象）
  ↓
G1：整堆分 Region，整体标记-整理 + 局部复制，优先回收价值最高的 Region
```

### 名词别混
- **Minor GC**：新生代回收（频繁、快）
- **Major / Full GC**：老年代 / 整堆回收（慢、应尽量避免）
- **Full GC 触发**：老年代不足、空间担保失败、`System.gc()`、元空间满等

## 七、常见收集器速查

| 收集器 | 分代 | 算法 | 特点 |
|--------|------|------|------|
| Serial | 新生代 | 复制 | 单线程，Client 模式/小内存 |
| ParNew | 新生代 | 复制 | Serial 的多线程版（配 CMS） |
| Parallel Scavenge | 新生代 | 复制 | **吞吐量优先** |
| Serial Old | 老年代 | 标记-整理 | 单线程，CMS 的兜底 |
| Parallel Old | 老年代 | 标记-整理 | 吞吐量优先 |
| **CMS** | 老年代 | **标记-清除** | 低停顿；并发标记/清理、浮动垃圾、**并发模式失败**、**碎片**；`+UseCMSCompactAtFullCollection` 才在 Full GC 时整理 |
| **G1** | 整堆 | 标记-整理 + 局部复制 | **可预测停顿**（`MaxGCPauseMillis`）、**Region + 优先回收价值高的（Garbage First）**、无碎片 |
| ZGC | 整堆 | 染色指针 + 读屏障 | 超大堆极低停顿（JDK11+实验，15 转正） |

### ⭐ CMS 四个缺点（背）
1. 并发占用 CPU（影响吞吐）
2. **浮动垃圾**（并发清理期间新产生的垃圾，只能留到下次）
3. **并发模式失败（Concurrent Mode Failure）** → 退化成 Serial Old 单线程 Full GC，停顿暴涨
4. **内存碎片** → 提前触发 Full GC
