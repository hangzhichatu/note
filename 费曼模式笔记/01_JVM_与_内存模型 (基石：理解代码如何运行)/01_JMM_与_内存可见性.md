## 主内存/工作内存
* 一句话本质 :
    Java 内存模型（JMM）中的主内存与工作内存模型，是一个为了解决多线程并发问题而设计的抽象理论模型。它的核心目的是屏蔽不同硬件和操作系统的内存访问差异，确保 Java 程序在各种平台上都能有一致的内存访问效果。简单来说，这个模型定义了程序中所有变量（实例字段、静态字段等）的访问规则，它规定了变量如何存储在内存中，以及线程如何读取和写入这些变量。

* 核心概念: 主内存与工作内存：
    JMM将内存抽象的分为两种类型：  
    1.主内存(`Main Memory`)：它是一个所有线程都共享的区域。所有的共享变量都在这里。它对应的硬件是RAM，在JVM的内存区域划分里面，它主要对应的是堆(Heap)，它的访问速度相对较慢，但是它是线程之间传递数据的唯一通道 **共享通道**  
    2.工作内容(`Working Memory`)：定义:每个线程私有的内存区域。它保存了该线程使用到的，来自内存的共享变量的副本。它对应的L2、L1等高速缓存和寄存器，在JVM中，它主要对应虚拟机栈中的局部变量表。  它访问速度极快，但是线程之间无法直接访问对方的工作内存。  
    **核心规则：线程对变量的所有操作（读取、赋值）都必须在其自己的工作内存中进行，不能直接读写主内存中的变量。不同线程之间变量值的传递，必须通过主内存来完成。**

* 核心概念：八种原子操作:  



| 操作类型 | 作用域 | 描述 |  
| :--- | :--- | :--- |  
| read (读取) | 主内存 | 将一个变量的值从主内存传输到工作内存，为 `load` 操作做准备。 |  
| load (载入) | 工作内存 | 将 `read` 操作获取的变量值放入工作内存的变量副本中。 |  
| use (使用) | 工作内存 | 将工作内存中变量的值传递给执行引擎（用于执行代码）。 |  
| assign (赋值) | 工作内存 | 将执行引擎接收到的值赋给工作内存中的变量副本。 |  
| store (存储) | 工作内存 | 将工作内存中变量的值传输到主内存，为 `write` 操作做准备。 |  
| write (写入) | 主内存 | 将 `store` 操作获取的变量值写入主内存的变量中。 |  
| lock (锁定) | 主内存 | 标识一个变量为线程独占状态。 |  
| unlock (解锁) | 主内存 | 释放一个被锁定的变量，使其能被其他线程锁定。 |    

* 关键场景复现:  
    一个典型的变量读取和修改流程如下：  
    线程需要读取一个变量时，会先执行 read 和 load 操作，将变量从主内存复制到自己的工作内存。  
    线程在工作内存中通过 use 和 assign 操作来使用或修改这个变量的副本。  
    当需要将修改同步回主内存时，会执行 store 和 write 操作，将新值写回主内存。  

* JMM解决的问题，以及它为什么要被引入，本质上是为了解决由硬件性能优化带来的三大并发问题：**可见性**、**原子性**和**有序性**  
     * 1可见性: 问题根源：当一个线程修改了共享变量的值，这个修改首先发生在该线程的工作内存中。由于工作内存是私有的，其他线程无法立即看到这个变化，它们可能还在使用自己工作内存中的旧值。这就是可见性问题。解决方法。解决方案：Java 提供了 volatile、synchronized 等关键字来保证可见性
         * `volatile`：保证一个线程对 `volatile` 变量的修改会立即刷新到主内存，并使得其他线程中该变量的缓存副本失效，强制它们在下一次使用时从主内存重新加载。
         * `synchronized`：在一个同步块或方法执行完毕后，线程会将工作内存中所有共享变量的修改都刷新到主内存；在获取锁时，会清空工作内存，确保从主内存读取最新的变量值。
     * 2原子性 问题根源：原子性指一个或多个操作要么全部执行成功，要么全部不执行，不可被中断。虽然 JMM 保证了单个 read、load、assign 等操作的原子性，但像 i++ 这样的复合操作（包含读取、加1、写回）在多线程环境下就不是原子的，可能导致数据不一致。解决方案：使用 `synchronized`、`ReentrantLock` 或 `java.util.concurrent.atomic` 包下的原子类（如 `AtomicInteger`）来保证复合操作的原子性。
     * 3有序性    问题根源：为了提高性能，编译器和处理器常常会对指令进行重排序。在单线程环境下，这不会影响最终结果，但在多线程环境下，重排序可能导致程序执行顺序与代码顺序不一致，从而引发难以预料的 Bug。 解决方案：`volatile` 和 `synchronized` 都能禁止特定类型的指令重排序。JMM 通过 内存屏障（`Memory Barrier`） 来实现这一点。volatile 变量的读写操作前后会插入特定的内存屏障，强制规定操作的顺序。
* 教科书级别的总结:JMM 是一个抽象模型：它不是 JVM 运行时的实际内存划分（如堆、栈），而是一套用于定义多线程如何正确访问共享变量的规范和契约。
核心是主内存和工作内存：通过这种划分，JMM 解释了多线程环境下数据不一致的根本原因。
目标是解决并发问题：JMM 通过定义一系列规则（如 happens-before 原则）和同步机制（如 volatile、synchronized），为 Java 开发者提供了一套强大的工具，用以编写正确、高效的并发程序。

* 快速自测 <a id ="JMMQuestions"></a>
Q1:在 JMM 中，线程是如何读取和修改共享变量的？它可以直接操作主内存吗？  
A1:不能直接操作,线程对变量的所有操作（读取、赋值）都必须在其工作内存（Working Memory）中进行线程不能直接读写主内存（Main Memory）中的变量。流程： 必须先将变量从主内存拷贝（read/load）到工作内存，操作完后再同步（store/write）回主内存。  
Q2:当一个线程修改了共享变量的值，其他线程多久能看到这个变化？volatile 关键字是如何解决这个问题的？  
A2:默认情况下不确定（可能永远看不到，取决于缓存同步策略）。volatile 保证立即可见。问题根源： 修改发生在线程的工作内存（CPU 缓存）中，未刷新到主内存，其他线程读取的是自己工作内存中的旧副本。Volatile 机制：
写： 强制将新值立即刷新到主内存。
读： 强制使其他线程的工作内存中该变量副本失效，迫使它们下次使用时从主内存重新加载。  
Q3:为什么 volatile 关键字不能保证复合操作（如 i++）的原子性？请举例说明。  
A3:答案： 因为 i++ 包含三个独立的操作，volatile 只能保证单次读写的可见性，无法保证这三个步骤作为一个整体不被中断。  
Q4:什么是“指令重排序”？JMM 通过什么机制来禁止重排序以保证有序性？  
A4指令重排序是编译器或处理器为了优化性能，改变代码执行顺序的行为。JMM 通过内存屏障来禁止特定类型的重排序。  
Q5在不使用 volatile 或锁的情况下，仅仅通过 synchronized 同步块，能否保证一个线程修改的变量对另一个线程可见？为什么？  
A5能。这是基于 JMM 的 Happens-Before 原则。
规则： 一个解锁操作（unlock）happens-before 于随后对同一个锁的加锁操作（lock）。
过程：
线程 A 在同步块内修改变量，退出同步块（解锁）时，会将工作内存的修改刷新到主内存。
线程 B 进入同一个锁的同步块（加锁）时，会清空工作内存，并从主内存重新加载最新的变量值。
因此，synchronized 既保证了原子性，也保证了可见性和有序性。  

## Happens-Before 原则
* 一句说明白: Happens-Before 原则解决了一个终极痛点：在充满指令重排序和缓存的世界里，我如何确定一个线程的修改，另一个线程一定能看见？  
* 在这里它基于场景和行为定制了一下8条原则，内容存在确定的Happen-Before情况，**如果操作 A happens-before 操作 B，那么操作 A 的执行结果（对内存的修改），对操作 B 必须是可见的**   
* Happens-Before 的八大“天然法则”  
      * 1. 程序顺序规则: 这是最符合人直觉的法则，在一段线程里面，代码写在前面的操作 happens-before 写在后面的操作。 ps:**注意：虽然编译器和 CPU 可能会重排指令，但必须保证单线程执行结果不变（as-if-serial 语义）。**  
      * 2. 锁规则，对一个锁的解锁操作，happens-before 后续对同一个锁的加锁操作。这是`synchronized`的核心原理，  
          * 线程 A 退出同步块（解锁）前，会把工作内存的变量刷回主内存。  
          * 线程 B 进入同步块（加锁）时，会清空工作内存，从主内存重新读取。   
          * 结论：线程 B 一定能看到线程 A 在锁内做的修改。
      * 3. volatile 变量规则 对一个 volatile 变量的写操作，happens-before 后续对同一个变量的读操作。：
          * 线程 A 写 volatile 变量，强制刷新到主内存。
          * 线程 B 读 volatile 变量，强制从主内存加载。
          * 结论：B 一定能看到 A 的最新值。
      * 4. 线程启动规则   线程 A 调用 thread.start() 之前的所有操作，happens-before 线程 B（被启动的线程）的任何操作 **人话：你在启动子线程之前，给变量赋的值，子线程一定能看到。**
      * 5. 线程终止规则 内容：线程 A 的任何操作，happens-before 线程 B 调用 thread.join() 返回后的操作。 **人话：子线程干完活退出了，主线程调用 join() 等待它结束后，主线程一定能看到子线程修改后的结果。**
      * 6. 线程中断规则  内容：对线程 interrupt() 的调用，happens-before 被中断线程检测到中断事件（如抛出 InterruptedException 或 isInterrupted() 返回 true）。
      * 7. 对象终结规则  内容：对象的构造函数执行结束（初始化完成），happens-before 它的 finalize() 方法开始。  
      * 8. 传递性规则  内容：如果 A happens-before B，且 B happens-before C，那么 A happens-before C。
            **人话：这是逻辑推理的基础，把上面的规则串联起来。**
## volatile
* 一句话本质 ：
    volatile 是通过插入**CPU内存屏障指令(LoadLoad/StoreLoad)**强制刷新 **Store Buffer** 并且失效其他核心的 **缓存行** (关联点:**MESI**) 解决了多核缓存
    不一致的问题，从而保证了 **可见性和有效性** ，代价 **禁止乱序执行导致的流水线停顿**

* 关键场景复现:  
    * 正面应用场景:
        <a id="SingletonjavaCode"></a>
        当我们需要指令以**此按次序执行**的时候，使用该关键字：
        ```java
        // 缺少 volatile
        private static Singleton instance; 
        public static Singleton getInstance() {
            if (instance == null) {
                synchronized (Singleton.class) {
                    if (instance == null) {
                        instance = new Singleton(); // 致命隐患点
                    }
                }
            }
            return instance;
        }
        ```

        这个时候在多线程场景下可能会出错，这个方法是一个**懒加载**的单例模式，假设有两个线程A、B分别使用getInstance方法获取单例对象，当该对对象还没有初始化的时候  
        两个线程均进入了 `getInstance() ` 方法内，这里就先假设 A线程先执行了 `instance = new Singleton();` 语句吧，注意这个创建对象的操作并不是原子性的，它分为多个子步骤 
        - 1.**分配内存：在堆空间中为对象分配一块内存** 、
        - 2**初始化对象，执行构造函数，填充对象字段**、
        - 3**赋值引用：将 instance 变量指向这块分配的内存地址** ，在没有使用volatile修饰的情况下对象的初始化过程步骤会被优化成   
        1->3->2 表面上看上去没什么对吧？反正初始化和赋值引用这两步谁先谁后不影响最终结果 -->如果是**单线程**的话,现在线程B也进到了getInstance方法了，并且检查了下发现instance它并不为空于是就return了该对象了，但是这个时候有可能 这个对象还是执行第二步，初始化对象，也就是说返回了一个 **半初始化**的对象给线程B用，这个时候就可能会出现问题了。而volatile实现这个是通过 **内存屏障**实现的。  
    * 多线程下保证**可见性** ：  
        可见性的定义：在多核环境下，一个核修改了该对象 其他核读取的时候会读取到该对象的最新值
* 用自己的话复述:  
    > **volatile**关键字，普通变量：每个人都在自己的小本子（L1缓存）上记笔记。老师（线程A）改了黑板上的字，小明（线程B）低头看自己的小本子，以为字没变，继续按旧的做。
    volatile 变量：老师配了一个大喇叭。只要老师改了黑板上的字，就通过喇叭喊一声‘变了！’。所有听到的人必须立刻划掉自己小本子上的旧数据，下次用时必须抬头看黑板。
    代价：每次改字都要喊喇叭，还要等所有人确认，速度比偷偷改小本子慢多了。而且如果几个人同时抢着改，喇叭会吵死（性能下降）。

    核心 volatile是是“**广播通知机制**”，而不是“**排队锁机制**” 关于 volatile 导致的缓存一致性的实现，详见 [MESI Protocol](##mesi-protocol)。（mesi待补充）
* 性能与边界  
    适用场景:  
    * 状态位标志: : volatile boolean stopped，用于优雅关闭线程
    * **单次安全发布** : 前面的懒汉式单例模式[点击跳转](#SingletonjavaCode)、配置对象的应用解析
    * 独立观察指标，非高频更新的
    
    不适用的场景 :
    * 复合运算：因为volatile没法保证这些操作的原子性，中间回被打断，导致数据丢失
    * 高频写入竞争：在循环中成千上万次修改同一个volatile变量  引发 **缓存行抖动** Cache Line Ping-Pong 性能下降 10-50倍  替代方案: 使用 LongAdder 或 ThreadLocal 分段统计。
    * **StoreLoad** 屏障: 这是最贵的屏障。它要求之前的所有写操作完成后，才能执行之后的读操作。这会清空 CPU 流水线，导致处理器空转等待

## final 语义
* 在 JMM 中，final 的语义主要体现在两个层面：
      * 语法层面：保证“不可变性”（基本类型值不变，引用类型地址不变）。
      * 内存层面：禁止指令重排序，保证对象在构造过程中的“安全发布”。
* 语法层面的“不可变性” ： 修饰基本类型：值一旦赋值，终身不变。修饰引用类型：引用地址一旦指向某个对象，终身不能指向别的对象（但对象内部的内容是可以修改的）。
* 内存层面：final 的“大杀器”——禁止重排序  
      * 1. 没有 final 时的“半初始化”危机 在没有 final 修饰的情况下，对象的初始化（构造函数执行）和对象的引用赋值（obj = new Object()）可能会发生指令重排序。  
      * 2. 加上 final 后的“安全发布”JMM 会强制插入内存屏障，禁止重排序。
* JMM 的两条铁律： 
      * 写 final 域规则：在构造函数内对 final 域的写入，禁止重排序到构造函数之外。效果：保证在对象引用被赋值给外部变量之前，final 属性一定已经初始化完成了。
      * 读 final 域规则：初次读对象引用，与随后初次读 final 域，这两个操作之间禁止重排序。效果：保证线程只要看到了对象引用，就一定能读到 final 域的正确值。  
      * 使用 final 修饰属性，不需要 volatile 或 synchronized，就能保证：一旦其他线程获取到了这个对象的引用，它就一定能看到这个对象中 final 域的正确初始化值。
* 总结：final vs volatile vs synchronized  

| 特性 | final | volatile | synchronized |  
| :--- | :--- | :--- | :--- |  
| 核心作用 | 不可变性 + 构造安全 | 可见性 + 有序性 | 原子性 + 可见性 + 有序性 |  
| 禁止重排序范围 | 窄：仅限构造函数内的初始化 | 广：所有读写操作前后 | 广：整个同步块进出 |  
| 多线程修改 | 不支持（一旦初始化不可改） | 支持（保证即时可见） | 支持（保证原子操作） |  
| 性能开销 | 极低（编译期/加载期优化） | 低（比锁轻量） | 高（涉及上下文切换） |  
| 适用场景 | 定义常量、不可变对象（如 String） | 状态标记位、单例双重检查 | 复杂逻辑的原子操作 |  

## mesi 协议
* 简单来说，JMM 是软件层面的契约，而 MESI 是硬件层面的执行者。
* 为什么需要 MESI？在现代多核 CPU 中，每个核心（Core）都有自己私有的 L1 和 L2 缓存（即 JMM 中的“工作内存”）。  
* 问题场景: 这就是缓存一致性（Cache Coherence）问题。MESI 协议就是为了解决这个问题而诞生的工业标准  
        1.核心 A 把变量 x 从内存读入自己的缓存，修改为 x=1。
        2.核心 B 也把变量 x 读入自己的缓存（此时还是 x=0）。
        3.如果核心 A 不通知核心 B，核心 B 就会一直以为 x=0，继续基于旧值计算。
* MESI 的四种状态：MESI 是四个单词的首字母缩写，代表了缓存行（Cache Line）的四种状态。每个缓存行都用 2 个比特位来标记自己的状态  

| 状态 | 名称 | 含义 | 核心特征 | 数据一致性 |  
| :--- | :--- | :--- | :--- | :--- |  
| M | Modified (已修改) | 脏数据。数据已被修改，且只存在于当前缓存中。 | 只有我有，且我和内存不一样。 | 不一致 (需写回内存) |  
| E | Exclusive (独占) | 干净数据。数据未被修改，且只存在于当前缓存中。 | 只有我有，且我和内存一样。 | 一致 |  
| S | Shared (共享) | 干净数据。数据未被修改，且可能存在于多个缓存中。 | 大家都有，我和内存一样。 | 一致 |     
| I | Invalid (无效) | 无效数据。该缓存行不可用。 | 数据作废。 | - |    

* 状态详解  
    M (Modified)：  
    这是最“霸道”的状态。当核心 A 处于 M 状态时，意味着只有核心 A 拥有这份数据的最新版本，主内存里的数据是过期的（脏的）。  
    此时如果其他核心要来读，核心 A 必须先把数据写回主内存，然后大家协商变成 S 状态。  
    E (Exclusive)：  
    这是最“舒服”的状态。只有我有这份数据，而且我没改过。  
    优势：如果我想修改数据，不需要通知其他核心（因为没别人在用），直接改成 M 状态即可，速度极快。  
    S (Shared)：  
    这是最“拥挤”的状态。大家都有这份数据，谁都没改过。  
    劣势：如果我想修改数据，必须先通过总线告诉所有其他核心：“你们手里的这份数据作废（Invalid）吧”，等它们都确认后，我 才能改成 M 状态。这会产生总线流量。  
    I (Invalid)：  
    数据过期或不存在。  
* 状态流转 ： MESI 协议通过监听总线上的读写请求来切换状态。我们可以把它想象成一个“状态机”  
        本地读取 (Local Read)：  
        如果缓存里有（E/S/M），直接读。  
        如果缓存里没有（I），去内存读。如果没别人用，变 E；如果别人也有，变 S。  
    
        本地写入 (Local Write)：  
        如果是 E：直接改，变 M（爽，不用通知别人）。
        如果是 S：先发信号让别人的缓存失效（Invalidate）， 然后自己变 M，再修改。  
        如果是 M：直接改（已经是老大了）。  

        监听他人读取 (Snooping Read)：  
        如果是 E：别人来读了，我不再独占了，降级为 S。      
        如果是 M：别人来读了，我必须把数据写回内存（Flush），然后降级为 S，让别人去读。     

        监听他人写入 (Snooping Write)：     
        不管我是 E 还是 S，只要发现别人要改数据，我立刻把自己的状态变为 I（失效）。     
* 副作用，**伪共享**
      * 原理：MESI 协议操作的最小单位是缓存行（Cache Line，通常是 64 字节），而不是单个变量。
      * 场景 变量 A 和 变量 B 靠得很近，在同一个 64 字节的缓存行里。
        线程 1 修改 变量 A，线程 2 修改 变量 B。  
      * 后果 ：线程 1 修改 A，根据 MESI 协议，它必须把整行缓存置为 M，并让其他核心的这行缓存失效。
        线程 2 的缓存行因此失效（虽然它改的是 B，和 A 没关系！）。  
        线程 2 被迫重新从内存读取。  
        结果：两个线程互相干扰，性能急剧下降，就像在“假共享”一样。    

      * Java 解决方案：使用 @sun.misc.Contended 注解或填充字节（Padding），确保热点变量独占一个缓存行，避免被 MESI 协议“误伤”。     
        关于字段填充的JVM启动配置 ：
        可以配置吗？ 可以。
        参数是什么？ -XX:ContendedPaddingWidth。
        怎么用？ 必须配合 -XX:-RestrictContended 才能让普通类的注解生效。
        默认多少？ 128 字节（为了对抗 CPU 预取机制）。
        需要填充的变量添加注解  
    
```java
import sun.misc.Contended;

public class MyData {
    @Contended
    public volatile long value = 0L;
}
```
