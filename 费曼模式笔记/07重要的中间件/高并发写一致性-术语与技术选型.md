## 〇、总框架：并发写冲突的三种解法（先记这个，一切对号入座）

> **同一个人同时改同一份数据 → 会乱**
> → A 让他们别碰面：**路由 / 分片 / 单一写入者 / 一致性哈希**
> → B 碰面了讲规矩：**锁(悲观) / CAS+版本(乐观)+重试 / 自旋**
> → C 改坏了能退回：**事务 / 幂等 / 回滚**
> 所有术语都归进这三桶里记。

---

## 一、数据层术语（数据长啥样、归谁管）

- **数据分片 Sharding**：按规则把大表切多块（分片）。例按 `user_id % 8` 拆 8 份。拆后单机变薄。
- **分片键 Shard Key**：决定"这条数据去哪个分片"的字段（如 account_id）。无它不知往哪存取。
- **副本/复制 Replication**：一份存多份（主 Primary/从 Replica）保高可用+读扩展。≠ 分片（分片=切多份，复制=存多份）。
- **幂等 Idempotency**：同操作做 N 次结果一样。用 `request_id` + 唯一索引兜底，**是"敢自旋重试"的底气**（无幂等重试=灾难）。

## 二、软件/逻辑层术语（并发代码怎么处理）

- **临界区 Critical Section**：同一时刻只允许一个线程/事务执行的代码段（"扣款+流水要包起来的那段"）。
- **悲观锁 Pessimistic**：先假设会冲突 → 一开始就锁。代表 synchronized/ReentrantLock / DB `SELECT...FOR UPDATE`。
- **乐观锁 Optimistic**：先假设基本不冲突 → 改前核对版本，不符失败/重试。代表原子类 CAS / DB version UPDATE。
- **版本号 Version**：每行加 `version`，改一次 +1；`UPDATE...WHERE version=你读到的`，对不上=冲突了。
- **行锁 Row Lock**：只锁某一行不是整表：`UPDATE account SET balance=balance-30 WHERE id=? AND balance>=30`（InnoDB 行锁+原子扣减+余额校验三合一）。
- **事务 & ACID**：多操作捆成一个不可分单元＝全成或全回滚。A 原子 C 一致 I 隔离 D 持久。
- **自旋 Spin**：CAS 失败原地循环重试；对付偶发冲突，代价是长时间抢不到就空转烧 CPU。
- **AQS**：Java 所有锁+同步工具共同地基＝通用排队器（state 状态 + CLH 队列 + CAS）。ReentrantLock/Latch/Semaphore/Barrier 都是用户，重写 tryAcquire/tryRelease 出不同工具。
- **降级 Backoff/Graceful degradation**：冲突太频繁，乐观→悲观、降低重试频率（堵车改收费高速）。

## 三、硬件/实例/路由层术语

- **实例 Instance**：一个跑起来的服务进程/容器（一个人）。
- **路由 Routing**：把请求决定发给哪个实例/分片。
- **负载均衡 LB**：把请求平均分给多实例防过载（Nginx/网关）。⚠️ 只管"平均"，不保证"同 key 同实例"→ 是防过载不是防冲突。
- **会话亲和/一致性路由 Sticky**：保证同一 key(账号) 的请求稳定发到同一目标（一致性哈希/按 key 路由）→ 减少跨实例抢同一行。
- **单一写入者 Single Writer**：每份数据任何时刻只一个"主人"写。是**从源头消灭冲突**的手法（别人碰不到就不冲突）。
- **选主/仲裁 Leader Election**：多副本选一个 leader，只有 leader 能写，保证单一写入者在分布式成立。
- **故障转移 Failover**：实例/主库挂了自动顶替。
- **分布式事务**：跨库跨机一致性（A 库扣款、B 库流水时）。方案：2PC（两阶段，强一致慢）/ TCC / Saga / 本地消息表。**当前只需知道名字+分工，主线推到微服务再深挖。**

## 四、一致性哈希（Consistent Hashing）详解

### 4.1 解决什么
分片/缓存**节点数量变化（扩缩容、宕机）时**，普通 `key % N` 会导致**几乎所有数据重新定位、大面积迁移/缓存雪崩**——一致性哈希让**增删只影响邻近一小段**。

### 4.2 算法 4 步
1. 哈希值域想成**环**（0~2³² 首尾相接）。
2. 节点（服务器）哈希落环上一点。
3. 数据 key 哈希后**沿环顺时针找第一个节点** = 归属。
4. 增删节点只抢走"它与其前一节点之间那段"数据。

### 4.3 关键实现（TreeMap 环）
- **`TreeMap.ceilingEntry(hash)`** = 顺时针第一个比它大的；没有就 `firstEntry()` 绕回环头。
- **虚拟节点**：真实节点在环上放 N 个影子（`node#v0..#v9`），解决两件事：
  - ① 负载均衡（真节点落点随机可能挤一堆）
  - ② **宕机/删除时数据平摊**（删 B=删它 10 个影子，影子各自的下家散落在不同真节点 → 不坨给单点）

### 4.4 无虚拟 vs 有虚拟（Boss 直觉印证）
| | 无虚拟节点 | 有虚拟节点(生产) |
|---|---|---|
| 增删后邻段数据归谁 | **坨给顺时针下一个**（单点负载突增，真集中） | 拆 N 段**平摊多台** |
> 修正："多 vs 坨"取决于**有没有虚拟节点**。朴素版确实有集中趋势（Boss 直觉对）；虚拟节点让它把那一整段拆成 N 小块平摊。

### 4.5 仍是"统计均匀"非精确 → Redis 为何不用它
虚拟节点只是近似均匀。**Redis Cluster 实际用"16384 固定哈希槽 + CRC16(key)%16384"**，槽可**精确迁移**，从根上避开一致性哈希"凭运气均匀、迁移不可控"。很多资料说"Redis 用一致性哈希"是**不准确**的。

### 4.6 生产自研少
不自研，直接用内置的：**Redis Cluster / ShardedJedis(客户端分片) / Cassandra / Nginx hash 指令**；真要自写就几十行 TreeMap 环 + 虚拟节点。

## 五、技术选型速查（方案 → 具体组件）面试 30 秒母版

| 方案目标 | 首选技术 | 配套/替代 |
|---|---|---|
| 分库分表 | ShardingSphere | MyCat |
| 强一致存储 | MySQL(InnoDB 行锁) | Oracle/PG |
| 超高频计数字段(可最终一致) | Redis(Lua/INCR) | — |
| 缓存分布式集群 | Redis Cluster | 一致性哈希/Ketama |
| 服务注册发现 | Nacos | Eureka/Consul |
| 入口 LB | Nginx | SLB / Spring Cloud Gateway |
| 分布式锁(悲观兜底) | Redisson(Redlock) | ZooKeeper/etcd 临时节点 |
| 乐观锁版本号 | MySQL version + UPDATE | ShardingSphere 兼容 |
| 幂等防重 | 唯一索引 + request_id | Redis setnx |
| 跨服务最终一致 | RocketMQ + 本地消息表 | Kafka / Saga |
| 分布式事务(深水区) | Seata(TCC/AT) | 2PC / Saga |

**面试母版一段话：**
> "数据层我用 ShardingSphere + MySQL 按 account_id 分片，行内 version 做乐观锁；超高并发余额先进 Redis Lua 原子扣减再落 MySQL。路由/缓存走 Redis Cluster / 一致性哈希保证同一 key 归位；分布式悲观兜底用 Redisson。跨服务可靠性走本地消息表 + RocketMQ 最终一致，强一致才上 Seata/TCC。所有重试写入带 request_id + 唯一索引兜幂等。"

## 📌 一句话能力链（自己记住的表述方式）
> 降低并发写冲突：**数据层按 key 分片（一致性哈希保平滑）→ 单一写入者；逻辑层乐观锁+版本号处理偶发竞争，超阈值降级加锁；跨多数据靠 DB 事务/跨机靠分布式事务；幂等 request_id 兜重试不重复。** 复杂场景路由层用一致性哈希把同 key 请求粘同实例。
