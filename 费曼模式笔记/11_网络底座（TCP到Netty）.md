## 0. 🎯 一句话本质

> **一次网络请求 = "数据怎么从网卡爬进你的 Java 代码" + "怎么用最少的线程管住最多的连接"。**
> 前者是 **TCP + 内核数据通路**（数据怎么来），后者是 **IO 多路复用 + Reactor**（怎么不被线程拖死）。
> Netty 不是新发明，而是把这两件事的工程坑（粘包、线程模型、内存管理）全都填好了的**工业级成品**。

## 1. 🧱 TCP：连接的建立、终结与代价

### 1.1 三次握手（含关键细节）

```
Client                                Server
  │── SYN, seq=x ─────────────────────→│   （不能带数据）
  │←─ SYN+ACK, seq=y, ack=x+1 ────────│   （不能带数据）
  │── ACK, seq=x+1, ack=y+1 ──────────→│   （可以带数据 ✅）
  │═══════════════ 数据传输 ═══════════│
```

**三次握手到底在确认什么**：
1. **双方收发能力都正常**（客户端能发能收，服务端能发能收）
2. **交换并同步初始序号**（ISN）
3. **防止历史延迟连接**浪费服务端资源 ← 这才是"为什么不能两次"的根本

**为什么不能两次？**
> 两次握手时，**服务端无法确认"客户端收到了我的 SYN+ACK"**。若客户端的旧连接请求在网络中延迟后才到达，服务端会为一个"客户端早已放弃"的连接白白分配资源。

**为什么前两次不能带数据？**
> 握手未完成，连接状态未就绪，带数据会引入复杂的状态处理；第三次之后客户端已确信"我能发、服务端能收"，数据捎带才安全。

### 1.2 四次挥手 与 TIME_WAIT

```
Client                                Server
  │── FIN ────────────────────────────→│   （我要关了）
  │←─ ACK ─────────────────────────────│
  │←─ FIN ─────────────────────────────│   （我也关了）
  │── ACK ─────────────────────────────→│
  │   ⏳ TIME_WAIT (2MSL) 后关闭         │   ← 主动关闭方进入
```

**TIME_WAIT 存在的两个理由**：
1. **保证最后的 ACK 能到达**：若 ACK 丢失，服务端会重发 FIN，客户端仍在 TIME_WAIT 可重发 ACK
2. **让延迟报文在网络中消亡**：否则可能污染下一个使用相同四元组的连接

**生产问题（要能量化）**：
- 主动关闭方（高频调用方 / 短连接服务端）积累大量 TIME_WAIT
- Linux 默认 2MSL ≈ **60 秒**，短连接场景下**本地端口（6 万多个）被耗光** → 无法建立新连接
- **解决**：
  - `net.ipv4.tcp_tw_reuse=1`（复用时序安全的 TIME_WAIT socket）
  - 改用**长连接 / 连接池**（从根本上减少连接数）
  - `SO_LINGER`（慎用，会发 RST）
- ⚠️ **反常识**：`tcp_tw_recycle` 已被**移除**（Linux 4.12+），会误杀 NAT 后的连接 —— 答它会被扣分

## 2. ⭐ IO 多路复用：select / poll / epoll

> **摸底空白区，本笔记重点。面试深水区高频。**

### 2.1 共同点（先说清楚，避免答偏）

三者都是 **IO 多路复用**：
- 都是"**一个线程监听多个 fd**"
- 阶段1（等数据就绪）**阻塞在 select/epoll**
- 阶段2（数据拷贝）**自己调 read() 拷贝** → **所以都是同步 IO**

### 2.2 本质区别：怎么知道"哪些 fd 就绪了"

| | select | poll | **epoll** |
|---|---|---|---|
| **数据结构** | 位图 fd_set | pollfd 数组（链表） | **红黑树 + 就绪链表** |
| **fd 上限** | **1024**（FD_SETSIZE） | 无 | 无 |
| **每次调用** | fd 集合**用户态→内核态全量拷贝** | 同左 | **只注册一次**，内核自维护 |
| **返回后** | **遍历全部 fd** 才知道谁就绪 | 同左 | **直接返回就绪链表**，无需遍历 |
| **复杂度** | O(n) | O(n) | **O(1)**（取就绪事件） |

**一句话本质**：
> **select/poll = 每次问内核"这堆 fd 哪些好了？"（全量拷贝 + 全量遍历）**
> **epoll = 内核自建一张表（红黑树），谁好了谁主动进就绪队列，我只取就绪的。**
> → 连接越多，epoll 优势越大。

**epoll 三大系统调用**（要能脱口而出）：
| 调用 | 作用 | 复杂度 |
|---|---|---|
| `epoll_create` | 创建 epoll 实例（内部红黑树） | — |
| `epoll_ctl` | 增/删/改 监听的 fd | O(log n) |
| `epoll_wait` | 阻塞等待就绪事件，返回就绪链表 | **O(1)** |

⚠️ epoll 的 O(1) 指"**取就绪事件**"的复杂度，不是整个流程。

### 2.3 LT vs ET（Netty 选 ET 的原因）

| | LT 水平触发（默认） | ET 边缘触发 |
|---|---|---|
| **通知时机** | 缓冲区**还有数据就每次返回** | **仅状态变化时通知一次** |
| **编程难度** | 简单 | 复杂 |
| **风险** | 效率略低（重复通知） | **不读干净就丢数据** |
| **典型** | 默认 | **Netty 默认 ET** |

**ET 为什么必须循环读到 `EAGAIN`**：
> ET 只在"从没数据→有数据"那一刻通知。若一次只读一半，**下次不再通知** → 剩余数据永久卡在缓冲区。
> 所以必须循环 `read()` 直到返回 `EAGAIN`（= "现在没数据了"，证明抽干）。

**必须配非阻塞 fd**：ET 下若 fd 阻塞，最后一个 read 会把线程卡死。

**Netty 为何选 ET**：它自带完整读循环框架，能保证读干净，用 ET 拿满性能。

## 3. ⭐ Reactor 与 Netty 线程模型

### 3.1 为什么业务不能放在 IO 线程

**Reactor 分工**：
- **IO 线程（Reactor）**：只做 `accept` / `read` / `write`，**快进快出**
- **业务线程池**：真正业务逻辑

**三个理由（结构化表达）**：
1. **串行阻塞 / 尾延迟放大**：一个 IO 线程管 N 个连接，某连接业务耗时 100ms → 其余连接事件全部排队
2. **吃不满多核**：单 IO 线程 = 单核，CPU 密集业务浪费多核
3. **风险传染**：一个慢请求拖垮整个 Reactor

**反例（什么时候可以合并）**：业务极快（纯内存）、无阻塞 IO、无锁竞争时，可合并省线程切换。

### 3.2 Reactor 三种模型

| 模型 | 说明 | 代表 |
|---|---|---|
| 单 Reactor 单线程 | 一个线程干连接+读写+业务 | 早期 NIO |
| 单 Reactor 多线程 | Reactor 管连接，业务丢线程池 | — |
| **主从 Reactor 多线程** | **MainReactor 管 accept，SubReactor 管读写** | **Netty 默认** |

### 3.3 BIO / NIO / AIO 对比

| | BIO | NIO | AIO |
|---|---|---|---|
| 模型 | 同步阻塞 | 同步**非阻塞**（多路复用） | 异步非阻塞 |
| 线程 | 一连接一线程 | **一线程管多连接** | 回调 |
| API | Stream | Channel+Buffer+Selector | CompletionHandler |
| 适用 | 连接少 | 高并发（Netty 基础） | Linux 支持不完善，少用 |

**BIO 致命问题**：1 万连接 = 1 万线程，线程栈默认 1MB → 光线程吃 10GB，加上上下文切换直接崩。

### 3.4 NIO 的坑 → 为什么需要 Netty

**手写 NIO 三大坑**：① 状态机复杂（半包）② 粘包拆包 ③ 线程模型易错

| 难题 | 手写 NIO | Netty |
|---|---|---|
| 粘包拆包 | 自己写状态机 | `LengthFieldBasedFrameDecoder` 内置 |
| 内存管理 | ByteBuffer 要 flip，易错 | `ByteBuf` 读写双指针 + 自动扩容 |
| 线程模型 | 自己写 Reactor | **主从 Reactor** 开箱即用 |
| 连接管理 | 自己实现心跳/重连 | `IdleStateHandler` |
| 内存泄漏 | 手动释放易漏 | 引用计数 + 泄漏检测 |

> **"NIO 是零件，Netty 是成品框架。"** Docker、RocketMQ、Dubbo、Spring WebFlux 底层都是 Netty。

## 4. 📦 TCP 粘包拆包与协议设计

**一句话本质**：**TCP 是字节流，没有消息边界。**（UDP 有数据报边界，故无此问题）

| 现象 | 说明 |
|---|---|
| 粘包 | 发两条消息，接收方一次读到两条 |
| 拆包 | 一条消息太大，接收方分多次读到 |

⚠️ **这不是 bug，是 TCP 固有特性** —— TCP 只保证字节顺序，不保证"消息"完整。

### 4.1 标准协议头设计（活学活用）

```
┌────────┬────────┬────────┬────────┬──────────────┐
│ 魔数    │ 版本号  │ 序列化  │ 消息类型│   长度字段    │
│ (4B)   │ (1B)   │ (1B)   │ (1B)   │    (4B)      │
├────────┴────────┴────────┴────────┴──────────────┤
│                  消息体 (Body)                     │
│            （长度由长度字段决定）                    │
└────────────────────────────────────────────────────┘
```

| 字段 | 作用 | 为什么需要 |
|---|---|---|
| 魔数 | 快速判断"是不是我的协议" | 第一时间拒绝非法连接 |
| 版本号 | 协议升级兼容 | 新旧版本共存 |
| 序列化算法 | 标明 Body 格式（JSON/Protobuf） | 解复用、可扩展 |
| 消息类型 | 区分请求/响应/心跳 | 分流处理 |
| **长度字段** | **解决粘包核心** | 接收方知道读多少字节 |
| Body | 真正的数据 | — |

**⚠️ 常见误区**：**校验码管"数据完整性"（防传输错误），HMAC/签名才管"防篡改"（需密钥）**，别混。

### 4.2 四种解决方案

| 方案 | 做法 | 缺点 |
|---|---|---|
| **① 长度字段**（最常用） | 头部写长度，按长度读 | 需协议约定 |
| ② 固定长度 | 定长，不足补空 | 浪费带宽 |
| ③ 分隔符 | `\n` 结尾（如 HTTP 头） | 内容不能含分隔符 |
| ④ 自定义协议头 | 魔数+版本+长度 | 复杂但最可靠 |

Netty 解码器：`LengthFieldBasedFrameDecoder` / `DelimiterBasedFrameDecoder` / `FixedLengthFrameDecoder`

## 4.5 ⭐ 盲区补充一：TCP 拥塞控制

### 两个"窗口"要分清

| | 流量控制 | 拥塞控制 |
|---|---|---|
| **管谁** | 接收方（别撑爆它） | 网络（别堵死路） |
| **窗口** | 接收窗口 `rwnd` | 拥塞窗口 `cwnd` |
| **谁通知** | 接收方在 ACK 里带 | **发送方自己探测（网络不告诉你）** |

> ⭐ **实际发送窗口 = min(rwnd, cwnd)**
> cwnd 是发送方**根据网络反馈动态估算**的、认为网络能承受的未确认数据量 —— **不是网络告诉你的**。

### 四阶段

| 阶段 | 行为 | 触发 |
|---|---|---|
| ① 慢启动 | cwnd **指数增长**（每 RTT 翻倍） | 连接开始 / 超时后 |
| ② 拥塞避免 | cwnd 线性增长（每 RTT +1） | cwnd ≥ ssthresh |
| ③ 快重传 | 收到 **3 个重复 ACK** 立即重传 | 3 个 dup ACK |
| ④ 快恢复 | `ssthresh=cwnd/2`，`cwnd=ssthresh`（不回 1） | 快重传后 |

**⚠️ 两个"回到起点"的区别（高频）**：

| 事件 | cwnd | 为什么 |
|---|---|---|
| **超时** | **→ 1，重新慢启动** | 网络"重病"（连 ACK 都回不来） |
| **3 个 dup ACK** | **→ 减半，快恢复** | 网络"小病"（能回包，只丢个别包） |

> 一句话：**"能收到反馈"说明网络还活着 → 不必从头开始。**

**为什么是 3 个 dup ACK**：1 个会误判乱序；数字太大发现太慢。3 是**误判率 vs 响应速度**的平衡。

**慢启动为什么"慢"却是指数**：慢在初始 cwnd=1 个 MSS（起点低），增长却是指数。

### 现代演进（加分）

| | CUBIC | BBR |
|---|---|---|
| 拥塞信号 | **丢包** | **带宽 + RTT** |
| 对缓冲区 | 倾向**填满** → bufferbloat | 主动**避免填满** |
| 后果 | 延迟飙升 | 延迟低吞吐高 |
| 适合 | 传统链路 | 长肥管道、丢包但带宽足 |

> **bufferbloat（缓冲膨胀）**：路由器缓冲区太大，CUBIC"丢包才减速"会填满缓冲区 → 延迟飙升但吞吐不涨。BBR 直接测带宽，不受此坑影响。

## 4.6 ⭐ 盲区补充二：半连接队列 与 SYN Flood

### 两个队列（关键）

```
客户端 SYN → [半连接队列 SYN Queue] → [全连接队列 Accept Queue] → accept()
          （收到SYN+ACK未收ACK）    （握手完成，等应用accept）
             tcp_max_syn_backlog         min(backlog, somaxconn)
```

| 队列 | 存什么 | 参数 | 溢出场景 |
|---|---|---|---|
| **半连接** | 发了 SYN+ACK、**没收到 ACK** | `tcp_max_syn_backlog` | SYN Flood → 半开堆积 |
| **全连接** | 握手**已完成**、等 accept | `min(backlog, somaxconn)` | 应用 accept 慢 |

### SYN Flood 原理

攻击者狂发 **SYN 但不回 ACK**（伪造源 IP）→ 服务端为每个 SYN 分配资源、发 SYN+ACK、等 ACK → **半连接队列塞满** → 正常 SYN 被丢。

> **资源不对称**：攻击者发 1 个 SYN（~40 字节，近零成本） vs 服务端分配连接表项+重传定时器 → **成本比可达 1:1000**。

### 防御：SYN Cookie（最经典）

> **不存储，用计算换存储** —— 把连接信息**编码进 SYN+ACK 的 seq 号**；收到 ACK 时**用计算重建状态**。

**⚠️ 为什么攻击者伪造不了**（关键理解）：
1. **seq 号是服务端算的**（`hash(四元组+时间+密钥)`），攻击者控制不了
2. 攻击者伪造 IP → **收不到 SYN+ACK** → 无法发出合法 ACK
3. 要伪造合法 ACK 必须知道哈希值 → 而哈希只在那份收不到的包里 → **死循环**

**⚠️ 真实弱点**：牺牲 TCP 选项（窗口缩放/SACK）影响性能 → 所以常配 `tcp_syncookies=2`（**队列快满才启用**）。

### 全连接队列溢出（生产更常见、更隐蔽）

- **现象**：用户报"连接超时"，**服务端日志却是空的** —— 因为三次握手在内核就完成了，应用层无感
- **原因**：应用 accept 太慢（线程池满 / 业务阻塞 / **JVM STW**）
- **排查**：`ss -lnt`（看 Send-Q 列）/ `netstat -s | grep -i listen`（看 overflow 次数）
- **`tcp_abort_on_overflow`**：0（默认）=丢 ACK（用户看到超时）；1=发 RST（用户立即感知被拒）

### ⭐ SYN_RECV 排障模板（Boss 实战总结）

```
现象：大量 SYN_RECV
  ↓ 量化：几~几十正常；持续上千/上万 → 异常
  ↓ 区分：
   【攻击】来源IP分散、SYN_RECV极多但 ESTABLISHED 少
   【应用慢】IP集中、SYN_RECV中等但伴随 accept 慢
  ↓ 支路A（攻击）：tcp_syncookies=1 + 降 tcp_synack_retries + 前置 LVS/Nginx/云高防清洗
  ↓ 支路B（应用慢）：线程池打满？Full GC？慢SQL/N+1？下游耗时？Netty业务是否误放IO线程？
```

## 4.7 ⭐ 盲区补充三：Netty EventLoop 单线程 与 ET/LT

### EventLoop 为什么"单线程"（刻意设计）

> **一个 Channel 的所有 IO 事件始终由同一个 EventLoop（线程）处理 → 完全不需要加锁。**
> **"单线程"是为了换"无锁"。**

三个理由：① 无锁化（多线程处理同一 Channel 就要同步 → 性能暴跌）② 避免上下文切换、cache 友好 ③ 保证同 Channel 事件顺序性

**多核怎么办**：多个 EventLoop 组成 **EventLoopGroup**，Channel 用**轮询**分配，**终生绑定**一个 EventLoop。

**默认线程数**：bossGroup = 1；workerGroup = **2 × CPU 核数**。

### ⭐⭐ ET vs LT（Boss 查资料纠正 AI 的案例）

> ⚠️ **重要纠正**：AI 曾称"Netty 默认用 ET"是**过时说法**。
> **准确事实**：Netty 早期支持 ET（`EpollChannelOption.EPOLLET`），**但 Netty 4.2 之后废弃原生 ET，统一用 LT**。
> 性能不靠 ET，靠：**无锁 EventLoop + ByteBuf 读写指针 + 内存池 + 零拷贝 + 高效线程模型**。

| | LT | ET |
|---|---|---|
| 通知 | 有数据就反复返回 | 仅状态变化通知一次 |
| 优点 | 简单稳健可预测 | 海量连接减少唤醒 |
| 缺点 | 重复唤醒 | 实现复杂、跨平台差异、写事件易错 |

**写事件为什么用 LT 且不能轻易注册 `EPOLLOUT`**：
> LT 下只要发送缓冲区**可写就不断通知** → 造成 **busy loop（空转 CPU）**。
> 所以 Netty **只在真正写不进去时才注册写事件，写完立即取消**。

## 5. 🔬 内核数据通路与零拷贝

> **摸底空白区，本笔记重点。这是"底层设计"能力的体现。**

### 5.1 一次 `read()` 的完整旅程

```
① 网卡收数据 ──DMA──→ 内核 Ring Buffer（网卡缓冲区）         【不占 CPU】
② 内核协议栈处理 ──→ socket 接收缓冲区（内核态）              【不占 CPU 太多】
③ 应用调 read() ──CPU 拷贝──→ 用户空间缓冲区                 【★ 耗时根源】
```

**关键点**：
- **DMA**：网卡直接写内存，不占 CPU（否则每字节都打断 CPU 会死）
- **内核缓冲区**：即使你代码没调 read，内核已经收着数据了（对应 TCP 接收窗口/滑动窗口）
- **两次数据拷贝**：网卡→内核（DMA，不占 CPU）、内核→用户（**CPU 拷贝，IO 慢的根源**）
- **为什么 IO 比 CPU 慢**：跨内核态/用户态拷贝 + 硬件延迟

### 5.2 零拷贝

**传统 `read() + write()` 发文件（4 次拷贝 / 4 次态切换）**：
```
磁盘 →[DMA]→ 内核页缓存 →[CPU]→ 用户缓冲区 →[CPU]→ socket缓冲区 →[DMA]→ 网卡
```
中间两次 **CPU 拷贝纯属浪费**（数据只是路过用户态）。

**`sendfile`（2 次拷贝 / 2 次切换）**：
```
磁盘 →[DMA]→ 内核页缓存 ─[CPU]─→ socket缓冲区 →[DMA]→ 网卡
              数据根本不进用户态！
```

**`mmap + write`（3 次拷贝）**：
```
磁盘 →[DMA]→ 内核页缓存（mmap 映射到用户空间）→[CPU]→ socket缓冲区 →[DMA]→ 网卡
                    （用户态共享内存，无拷贝）
```

| 方案 | 拷贝次数 | 特点 |
|---|---|---|
| 传统 read+write | 4 | — |
| **mmap+write** | 3 | 用户态能"看到"数据（可修改），仍有 1 次 CPU 拷贝 |
| **sendfile** | 2 | 最快，数据完全不过用户态，但用户态无法处理数据 |

**⚠️ 关键澄清**：
> **"零拷贝"不是"零次拷贝"**，而是**减少 CPU 拷贝 + 减少上下文切换**。DMA 拷贝与 CPU 无关。

**⚠️ 真正零拷贝（进阶）**：`sendfile` 配合网卡 **SG-DMA** 支持，可让数据**完全不经 CPU** → 0 次 CPU 拷贝。

**Netty 的"零拷贝"（另一层含义）**：`CompositeByteBuf`（逻辑合并 buffer 不实际拷贝）、`ByteBuf.slice()`、`FileRegion`（基于 sendfile）。

## 6. ⚡ 性能与边界

### 适用 / 禁区

| 场景 | 选择 |
|---|---|
| 连接少、内部系统、逻辑简单 | **BIO** 够用（如 572 的 SFTP） |
| 高并发、海量连接、网关 | **NIO + Netty** |
| 文件传输、静态资源 | **零拷贝（sendfile）** |
| 短连接高频调用 | ⚠️ 警惕 TIME_WAIT 堆积 → 用连接池 |

### 性能杀手
- **BIO 线程爆炸**：连接数 → 线程数，内存和上下文切换双杀
- **ET 漏读**：不循环读到 EAGAIN → 数据永久卡死
- **业务阻塞 IO 线程**：尾延迟放大，拖垮整个 Reactor
- **TIME_WAIT 堆积**：短连接场景端口耗尽
- **粘包拆包处理不当**：消息错乱
