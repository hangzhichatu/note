## 1. 🎯 一句话本质

**RAG = 把"外部知识"变成"可检索的索引"，检索时把最相关的**原文**塞进 prompt，让模型照着念。**

> RAG 两段式：
> ```
> 【离线：建索引】
> 原始文档 → 切分(chunk) → 每块算 embedding → 存进向量库
>                           ↓
>                     同时保留原文（向量是"索引"，不是"内容"）
>
> 【在线：检索】
> 用户问题 → 算 embedding → 向量库找最相似的 topK 块
>         → 取出这些块的【原文】→ 塞进 prompt → 模型回答
> ```
>
> **关键**：向量库里存的不是"内容"，是内容的"**坐标**"。检索时拿回来的是**原文块**，不是向量。

## 2. 💥 灾难现场 (The Disaster Scenario)

### 场景 A：以为向量检索万能，结果精确术语全丢

**错误认知**："上向量检索就对了，语义理解更强"

**底层发生了什么**：
```
用户问："LAMC_InterfaceManager 是干什么的"
文档标题："LAMC_InterfaceManager_mxJPO 183个JPO之一"

向量检索：
  embedding 把 "LAMC_InterfaceManager" 压缩成语义向量
  → 它和"若依接口类""集成管理类"的向量可能很近
  → 于是返回一堆【语义相关但不是这个类】的内容 ❌
```

**根因**：**embedding 会把专有名词/代码标识符"语义化"成模糊概念** —— 越精确的词，向量越容易漂移。

**修复关键**：
- 精确标识符（类名/方法名/报错码/专有名词）→ **BM25 更稳**
- 所以必须 **混合检索**，不能只上向量

### 场景 B：以为 BM25 就够用，结果换个说法就搜不到

**错误认知**："关键词检索又快又准，够用了"

**底层发生了什么**：
```
用户问："查询条件怎么写"
文档标题："## DomainObject.findObjects 的 where 条件"
           ↑ 只有 findObjects 和 where

BM25 切词：["查询","条件","怎么","写"]
  → 文档里这些词一个都没有 → 命不中 ❌
```

**根因**：**BM25 是字面匹配，不懂"query 条件"和 "where 条件"是一回事。**

**三个验证案例**：

| 查询 | BM25 | 向量 | 谁赢 |
|---|---|---|---|
| `findObjects 怎么用` | ✅ 命中（有标识符） | ⚠️ 可能漂移 | **BM25** |
| `查询条件怎么写` | ⚠️ 悬（靠文档有没有这些字） | ✅ | **向量** |
| `过滤对象的写法` | ⚠️ 悬 | ✅ | **向量** |
| `那个改文档版本号报错的问题` | ❌（"版本号"≠"Revision"，"改"≠"赋值"） | ✅ | **向量** |
| `那个问题呢` | ❌ | ❌ | **谁都输 → 需 Query Rewriting** |

**关键洞察**：判别标准**不是"问题精确不精确"，而是"问题里有没有字面能匹配的锚点"**。

### 场景 C：以为"多造几个同义查询"就等于语义检索

**错误做法**：用 LLM 把一个查询改写成 10 个同义词，全部走 BM25 —— "这不就语义检索了吗？"

**底层发生了什么**：
```
用户问："版本号报错"
文档写："Revision 赋值 bug"

LLM 造同义词：版本 / 版次 / revision ...
  → 只能覆盖"同义"
  → 覆盖不了"相关/共现"（"赋值"这个业务动作不在查询里，LLM 也想不到）
  → 本质仍是【字面匹配】，只是机会变多
```

**关键洞察**：向量空间里的"邻近"**不是同义词关系**，是"**使用场景/共现关系**"的统计。
> "Revision" 和 "版本号" 的桥梁，是 embedding 训练时铺的 —— **一旦落到"关键词"平面，桥就断了。**

**修复关键**：Query Expansion 和向量检索**互补不替代**：
- LLM 做 **Query Rewriting**（补指代、拆子问题、扩同义）
- 向量 + BM25 **并行检索**
- **RRF 融合**
- **Rerank 精排**

## 3. 🧠 费曼复述 (The Feynman Test)

### 👶 给实习生的比喻

**RAG 是什么**：给模型配一个**图书馆 + 索引卡**。
- 离线：把每本书切开，给每片纸写张"主题索引卡"（向量），但**卡上不写内容，只写位置**
- 在线：你问问题 → 拿你的问题找最像的索引卡 → **按卡去找那片纸的原文** → 把原文给模型看 → 模型照着念

**BM25 vs 向量**：
- **BM25 像图书馆的"书名目录"**：你查"Java"，就给你所有书名含"Java"的书。**精确，但你说"面向对象编程语言"它就找不到 Java 的书了。**
- **向量像图书管理员的"感觉"**：你说"我想找本讲面向对象的书"，他能给你 Java 相关的书（即使书名没有这些字）。**但你说"我要那本叫《Java编程思想》的"，他反而可能给你一堆"讲 Java 的书"，拿不准具体哪本。**

**→ 所以最好的办法是：书名目录 + 管理员一起用（混合检索）。**

### ⚖️ 核心对比

| 维度 | BM25（关键词） | 向量检索 |
|---|---|---|
| **匹配本质** | **字面**（词表对齐） | **语义**（向量空间邻近） |
| 索引结构 | 倒排索引 | HNSW / IVF 近似最近邻 |
| 查询复杂度 | **O(1)~O(词频)**，极快 | O(log n)~O(n) |
| 延迟 | **亚毫秒** | 毫秒~几十毫秒 |
| 内存 | 低 | **高**（维度×数量，1536维×10万条≈600MB） |
| 建索引成本 | 纯 CPU，几乎零成本 | **要跑 embedding 模型**（钱/算力） |
| 语义相似 | ❌ | ✅ 强 |
| **精确术语** | ✅ **强** | ⚠️ 弱（会被"语义化"） |
| 同义/改写 | ❌（需维护同义词表） | ✅ 强 |
| 代码/API 名 | ✅ | ❌ 容易漏 |
| 增量更新 | 容易 | 较麻烦 |
| 扩展性（万条以上） | 靠人维护目录 | ✅ 自动 |

### 混合检索架构（★ 正确形态）

```
用户查询
   ↓
①【Query Rewriting】LLM 改写查询（补指代、扩同义、拆子问题）
   ↓
②【并行检索】
   ├─ 向量检索（语义）────→ topK₁
   └─ BM25 检索（字面）───→ topK₂
   ↓
③【RRF 融合】按排名合并 → topK
   ↓
④【Rerank】交叉编码器精排
   ↓
⑤【生成答案】+ 引用
   ↓
⑥【可选：置信度循环】不够 → 回到①（限次数）
```

**RRF（Reciprocal Rank Fusion）怎么算**：
```
score(doc) = Σ  1 / (k + rank_i(doc))       # k 通常取 60
            各路检索
```
> 例：某文档在 BM25 排第 1、在向量排第 3 → 得分 = 1/(60+1) + 1/(60+3)
> **好处**：不用调权重，按"排名"融合，两路互补。

### "结合"是并行，不是串行（★ 关键区分）

```
❌ 错误（串行，有损）：
  查询 → embedding → 关键词 → BM25 → 判断 → 循环
              ↑ 中间损失信息，且丢了向量的语义优势

✅ 正确（并行）：
  查询 → [LLM改写] ─┬→ 向量检索 ─┐
                    └→ BM25检索 ─┴→ RRF融合 → Rerank → 生成
```
**一句话**：**"结合"不是让向量给 BM25 打下手，而是让两者平等投票。**

### Rerank 为什么必要（Bi vs Cross Encoder）

| | Bi-Encoder（召回用） | Cross-Encoder（精排用） |
|---|---|---|
| 做法 | 查询和文档**分别**编码成向量，算余弦 | 把 (查询, 文档) **拼在一起**喂进模型 |
| 能捕捉 | 粗粒度相似 | **细粒度词间交互** |
| 速度 | ✅ 快（文档向量可预先算好） | ❌ 慢（每个候选单独跑） |
| 精度 | 中 | **高** |

**三段式标准架构**：
```
① 召回层（快，从百万里捞几百）：向量 + BM25
② 精排层（准，从几百里选十几）：Cross-Encoder Rerank
③ 生成层：只把这几条喂给 LLM
```
**记忆点**：**Bi-Encoder 快但不准，Cross-Encoder 准但不快。一个用于召回，一个用于精排。**

## 4. ⚡ 性能与边界 (Performance & Boundaries)

### ✅ 适用场景 (Safe Zones)

| 场景 | 方案 |
|---|---|
| 知识量小（<几千字） | 全量塞上下文（不用 RAG） |
| 有精确标识符（类名/报错码） | BM25 优先 |
| 口语化/同义/跨表达 | 向量优先 |
| 生产规模（万条以上） | **混合检索 + Rerank** |
| 需要引用溯源 | 检索结果带原文出处 |

### 🚫 绝对禁区 (Danger Zones)

- **纯向量检索用于代码/API 知识库** → 精确类名会被语义化，召回漂移
- **纯 BM25 用于自然语言问答** → 换个说法就搜不到
- **串行"embedding→关键词→BM25"** → 丢语义优势，还多花一次 LLM
- **不处理指代（"那个""它"）** → 向量和 BM25 都会扑街
- **停用词/泛词进 BM25** → "文档""问题""那个"这类高频词 IDF 低，命中等于没命中

### 📉 性能杀手

**embedding 是成本大户**：
- 建索引时每条 chunk 都要跑一次（且文档更新要重跑）
- 维度越高越吃内存（1536 维 × 10 万条 ≈ 600MB）
- **所以 memory_search 要降级兜底**：embedding API 不可用时自动切 BM25。**不是优化，是保命。**

**上下文成本**：
- 检索回来多少条、每条多长，直接决定 token 成本
- **宁可少而精**：塞 100 篇不如选 5 篇最相关

## 5. 📊 检索质量评估

**怎么知道检索变好了？**

| 指标 | 含义 |
|---|---|
| **Recall@K** | 前 K 条里包不包含正确答案（能不能找到） |
| **Precision@K** | 前 K 条里有多少是相关的（找得准不准） |
| **MRR** | 第一个正确答案的排名倒数（越靠前越好） |
| **NDCG** | 考虑排序位置的综合评分 |
| **Hit Rate** | 至少命中一条的比例 |

**工程做法**：建一个"问题 → 应命中文档"的测试集（几十条就够），改检索策略后跑一遍对比。

## 6. ❓ 自测灵魂拷问 (Self-Quiz)

**Q1: RAG 里向量库存的是"内容"还是"坐标"？检索拿回来的是什么？**
A: (关键点：存坐标，拿回原文块；向量是索引不是内容)

**Q2: BM25 和向量检索的本质区别？判别该用哪个的标准是什么？**
A: (关键点：字面 vs 语义；标准是"查询里有没有字面能匹配的锚点"，不是"问题精确不精确")

**Q3: 为什么说"向量检索对精确术语反而不如关键词"？**
A: (关键点：embedding 把专有名词语义化成模糊概念，越精确越容易漂移)

**Q4: 混合检索为什么要并行而不是串行？**
A: (关键点：串行丢语义优势且多花 LLM；并行各取所长，RRF 融合)

**Q5: RRF 怎么算？为什么不用调权重？**
A: (关键点：Σ 1/(k+rank)；按排名融合，两路都排前面的得分高，天然平衡)

**Q6: 为什么混合检索后还要 Rerank？Bi vs Cross Encoder？**
A: (关键点：Bi 快但不准（无交互）；Cross 准但不快（拼一起跑）；召回用 Bi，精排用 Cross)

**Q7: 用 LLM 造 10 个同义查询走 BM25，能替代向量检索吗？**
A: (关键点：不能；本质是增强 BM25，仍是字面匹配；同义词覆盖不了"共现/相关"；还多花 LLM)

**Q8: 用户问"那个问题呢"，检索为什么必然失败？怎么解？**
A: (关键点：指代无语义信息，向量和 BM25 都救不了；需 Query Rewriting 用对话历史补全)

**Q9: 为什么 RAG 的质量问题 80% 在检索？**
A: (关键点：检索错了模型会忠实照着错资料胡说还带引用，比幻觉更难发现)

**Q10: 怎么做检索质量评估？**
A: (关键点：问题→应命中文档的测试集；Recall@K / Precision@K / MRR / NDCG)
