## 1. 🎯 一句话本质

**模型不会执行任何工具 —— 它只会输出一段形状为"我要调用某函数"的文本，真正的执行永远是宿主代码干的。**

> 三个推论（本讲一切概念的地基）：
> 1. **模型是决策器，代码是执行器** → 循环控制权在代码手里（防死循环、卡成本、管安全）
> 2. **工具是"暴露给模型的能力"，不是"强制执行器"** → 正确性必须靠出口校验，不能指望模型自觉
> 3. **Function Calling 管"怎么说话"，MCP 管"怎么插电"** → 两者是上下层，不是竞品

## 2. 💥 灾难现场 (The Disaster Scenario)

### 场景 A：以为"模型调用工具，工具返回结果给模型"

**错误认知**：模型 → 调用工具 → 工具执行 → 返回模型

**底层发生了什么**：
- 模型没有文件系统、网络、shell，**它执行的只有"生成 token"这一个动作**
- `tool_calls` 里的 `arguments` 只是**一段 JSON 字符串**，模型输出完就结束了
- 真正"调工具"的是你的代码：解析 → 校验 → **执行** → 包装成 tool 消息 → 回填 → 再问模型
- **最阴的**：如果你以为"模型在执行"，就会把"校验/兜底/防死循环"的责任推给模型 → 报错时模型原地打转（它只知道"工具失败"，不知道怎么改）

**修复关键**：**校验、执行、回填、终止全部写在宿主代码里**，模型只管输出意图。

### 场景 B：schema 卡太死，模型完不成任务直接摆烂

**错误做法**：把部署包的完整结构（JPO 名 + 列定义 + 交叉引用 + 路径）全塞进一个工具的 inputSchema，要求模型一次填完

**底层发生了什么**：
- 参数要过 JSON Schema 校验 → 字段越多、约束越严，**一次通过率指数下降**
- 模型失败时会重试，但**每次重试都可能换一种错法** → 烧 token、超时，最后输出"我无法完成"
- 更糟：模型为"凑齐必填参数"**编造内容**（幻觉式填参）

**修复关键**：**入口宽、内部严** —— 让模型面对最宽松的接口（只输出松散 intent），严格性（补默认值/规范化/把关）放在你的代码里。

### 场景 C：让模型自己保证 MQL 语法正确

**错误做法**：写个 lint 工具给模型调，以为"调了就不会错"

**底层发生了什么**：
- 工具是**执行器**不是**强制执行器** → 模型**可能压根不调**（它觉得自己写对了）
- 参数也可能传错（截断、带 markdown 围栏、拼写错）
- 就算调了、返回"非法"，模型也可能**不理解"非法在哪"**，重复同样的错

**修复关键**：**出口校验兜底** —— 模型不调工具也拦得住：返回给用户前，代码自己跑一遍 lint，不合格就打回重试（清洗→校验→重试）。

## 3. 🧠 费曼复述 (The Feynman Test)

### 👶 给实习生的比喻

**Function Calling 是什么**：模型是一个**只会填申请单的客服**。你问它"帮我读一下配置文件"，它不会自己跑去开文件——它填一张单子写着"申请调用 read，参数 path=AGENTS.md"，然后**递给你的代码**。真正去开文件的是**你的代码**（前台）。开完把结果贴在单子背面（回填），再递回给客服，客服接着说下一步。

- **模型的输出 = 申请单（意图）**，不是动作
- **你的代码 = 前台（执行器）**，干所有实事
- **`finish_reason`** = 单子上的状态：`tool_calls`=「我还要递单子」/ `stop`=「我说完了」

**Agent Loop 是什么**：就是"客服递单子 → 前台办事 → 结果贴回单子 → 客服再想"的**无限循环**，直到客服说"我没单子要递了"（`stop`）。**循环几轮是走出来的，不是排出来的** —— 这叫 Loop（循环），不是 Pipeline（流水线）。

**MCP 是什么**：**AI 工具界的 USB-C**。同一个工具（比如你的部署包生成器），插到 Cursor、Claude Desktop、自研 Agent 上都能用——**因为大家都认同一个"插座标准"**。没有 MCP 之前，每个框架要写一遍转接头（M×N）；有了 MCP，工具写一次（M+N）。

### ⚖️ 核心对比

| 概念 | 一句话本质 | 解决什么 | 常见混淆 |
|---|---|---|---|
| **Function Calling** | 模型输出"调用意图"JSON | 模型怎么表达要调工具 | ❌ 不是模型执行工具 |
| **MCP** | 工具暴露的标准化协议 | 工具怎么跨框架复用 | ❌ 不是 FC 的替代品（是下层） |
| **Tools** | 可执行函数（**模型**决定调） | 让模型能做事 | ❌ 不是 Resources |
| **Resources** | 可读数据（**应用**决定注入） | 给模型喂资料 | ❌ 知识库该做这个，不是 Tool |

| 安全分级方式 | 本质 | 为什么 |
|---|---|---|
| **按危险度** | 主观判断（"这危险吗"） | ❌ 判断会变、因人而异，没法写代码 |
| **按可逆性** ✅ | 事实判断（"能撤销吗"） | ✅ 客观、可自动化、可写规则 |

### Agent Loop = while 循环（★ 记忆锚点）

```
while (true) {
    resp = LLM(messages, tools)              // ① 模型思考 + 决定行动
    messages.add(resp.message)               // ② 不管文本还是 tool_calls 都要加
    if (resp.finish_reason == "stop") break; // ③ 出口：模型不调工具了
    for (call : resp.tool_calls) {           // ④ 可能多个（并行）
        result = execute(call)               //    你的代码真正执行
        messages.add(toolMsg(call.id, result))//   回填，靠 id 配对
    }
}
```

**三道墙（必须在代码里，不能交给模型）**：
```
① 最大轮数      → 软墙（防转圈）
② 超时/预算     → 硬墙（防烧钱）
③ 无进展检测    → 智能墙（防换皮重试，连续 N 轮 Observation 相同就停）
```

> **为什么控制权必须在代码**：模型能看见的是**文本**；代码能看见的是**成本、状态、安全边界**。模型给不了这三样。

### 部署包生成器的依赖链（串行 + 循环依赖）

```
① 数据模型(Type+属性) → ② JPO → ③ XLS/Spinner 配置
                                    ↑ 真·循环依赖：
   table 列定义 需要 JPO 的方法名
   JPO 方法入参 需要 table 列定义的对象类型
```

**破环三法**：① 定契约（JPO 签名 + 列定义同时冻结）② 占位符两遍法 ③ 人工裁决（HITL）
> **"为什么不能全自主"的真实案例：循环依赖 = 模型会打转。工作流里插一个"契约冻结"阶段就能破环。**

## 4. ⚡ 性能与边界 (Performance & Boundaries)

### ✅ 适用场景 (Safe Zones)

| 场景 | 做法 |
|---|---|
| 工具选择 | 用 **enum** 约束参数（生成时堵错，比事后校验强） |
| 错误回灌 | **细颗粒度**：报错 + 方向 + **示例**（把生成题变抄写题） |
| 并行调用 | **只读**可并行（无依赖+无副作用冲突） |
| 安全管控 | 沙箱 + 版本控制 → 大胆放开读写；删除/修改才审批 |
| 自主性 | **渐进式**：Workflow 做骨架，Agent 做肌肉 |

### 🚫 绝对禁区 (Danger Zones)

- **以为模型在执行工具** → 校验/兜底责任错位 → 死循环
- **schema 大而全** → 一次通过率暴跌 → 模型摆烂或编造参数
- **让模型"自觉调工具"保证正确性** → 出口没有校验 = 必翻车
- **两个写操作并行发起** → 竞态（同目录/同清单文件）
- **把"写操作串行"理解成"上写锁"** → 层面混淆（后者是资源层并发控制）
- **靠每次审批保安全** → 人烦死；正解是"让审批变得不必要"（沙箱+版本控制）
- **以为 MCP 管权限** → MCP 是能力协议，**没有 access control**

### 📉 性能杀手

**往返次数 ≈ 延迟和成本**：
```
串行: 模型→A→回填→模型→B→回填→模型   ← 3 次往返
并行: 模型→[A,B]→回填→模型            ← 2 次往返
```
→ 能并行就并行（判据两条：无数据依赖 + 无副作用冲突）

**M×N → M+N**：
```
无 MCP: M 个工具 × N 个框架 = M×N 套接入代码
有 MCP: M 个工具 + N 个框架，各自实现 MCP = M+N
```

**错误回灌的搜索空间**：
```
粗("参数非法")  → 猜→试→错→再猜，空间极大
细(带示例)      → 照抄示例改一下，空间≈0
```

## 5. 🔒 MCP 专项（本讲新增）

### 架构三角色

```
┌──────────┐   协议   ┌──────────┐   协议   ┌──────────┐
│MCP Host  │◄────────►│MCP Client│◄────────►│MCP Server│
│(Agent)   │          │(连接器)  │          │(工具方)  │
└──────────┘          └──────────┘          └──────────┘
  OpenClaw              Host内置           你的部署包生成器
```

### 三类能力（高频考点）

| 类型 | 谁决定 | 例子 |
|---|---|---|
| **Tools** | **模型**主动调 | `gen_xls` / `validate_xls` |
| **Resources** | **应用**决定注入 | 3de-ai-kb 知识库 ★ |
| **Prompts** | **用户**主动用 | "生成一个 Trigger JPO"模板 |

> ⚠️ **知识库做 Resources 不是 Tools**：因为"该不该注入这段知识"不该由模型决定，该由 RAG 检索逻辑决定。

### MCP vs Function Calling（必考）

| | Function Calling | MCP |
|---|---|---|
| 层次 | **模型 ↔ 应用** | **应用 ↔ 工具** |
| 规定 | 模型怎么表达调用意图 | 工具怎么暴露给应用 |
| 类比 | 语言（怎么说话） | **插座标准（怎么插电）** |

**缺的两样（FC 做不到的）**：
- 工具怎么被**发现** → MCP 的 `tools/list`
- 工具怎么被**调用** → MCP 的 `tools/call`

### MCP 的安全（反直觉）

| 层 | 管权限吗 |
|---|---|
| MCP 协议 | ❌ 不管（只定义怎么传调用/结果） |
| MCP Server | ✅ 业务级权限自己实现 |
| Host | ✅ 审批/沙箱/审计 |

> **MCP 有 capability negotiation（我能提供什么），但没有 access control（你有没有权调用）。**
> **类比**：USB-C 规定引脚，不规定"U 盘里文件谁能读"——那是上层的事。
> **信任风险**：恶意 Server / 提示注入 / 权限过大 → 这是 MCP 当前最大争议。

### 面试答法

> "MCP 我理解为 AI 工具界的 USB-C，解决的是'工具怎么被标准化暴露'的问题——它和 Function Calling 不在同一层，FC 管模型怎么表达调用意图，MCP 管工具怎么被提供出来。我实际用它把 3DE 的私有能力（JPO 生成、XLS 校验、MQL 封装）暴露给任意 AI 客户端，一次开发多框架通用。但要注意 MCP 本身不管权限，安全要靠 Host 层和 Server 层各自兜。"

## 6. 🔍 AI 产出治理（开放题：开源 AI 内容淹没）

### 本质
> **AI 把"生产"的边际成本降到接近 0，但没降低"验证"的边际成本 → 瓶颈全部压到验证环节。**

（注：说"成本"不说"效率"——因为说"效率没跟上"会被追问"那写个 AI 审核工具不就行了"；说"成本没降低"直指：验证成本是结构性的。）

**三个崩塌**：

| 表象 | 本质 |
|---|---|
| AI 淹没 Issue | 信噪比崩塌 |
| AI 提交混进 git | 可追溯性崩塌 |
| 人工审不过来 | 质控带宽是瓶颈 |

**与本讲其他章节同构**：
```
第1讲：模型生成代码 → 【清洗→校验→重试】
2.5  ：Agent写文件 → 【权限/沙箱/审计】
开源 ：AI提交PR   → 【准入/标注/分级审核】
572  ：AI生成部署包 → 【部署前校验+版本管理+人工签字】
同一个结构：生产者 → 【验证闸门】→ 消费者
```

### 业界做法（2024-2026）

| 项目 | 做法 |
|---|---|
| Linux kernel | AI 提交必须标注（`Assisted-by:`）+ 签 **DCO**，承担同等责任 |
| curl | 一度**全面禁止** AI 生成的 Issue/PR |
| Fedora | 要求 AI 贡献声明 |
| Gentoo | AI 提交需标注，接受**更严格**审查 |

> 共识：**Human Accountability —— AI 可以参与，但责任必须落在人头上。**
> 关键：**不选择"禁止 AI"**（禁不掉），而是**承认参与 + 要求披露 + 责任可追溯**。跟 2.5"不靠禁止靠治理"同哲学。

### 治理框架（四层，层层递进）

```
① 标注层  AI 参与必须显式标注（Assisted-by: / Reviewed-by: / Signed-off-by:）
          → 把"AI 提交"变成可检索、可统计、可分级的对象；没这层后三层无从下手

② 准入层  提交前 CI 自动校验（lint/test/格式）→ 不合格直接拒绝，进不了人的视线
          → 把第一道验证交给机器，不交给人的眼睛（= 572 的 validate_xls）

③ 分级层  按"风险 × 可逆性"分档（文档轻审 / 核心重审）
          → 不分级 = 重要的没审透 + 不重要的浪费带宽

④ 追溯层  小步提交 + 单一目的 + 原子性 + 有意义 message
          → 直接回答"难以定位是哪次提交"
```

**④ 的四条纪律**：

| 纪律 | 目的 |
|---|---|
| 小步（改动量小） | bisect 定位到 commit 后，范围够小 |
| 单一目的 | 能判断"这次提交和 bug 有没有关系" |
| 原子性（能独立编译测试） | 二分时每步都是"可用的点" |
| 有意义的 message | 事后理解意图（AI 写的常是"update file"废话） |

> **金句**："AI 生成的内容越多，越需要'提交粒度'纪律"（AI 天然倾向一次干很多 → bisect 失效）。
> **"AI 时代 git 纪律不是变宽松了，是变得更重要了。"**

### AI 为什么放大这个问题

| AI 特性 | 影响 |
|---|---|
| 生产成本≈0 | 供给爆炸 → 信噪比雪崩 |
| 倾向一次做很多 | 提交粒度变大 → bisect 失效 |
| 产出"看起来对" | 审核者需逐行验证，不能"读着顺"放行 |
| 责任主体模糊 | "谁写的"→"谁提交的"，责任链重设 |

> 🔑 **AI 让"产出"变便宜，但让"验证"变贵（因为它看起来对）→ 治理重心从"管生产"转向"管验证"。**

### 金句弹药包

1. **本质**：AI 把生产成本降到 0，没降低验证成本——瓶颈全压在验证环节
2. **方向**：治理不是限制 AI 生产，是建立验证带宽
3. **追溯**：AI 生成越多越需要"提交粒度"纪律（bisect 会失效）
4. **责任**：AI 可以参与，但责任必须落在人头上
5. **静默失败**：代码错了编译报错，XLS 错了系统不报错
6. **AI 审 AI**：能压缩第一道验证成本，但消不掉——AI 的"看起来对"恰恰最难验证

## 7. ❓ 自测灵魂拷问 (Self-Quiz)

（复习时遮住答案，口头回答）

**Q1: 模型是怎么"调用"函数的？它执行了吗？**
A: (关键点：模型只输出"调用意图"JSON；执行永远是宿主代码；模型=决策器，代码=执行器)

**Q2: 为什么循环控制权必须在宿主代码，不能交给模型？**
A: (关键点：模型输出有概率非法→校验要在代码层；模型"该不该停"也是概率性的→终止要在代码层；成本/状态/安全只有代码看得见)

**Q3: Agent Loop 的三道防护墙？各自防什么？**
A: (关键点：最大轮数=软墙防转圈；超时/预算=硬墙防烧钱；无进展检测=智能墙防换皮重试)

**Q4: description 必须回答哪三个问题？哪个最关键？为什么？**
A: (关键点：是什么/何时用/何时别用；第三个最关键——模型默认倾向"多调"，这句是刹车)

**Q5: 为什么"入口宽、内部严"？为什么不直接把 schema 写死？**
A: (关键点：schema 越严一次通过率越低→模型重试/摆烂/编造参数；严格性从模型转移到代码)

**Q6: enum 约束和事后校验的本质区别？**
A: (关键点：enum 在"生成时"堵死；事后校验是"事后补救"。选择题比填空题容易)

**Q7: 错误回灌为什么要"细颗粒度"？**
A: (关键点：降低模型搜索空间；带示例=把开放式生成降级成填空题/抄写题)

**Q8: 判断两个工具调用并行还是串行的判据？**
A: (关键点：两条——① 无数据依赖 ② 无副作用冲突；写操作不并行发起)

**Q9: 安全边界按什么分级？为什么不用"危险度"？**
A: (关键点：按可逆性；危险度是主观会变的判断，可逆性是客观可写成代码的规则)

**Q10: 沙箱 + 版本控制为什么能让你大胆放开读写？**
A: (关键点：沙箱控爆炸半径、版本控制可回滚→最坏只是"污染沙箱+一次revert"→审批变得不必要)

**Q11: prompt 注入是什么？三道防线？**
A: (关键点：外部内容夹带指令被模型当命令；权限矩阵兜底+输入输出隔离+最小权限。安全是防被骗不是防犯错)

**Q12: MCP 和 Function Calling 什么关系？**
A: (关键点：上下层不是竞品；FC=模型↔应用，MCP=应用↔工具；FC 管怎么说话，MCP 管怎么插电)

**Q13: Function Calling 缺什么，MCP 补上？**
A: (关键点：工具的"发现"（tools/list）和"调用"（tools/call）；M×N 变 M+N)

**Q14: Tools 和 Resources 区别？知识库该做哪个？**
A: (关键点：Tools=模型决定调，Resources=应用决定注入；知识库做 Resources，因为该不该注入不该由模型定)

**Q15: MCP 管权限吗？**
A: (关键点：不管！有 capability negotiation 没有 access control；安全靠 Host+Server 各自兜；信任问题是 MCP 最大争议)

**Q16: 开源 AI 内容淹没问题，治理框架四层？**
A: (关键点：标注/准入/分级/追溯；本质是验证带宽瓶颈；Human Accountability；追溯靠"提交粒度"纪律)

**Q17: 为什么说"AI 时代 git 纪律更重要"？**
A: (关键点：AI 倾向一次干很多→提交粒度大→bisect 定位到 commit 后范围还是太大→需要小步/单一目的/原子性/有意义message)
