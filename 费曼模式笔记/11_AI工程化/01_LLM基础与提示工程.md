## 1. 🎯 一句话本质

**LLM 是一个概率接龙机器 —— 它只会做一件事：看着已有文本，猜下一个 token 是什么。**
其他所有概念（temperature、CoT、结构化输出、幻觉、上下文成本）都是从这一句推出来的。

> 三个推论（一切概念的地基）：
> 1. **每个 token 都要跑一遍完整网络** → CoT 有效的根本原因
> 2. **输出是采样出来的，不是查出来的** → 需要 temperature、会产生幻觉
> 3. **模型是无状态的** → Agent 成本 O(n²)、必须重发历史

## 2. 💥 灾难现场 (The Disaster Scenario)

### 场景 A：max_tokens 设太小，Agent 静默崩溃

**错误做法**：给工具调用场景设置 max_tokens = 100

```
模型正在输出：
{"tool": "writeFile", "path": "D:\\a.java", "conte     ← 到 100 token 被硬截断
```

**底层发生了什么**：
- 自回归生成被强行截停，停的位置**不在任何语义边界**
- JSON 残缺成 `{"tool": "writeFile", "path": "D:\\a.java", "conte` → `JSON.parse()` 直接抛异常
- 工具调用参数不完整 → 执行报错 → **整个 Agent 循环中断**
- **最阴的**：部分 API 不抛错，只在响应里给 `finish_reason: "length"`，不看就不知道被截了

**修复关键**：工具调用场景 max_tokens 必须给足（≥2000，写文件类更大），并**强制检查 finish_reason**。

> ⚠️ 常见概念混淆：max_tokens（管**输出**长度）≠ 上下文窗口（管**输入+输出**总容量）≠ compaction（窗口满了**裁剪历史**）。三件事。

### 场景 B：以为 temperature=0 就完全可复现

**错误认知**："设成 0 了，结果应该每次都一样"

**底层发生了什么**：
- temperature=0 执行的是 **argmax（取概率最大的 token）**，逻辑上确实确定
- **但"概率值"本身在并行计算中不稳定**：
  - GPU 并行归约：矩阵乘法加法顺序随线程调度变化，**浮点加法不满足结合律** `(a+b)+c ≠ a+(b+c)` → logits 末位抖动
  - MoE 路由抖动：边界情况下 token 走哪个专家可能翻转
  - 批处理组成：你的请求和别人打包在一起，batch size 变化影响数值
  - 算子差异：不同硬件/kernel 版本结果不同
- **当 top-1 和 top-2 概率极近时，这点抖动会导致翻转**

**修复关键**：要绝对可复现需 **固定 seed + 确定性算子 + 关闭非确定优化**（多数云 API 不提供）。工程上接受"近似确定"。

### 场景 C：以为"多生成几个查询"就等于语义检索

**错误做法**：用 LLM 把一个查询改写成 10 个同义词，全部走 BM25，合并结果——"这样不就等于语义检索了？"

**底层发生了什么**：
```
用户问："版本号报错"
文档写："Revision 赋值 bug"

LLM 造同义词：版本 / 版次 / revision ...
  → 只能覆盖"同义"
  → 覆盖不了"相关/共现"（"赋值"这个业务动作根本不在查询里，LLM 也想不到）
  → 本质仍是【字面匹配】，只是字面匹配的机会变多了
```

**关键洞察**：向量空间里的"邻近"**不是同义词关系**，是"使用场景/共现关系"的统计。
> "Revision" 和 "版本号" 的桥梁，是靠 embedding 训练时铺的 —— **一旦落到"关键词"这个平面，桥就断了。**

**修复关键**：Query Expansion（同义改写）和向量检索是**互补不是替代**。正确架构 = LLM 改写 + 向量/BM25 **并行**检索 + RRF 融合。

## 3. 🧠 费曼复述 (The Feynman Test)

### 👶 给实习生的比喻

**LLM 是什么**：就像一个**只能玩"成语接龙"的机器**。你给它一段话，它不"理解"，它只是根据见过的海量文本，算出"下一个字最可能是什么"。

- **temperature** = 它的"胆子大小"。调到 0，它永远选最稳的字（但偶尔还是会因为"手感"抖一下）；调到 2，它就敢用生僻字，也更容易语无伦次。
- **CoT** = 让它**打草稿**。"17×23 等于几？"直接问容易错；让它"先在纸上写 17×20=340，17×3=51，加起来 391"，就对。**草稿纸就是多出来的计算步数。**
- **ReAct** = 让它**一边想一边查**。CoT 只是在脑子里想，ReAct 是"想→查资料→看到结果→接着想→再查"，直到它自己说"我不用查了，答案是……"。
- **结构化输出** = 要求它**必须按表格填**。它天生爱写散文，你得规定"只填这张表，别加废话"。

### ⚖️ 核心对比

| 技巧 | 一句话本质 | 解决什么 | 常见混淆 |
|---|---|---|---|
| **CoT** | 多生成中间步骤 = 多给计算量 | 复杂推理算力不够 | ❌ 不是多次采样投票 |
| **ReAct** | 交替思考+调工具，结果回填 | 需外部信息/可纠错 | ❌ 不是"想得更多" |
| **Self-Consistency** | 采样 N 次取多数 | 单次推理走错路 | ❌ 不是 CoT |
| **Role Prompting** | 给个人设 | 输出风格 | ❌ 不提升事实准确率 |

| 参数 | 管什么 | 一句话 |
|---|---|---|
| **temperature** | 概率分布的锐化/平滑 | 调"大胆程度" |
| **top_p** | 候选集截断 | 调"候选名单大小" |
| **max_tokens** | 输出长度上限 | 调"允许说多长" |

**采样流程（把三个参数串起来）**：
```
模型算出 logits（每个词的原始分数）
      ↓
① temperature 缩放：logits ÷ T
      ↓
② softmax → 概率分布
      ↓
③ top_p / top_k 截断候选集
      ↓
④ 从剩下的里采样（或 argmax）
      ↓
得到 1 个 token
```

**为什么 CoT 有效（数学版）**：
```
设模型有 L 层：
无 CoT：输入 → 直接输出答案 → 计算量 = 1 次前向 × L 层
有 CoT：输入 → 步骤1 → ... → 步骤m → 答案 → 计算量 = (m+1) 次前向 × L 层

复杂问题需要 > L 步的串行计算
直接输出 = 只有 L 层算力 → 不够 → 错
CoT = m 个中间 token → 等效计算深度 m×L → 够了
```
**反向验证（能反推原理才算懂）**：所以 CoT **对多步计算有效，对查表类无效** —— 实测数学题提升巨大、事实问答几乎无变化。

### ReAct = while 循环（★ 记忆锚点）

```
while (true) {
    resp = LLM(messages)              // ① 模型思考 + 决定行动
    if (resp 是最终答案) break;        // ② 终止条件
    result = exec(resp.tool)          // ③ 执行工具
    messages += (resp, result)        // ④ 结果回填上下文
}
```
- **谁控制循环**：不是代码写死的，**循环走向由模型每步输出决定**
- **终止条件**：**模型主动输出最终答案**（不是代码判断"任务完成"）
- **三要素**：Thought（思考）/ Action（行动）/ Observation（观察）

## 4. ⚡ 性能与边界 (Performance & Boundaries)

### ✅ 适用场景 (Safe Zones)

| 参数组合 | 场景 |
|---|---|
| T=0, top_p=1, max_tokens 给足 | 代码生成 / JSON / **Agent 工具调用** |
| T=0~0.2 | 分类 / 抽取 |
| T=0.3~0.7 | 问答 / 总结 |
| T=0.9~1.2 | 创意写作 / 头脑风暴 |

**为什么 Agent 几乎总是 T≈0**：
> **Agent 的输出是代码的输入，不是给人读的文本。** 代码要求确定性：
> ① 工具调用要可靠（JSON 参数抖一下就解析失败）② 决策要可复现（否则没法调试/回归）③ 输出要被程序处理。

### 🚫 绝对禁区 (Danger Zones)

- **max_tokens 设太小用于工具调用** → 输出截断 → JSON 残缺 → Agent 崩（见灾难现场 A）
- **temperature 和 top_p 同时调** → 机制不同（缩放 vs 截断），互相干扰。**只调一个**
- **对推理模型（o1/R1）手动加 "think step by step"** → 它已内化 CoT，**收益很小甚至有害**
- **靠 system prompt 保证安全** → 约束力强 ≠ 硬保证，用户可用 prompt injection 覆盖
- **指望 Role Prompting 提升事实准确率** → 安慰剂，反而因"角色光环"让模型更自信地编

### 📉 性能杀手

**Agent 的 token 成本是 O(n²)**：
```
LLM 无状态 → 第 k 轮必须把前 k-1 轮全部重发
总 token = 1 + 2 + ... + n = n(n+1)/2 ≈ O(n²)
```
→ 省钱顺序：**prompt 缓存**（命中部分便宜约 10 倍，★★★★★）> **模型分级** > **上下文裁剪**（有损）

**Lost in the Middle**：
```
[关键信息] ... [一堆无关内容] ... [关键信息]
    ↑                                ↑
  记得住                           记得住
              ↑ 中间容易丢
```
→ RAG 注入要**排序**，最相关的放**两端**。
→ **"上下文窗口大" ≠ "长上下文能力强"**（面试加分句）

## 5. 🔒 结构化输出（Agent 命脉）

### 为什么是命脉
```
模型输出 → 你解析 → 执行
             ↑ 解析失败 = Agent 崩 = 循环断
```

### 四层保障（从软到硬）

| 层 | 手段 | 机制 | 可靠性 |
|---|---|---|---|
| ① | 提示约束（"只输出 JSON"） | 只是"建议" | 低（模型会忘） |
| ② | **JSON Mode** | 解码层强制语法合法 | 中（能 parse，**字段可能全错**） |
| ③ | **Structured Outputs** | 按 **schema** 约束解码 | 高（字段名/类型对） |
| ④ | **约束解码**（GBNF/grammar） | 采样时非法 token 概率置 0 | 最高（理论不会错） |

> ⚠️ **高频考点：JSON Mode ≠ Structured Outputs**
> - JSON Mode：保证"是合法 JSON" → 可能是 `{"foo":"bar"}` 完全不对
> - Structured Outputs：保证"符合我给的 schema" → 字段名/类型/必填都对

### 工程三件套（★ 真实做过）

```
清洗 → 校验 → 重试

清洗：剥掉 markdown 围栏、前后缀、多余解释
校验：解析 + schema 校验 + 业务规则校验
重试：把错误信息回灌给模型，让它自己修
```

**重试三要点**：① 限制次数（2~3 次，否则烧钱死循环）② 带上错误信息（否则模型只会重复错）③ 仍失败 → 降级或转人工

> 📌 **572 真实案例（面试王牌）**：`AsyncApiLogRequestParser`
> - 优先按标准 JSON 解析 → 失败回退旧格式（Map.toString 的 `{requestId=xxx}`）
> - 修正了一个 bug：JSON 格式下 `getRequestId` 返回 null，因为 key 是 `"requestId"`（**带右引号**），原正则 `requestId:` 匹配不上 → 改为 `requestId"?\s*[=:]\s*"?([^",}\s]+)`
> **这就是"清洗+校验"的真实落地。**

## 6. 🔍 幻觉与抑制

### 本质
> **模型是概率接龙，不是查数据库。它的目标函数是"生成像样的文本"，不是"说真话"。**
> 幻觉不是 bug，是**机制的自然产物**。分三类：事实性 / 忠实性 / 格式性。

### 五层抑制（按有效性）
```
① RAG（喂真实资料）★★★★★   ← 最有效
② 引用溯源 ★★★★
③ 交叉校验 ★★★★
④ 降低 temperature ★★★
⑤ 明确"不知道" ★★★
```

### ⚠️ 最关键的洞察
> **RAG 有效的前提是检索质量好。** 检索错了 → 模型"忠实地照着错资料胡说"，还带"引用"，**更难发现**（garbage in, garbage out）。
> → **RAG 系统的质量问题，80% 在检索，20% 在生成。**

### 面试答法
> "分三层：**检索层**——先喂真实资料（RAG，最有效）；**生成层**——要求引用来源、温度压 0、明确'不知道'；**验证层**——关键输出做校验（编译/单测/规则）。但诚实说：不可能 100% 消除幻觉，工程做的是'把错误挡在影响面最小的地方'。"

## 7. ❓ 自测灵魂拷问 (Self-Quiz)

（复习时遮住答案，口头回答）

**Q1: temperature=0 是否等于完全可复现？为什么？**
A: (关键点：argmax 逻辑确定，但浮点加法不满足结合律 + GPU 并行归约顺序不定 → logits 抖动；top-1/top-2 接近时翻转)

**Q2: Agent 场景为什么几乎总是 temperature≈0？**
A: (关键点：输出是代码的输入不是给人读的；工具调用要可靠、决策要可复现、输出要被程序解析)

**Q3: max_tokens 太小，在 Agent 场景会造成什么故障？**
A: (关键点：输出硬截断 → JSON 残缺 → 解析炸 → 工具调用参数不完整 → 循环中断；注意 finish_reason=length)

**Q4: CoT 为什么有效？从 Transformer 计算步数角度讲。**
A: (关键点：Transformer 计算步数固定=层数；CoT 把计算摊到更多 token=更多计算深度；隐式计算外化成显式 token)

**Q5: CoT 和 Self-Consistency 的区别？**
A: (关键点：CoT 单次多步换计算量；SC 多次采样投票降方差)

**Q6: ReAct 三要素？它和 while 循环什么关系？终止条件？**
A: (关键点：Thought/Action/Observation；本质是 while 循环；循环走向由模型每步输出决定；终止=模型自己说不调工具了；必须加最大轮数/无进展检测保护)

**Q7: 保证模型输出合法 JSON 的四层手段？**
A: (关键点：提示约束 → JSON Mode → Structured Outputs → 约束解码；JSON Mode ≠ Structured Outputs)

**Q8: 结构化输出工程三件套？重试要注意什么？**
A: (关键点：清洗→校验→重试；重试限次数、带错误信息、失败降级；571 的 Parser 案例)

**Q9: 幻觉抑制最有效的手段？为什么说"RAG 的 80% 问题在检索"？**
A: (关键点：RAG；检索错了模型会忠实照着错资料胡说还带引用，更难发现)

**Q10: Lost in the Middle 现象？对 RAG 有什么指导？**
A: (关键点：关键信息放中间容易丢；RAG 注入要排序，最相关放两端)

**Q11: Agent 的 token 成本为什么是 O(n²)？三个省钱手段？**
A: (关键点：LLM 无状态→每轮重发全部历史→1+2+...+n=n(n+1)/2；prompt 缓存/模型分级/上下文裁剪)
