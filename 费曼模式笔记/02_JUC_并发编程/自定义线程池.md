## 自定义线程池

* 导入场景：小王的单线程噩梦，假设有这样一个网站，日常的工作就电商下单。这个动作包含若干操作，扣减库存（数据库操作，耗时 50ms）生成订单（数据库操作，耗时 50ms）发送短信通知（第三方接口调用，耗时 100ms）。按照敏捷开发的原则，快速实现了出版的系统，
   即单线程串行处理代码逻辑：主线程接收请求 -> 扣库存 -> 生成订单 -> 发短信 -> 返回“成功”。
   问题，假设服务器只有 1 个核心线程。如果有 1000 个人同时下单，最后一个人可能要等几十秒甚至几分钟。用户体验崩塌。 （这样不好）
* 优化，多线程执行，但不用线程池：   
    改进思路：为了快！每来一个请求，我就 new Thread(() -> { 业务逻辑 }).start()。大家各跑各的，互不干扰。
    遇到的问题：创建与销毁的开销：在 Java 中，创建一个线程是非常“重”的操作。它需要向操作系统申请资源、分配内存（栈空间）、初始化上下文。如果请求极其频繁（如每秒 1000 个），CPU 可能花 50% 的时间在“生线程”和“死线程”上，真正干业务的时间反而少了。 
    资源耗尽（OOM）：这是最致命的。假设内存只有 8GB，每个线程栈分配 1MB。如果瞬间来了 10,000 个请求，就需要 10GB 内存。操作系统会直接杀掉进程，或者抛出 `OutOfMemoryError: unable to create new native thread`。

* 最终方案 线程池（终极方案）:
    改进思路：既然“创建线程”太贵，“无限线程”太危险，那我们“提前创建好一批线程，放在池子里备用”。
    复用：任务做完了，线程不销毁，回池子里歇会儿，等下一个任务。省去了频繁创建/销毁的开销。
    限流：池子大小是固定的（比如最大 50 个）。就算来了 10,000 个请求，也只有 50 个在跑，剩下的排队。虽然排队会慢一点，但保证了服务器绝对不会因为内存溢出而崩溃。

    结果：又快又稳。既利用了多核 CPU 的优势，又控制了资源消耗。

## 手动管理线程的二三事
* 减少资源消耗，手动管理：频繁 `new Thread()` 会导致系统频繁进行系统调用，消耗大量 CPU 和内存。线程池：通过复用已有的线程，减少了线程创建和销毁的开销。
* 提高响应速度（提速） 手动管理：新请求来了，如果要先创建线程，会有延迟。 线程池：线程早已创建好（核心线程），任务来了直接执行，几乎没有等待时间。
* 提高线程的可管理性（保命） 手动管理：无法控制并发量。一旦流量洪峰到来，无限创建线程会导致内存溢出，拖垮整个服务器。  线程池：提供了统一的分配、调优和监控能力。我们可以限制最大并发数，把多余的任务排队，保证系统在负载过高时依然能“苟延残喘”而不是直接“暴毙”。

* 一句话说明白，线程池的诞生解决的核心问题和矛盾 :解决“**高并发场景下，线程频繁创建销毁消耗资源**”以及“**无限制并发导致系统资源耗尽**”这两个核心矛盾。

## 线程池的认识

* 线程池认识模型，对线程池的理论模型的认识。**线程池就是一个“银行大厅”** ，它服务任务，有多个常驻柜台（核心线程数 `corePoolSize`），只要现在正在跑的任务数量小于核心线程数目，当新任务来的时候，立马就能安排服务，当所有常驻柜台都满了的时候，新来的任务就必须要排队  **工作队列 (`workQueue`)**  等候区的椅子。柜员忙不过来时，客户先坐椅子上排队。但是假如任务已经多到排队的队列都满了（假设设置了工作队列长度），这种时候就会新增临时窗口了 **最大线程数 (`maximumPoolSize`)：柜员 + 临时窗口。** 这个时候就会有多个新开的窗口来加快任务的处理速度了。接下来考虑最极端的情况了，工作队列满了，所有的能开的窗口都开了，但是还是有任务源源不断的进来，这个时候就不得不拒绝某些任务的  **拒绝策略 (`handler`)**  

* 线程池任务工作模型。严格定义线程的行为如下:
     * 当一个任务提交到线程池时：  先看核心线程：当前线程数 < corePoolSize 吗？ 是 → 创建新核心线程执行任务。  否 → 进入第2步。
     * 再看队列：队列满了吗？  没满 → 放入队列，等待空闲线程来取（这是关键，先排队，而不是马上加线程）。  满了 → 进入第3步。
     * 看最大线程：当前线程数 < maximumPoolSize 吗？ 是 → 创建非核心线程（临时工）执行任务。   否 → 进入第4步。
     * 触发拒绝策略：队列满了，人也满了，执行 `RejectedExecutionHandler`。

## 线程池的参数配置与调优

* 场景识别，线程池的参数配置  
      1. 核心线程数 (corePoolSize) 与 最大线程数 (maximumPoolSize):这里需要识别的是输入的任务是IO密集型（查数据库、调RPC、读写文件（大部分时间在等））的还是   CPU密集型的（逻辑复杂、死循环、加密计算（不怎么查库/调接口））。CPU密集型的话，要确保CPU尽可能的使用，同时要避免因为上下文切换导致变慢，因此`N + 1` (N为CPU核数).IO密集型的 线程在等IO时CPU是空闲的，所以要开多一点线程，让CPU别闲着。 公式是 `2N` 或 `N * (1 + 等待/计算)` (后面那个式子需要通过分析事务的计算IO耗时比例才能得到具体的值)    
      2. 工作队列 (`workQueue`)：OOM的重灾区: 这里有一个绝对原则：生产环境严禁使用无界队列！   
      LinkedBlockingQueue (无界/默认) **绝对不要在生产环境用这个** 注意  `Executors.newFixedThreadPool` 这个方法返回的就是无限容量的  
      ArrayBlockingQueue (有界) 初始化时必须指定大小（如 1000）。 内存可控，满了就会触发拒绝策略，保护系统。 生产环境首选。  
      SynchronousQueue (不存元素)： 特点：容量为0。提交任务必须立刻有线程接手，否则直接进“最大线程”判断或拒绝 适用：Executors.newCachedThreadPool 用的这个。适合突发流量，但要注意 maximumPoolSize 不能设太大，否则线程爆炸。  
      3. 拒绝策略 (`RejectedExecutionHandler`)：最后的防线    

| 策略 | 行为 | 适用场景 |  
| :--- | :--- | :--- |  
| `AbortPolicy` (默认) | 直接抛 `RejectedExecutionException` 异常。 | 允许报错，前端提示“系统繁忙”，快速失败。 |  
| `CallerRunsPolicy` | 谁提交，谁执行（比如主线程自己跑）。 | 非常重要！ 这是一个“背压”机制。提交慢了，调用方（如Tomcat线程）会被占用，导致HTTP响应变慢，从而让上游  （浏览器/网关）自动减速。适合不允许丢数据的场景。 |  
| `DiscardPolicy` | 默默丢弃，不抛异常。 | 比如日志记录、非核心监控数据，丢了就丢了。 |  
| `DiscardOldestPolicy` | 丢弃队列里最老的任务，尝试提交当前任务。 | 消息有实效性，旧的消息不重要（如实时股价推送）。 |  


## 实战设计与避坑
* 为什么不用`Executors`？  你在若依或工作中可能见过 `Executors.newFixedThreadPool(10)` 原因：它默认用了 LinkedBlockingQueue（无界队列）后果：一旦请求积压（比如数据库挂了，处理极慢），队列会无限塞入任务，直到堆内存爆掉  正确姿势：永远使用 ThreadPoolExecutor 构造函数手动创建，显式指定队列大小  
* 生产环境配置模板（参考）  假设你是一个IO密集型服务（查库、调接口）：

```java
// 这是一个标准的中级开发配置模板
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    10,  // corePoolSize: CPU核数 * 2 (假设是IO密集)
    20,  // maximumPoolSize: 弹性扩容上限
    60L, // keepAliveTime: 非核心线程空闲60秒回收
    TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000), // 有界队列！容量根据内存估算
    new ThreadFactory() { ... },    // 自定义线程名，方便排查日志（如：order-pool-1）
    new ThreadPoolExecutor.CallerRunsPolicy() // 拒绝策略：让调用方跑，防止丢单
);

```

* 线程池监控 其实线程池也有状态: 
    `getActiveCount()`：当前干活的线程数。如果长期等于 `maximumPoolSize`，说明线程池满了，系统在硬抗。
    `getQueue().size()`：队列堆积数。如果长期很大，说明消费不过来，需要扩容或优化SQL。
