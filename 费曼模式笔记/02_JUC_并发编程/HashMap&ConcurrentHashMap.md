## HashMap
* 一句话HashMap特点:
    JDK 1.8 内存结构引入红黑树[背景](#HashMap1)，当**满足条件**时候 ，链表会转树，多线程情景下 HashMap扩容会发生未定义的行为，造成内容丢失或者死循环的情况（不同版本异常类型不一样）


* <a id = HashMap1></a>**背景** ：在JDK 1.8之前HashMap只有数组＋链表当哈希冲突严重的时候，链表过长回导致查询退化到O(n)级别。JDK引入红黑树，将最坏的情况优化位 O(log n)  
    以下是一些关键的参数:
    * `TREEIFY_THRESHOLD` 默认值是8 ，表示为当链表长度达到8的时候，才会 **可能** 触发转树操作
    * `UNTREEIFY_THRESHOLD` 默认值是6 ，表示当树的节点数目小于6时候，回将红黑树转回链表 （注释:退树操作和转树操作的临界点不一样，是为了避免频繁的转树退树操作导致的新能损耗）
    * `MIN_TREEIFY_CAPACITY` 最小转树容积 
      - 一个桶是否转树需要从两个条件去判断 ，1、当前的链表的长度 2、数组的长度 ，只有当链表长度大于8且数组容量大于等于 64时，才会真正执行 `treeifyBin()` 转树
      - 如果数组容量小于 64 即使链表长度大于8也不会触发转树操作，HashMap 也会优先选择 扩容 (resize)
    * `负载因子` 默认值是0.75 ，这个因子决定了HashMap什么时候会扩容[负载因子来源](#fuzaiyinzi)
      - 当HashMap中存储的元素的个数(Size)超过了 **容积** × **负载因子** 的时候就会触发扩容机制
      - 扩容操作是这样的
        * 第一阶段 ，计算新容量与创建新数组: 容量翻倍新容量等于旧容量的两倍且容量始终为**2的幂次方** 如果翻倍后超过最大限制 2^30 则不再扩容阈值设置为 Interger.MAX_VALUE。然后计算新阈值，最后，分配内存，创建一个新的Node<K,V>[] newTable数组
        * 第二阶段 :数据迁移，这是最耗时的环节，它会遍历每个桶，桶的情况分为三种，只有一个节点、链表、树。  
            单个节点场景:如果只有一个节点的话新下标只有两种可能， old下标或者old下标+old容积 （这点可以从哈希码高位快速判断，而不用再次计算）  
            链表节点场景(**JDK 1.8优化**) 在JDK 1.7里面链表迁移需要重新计算Hash值并且头插法插入(导致顺序反转和死循环风险)  ，**JDK 1.8**这个版本多线程扩容会导致数据丢失的情况。
            红黑树场景: 需要做的有  **检查退化**：如果树太小，直接退化成链表，按链表逻辑转移。 **树拆分（Split）** 如果不能退化，必须将一颗大树拆分成两颗小树，需要遍历整颗树分为两组 lo，hi，然后分别重新树化，最后将两颗树放入到新数组的 j和j+oldCap位置上  [分树操作源码](#TreeNode.split) | [分树操作思路详解](#TreeNode.split.description)
        * 第三阶段:切换引用将所  有数据迁移完毕后，执行 `table = newTab` 
    * 数学原理（泊松分布）：<a id = fuzaiyinzi></a>
        官方注释中明确提到，在负载因子 0.75 的情况下，链表长度符合泊松分布。
        长度为 8 的概率极低（约 0.00000006）。
        选择 8 是为了在极少发生（节省空间）和极端性能保障之间取得平衡。 
### HashMap源码部分
* JDK 1.8 HashMap 内部类 TreeNode 中的 split 方法核心逻辑 <a id = TreeNode.split></a>
  ```java
    /**
     * 内部类 TreeNode 的方法
    * 作用：在 HashMap 扩容时，将当前的红黑树拆分为低位(lo)和高位(hi)两部分
    * 
    * @param map 当前的 HashMap 实例
    * @param tab 新的数组表 (newTab)
    * @param index 当前桶在旧数组中的索引 (也是新数组中 lo 组的目标索引)
    * @param bit 用于判断高低的掩码 (通常是 oldCap，即 2 的幂)
    */
    final void split(HashMap<K,V> map, Node<K,V>[] tab, int index, int bit) {
        TreeNode<K,V> b = this; // 'this' 是当前红黑树的根节点
        
        // ---------------------------------------------------------
        // 【准备阶段】定义两个临时链表的头尾指针
        // 注意：这里虽然定义为 TreeNode，但在分组完成前，它们仅作为临时链表使用
        // ---------------------------------------------------------
        TreeNode<K,V> loHead = null, loTail = null; // 低位组 (low) 的头和尾
        TreeNode<K,V> hiHead = null, hiTail = null; // 高位组 (high) 的头和尾
        
        int lc = 0; // 低位组计数器 (Low Count)
        int hc = 0; // 高位组计数器 (High Count)

        // ---------------------------------------------------------
        // 【阶段一：无脑分组 & 同步计数】
        // 策略：不判断是否退化，不修改树结构(left/right/parent)，
        // 仅利用 TreeNode 维护的 'next' 指针，将所有节点线性遍历并挂到两个临时队列中。
        // ---------------------------------------------------------
        do {
            TreeNode<K,V> next = (TreeNode<K,V>)b.next; // 保存下一个节点，因为我们要修改 b.next
            b.next = null; // 断开当前节点与后续节点的连接，防止环或脏数据
            
            // 核心判断：根据 hash 值与 bit (oldCap) 进行按位与运算
            // 结果为 0 -> 归入低位组 (lo)
            // 结果不为 0 -> 归入高位组 (hi)
            if ((b.hash & bit) == 0) {
                // --- 处理低位组 (lo) ---
                if (loTail == null) {
                    loHead = b; // 如果队列为空，当前节点即为头
                } else {
                    loTail.next = b; // 否则，挂到尾巴后面
                }
                loTail = b; // 更新尾巴为当前节点
                lc++; // 【关键】计数器 +1
            } else {
                // --- 处理高位组 (hi) ---
                if (hiTail == null) {
                    hiHead = b;
                } else {
                    hiTail.next = b;
                }
                hiTail = b;
                hc++; // 【关键】计数器 +1
            }
            b = next; // 移动到下一个节点
        } while (b != null); // 直到遍历完所有节点

        // ---------------------------------------------------------
        // 【阶段二：独立决策 & 最终形态转换】
        // 此时遍历结束，lc 和 hc 已确定。
        // 对 lo 组和 hi 组分别进行独立判断，互不干扰。
        // ---------------------------------------------------------

        // === 处理低位组 (lo) ===
        if (loTail != null) {
            loTail.next = null; // 闭合低位链表，防止指向脏数据
            
            // 【决策点】判断是否退化
            // 阈值 UNTREEIFY_THRESHOLD = 6
            if (lc <= UNTREEIFY_THRESHOLD) {
                // 情况 A: 节点数 <= 6，需要退化
                // 动作：创建全新的普通 Node[] 链表，丢弃 TreeNode 结构
                // 这是一个重量级操作：涉及新对象分配和数据拷贝
                tab[index] = loHead.untreeify(map);
            } else {
                // 情况 B: 节点数 > 6，保持树结构
                // 动作：将刚才分好的临时链表，重新构建成红黑树
                // 注意：如果 hiHead 不为空，说明发生了拆分，原树结构已破坏，必须重新 treeify
                tab[index] = loHead;
                if (hiHead != null) {
                    tab[index] = loHead.treeify(tab);
                }
            }
        }

        // === 处理高位组 (hi) ===
        if (hiTail != null) {
            hiTail.next = null; // 闭合高位链表
            
            // 【决策点】独立判断 hi 组是否退化
            if (hc <= UNTREEIFY_THRESHOLD) {
                // 情况 A: 节点数 <= 6，退化转链表
                // 即使 lo 组变成了树，hi 组依然可以独立变成链表 (混合形态)
                tab[index + bit] = hiHead.untreeify(map);
            } else {
                // 情况 B: 节点数 > 6，重建树
                tab[index + bit] = hiHead;
                if (loHead != null) {
                    tab[index + bit] = hiHead.treeify(tab);
                }
            }
        }
    }
    ```
    分树操作的逻辑：<a id = TreeNode.split.description></a>
    * 无脑分组：遍历原树，不修改节点的核心树结构（left, right, parent 暂时不动，或者仅利用 next 指针），只是把节点分别挂到两个临时的链表队列（loHead/loTail 和 hiHead/hiTail）中。
    * 事后判断：等所有节点都分完组了，拿着计数器 lc 和 hc 去判断。
    * 最终执行：
        如果 lc <= 6 -> 调用 untreeify() 转成普通链表。
        如果 lc > 6 -> 调用 treeify() 重新构建红黑树。

## ConcurrentHashMap
* 一句话本质:  专门在多线程条件下使用的HashMap，数据结构设计上采用了多种方法保证读、写、**转树** 操作安全和尽可能高效
* 核心故事：银行柜台的故事 (背景与痛点) : 
想象 `ConcurrentHashMap` 是一个超大的`银行大厅`，用来存储客户数据。
  * JDK 1.7 之前 (HashTable)：整个银行只有1个柜台，所有客户（线程）必须排这一条队。一个人办业务，其他人全得等着。效率极低。
  * JDK 1.7 (Segment 分段锁)：
     * 改进：银行把大厅隔成了 16 个小房间 (Segment)，每个房间有一个柜台。
     * 效果：16 个人可以同时办业务，互不干扰。
     * 缺点：
         - 固定死板：房间数量固定（默认16），如果人多，房间里还是得排队   
         - 浪费空间：即使没人，这16个房间的装修（内存开销）也得留着。
         - 跨房间麻烦：如果要统计全行总人数（size），得把16个房间锁住一个个数，很慢。
  * DK 1.8 (Node 桶级锁 + CAS)：彻底拆墙！
      * 改进：拆掉所有隔断房间。大厅里有 64 个（甚至更多）独立的小窗口 (Node 桶)。
      * 规则：谁去哪个窗口，就只锁那个窗口。如果两个人去了同一个窗口，后到的那个人在窗口门口等一会（synchronized），或者试试能不能插队成功（CAS）。
      * 优势：并发能力直接取决于窗口数量，理论上可以非常高。而且没人的窗口不占额外锁资源。  
* 关键机制拆解
  * 机制一：怎么保证大家不抢错数据？(锁的粒度)
      * 旧方案 (1.7)：锁的是“房间” (Segment)。房间里哪怕有100个格子，只要锁了房间，其他人都进不来。
      * 新方案 (1.8)：锁的是“格子” (Node / 桶)。
      * 怎么做到的？  如果是空格子：直接用 CAS (Compare-And-Swap) 尝试放入数据。就像往空信箱投信，只要信箱没被占用，瞬间完成，不用钥匙。
        如果是有数据的格子（发生了哈希冲突，变成了链表或树）：就用 synchronized 锁住这个格子的头节点。  
      * 为什么不用 ReentrantLock 了 因为 synchronized 在 JDK 1.6 后变聪明了（有偏向锁、轻量级锁），对于这种短时间、低竞争的锁，它比重型的 ReentrantLock 更省内存、更快。
  * 机制二：链表太长了怎么办？(红黑树化)
      * 问题：如果大家都运气不好，全挤到了第 5 号窗口，链表会变得巨长，找数据要遍历半天 (O(n))
      * 解决：当链表长度超过 8，且总窗口数超过 64 时，把这个窗口的链表变成红黑树。
      * 比喻：原本大家排成一队（链表），现在改成按身份证号排序站成方阵（树），找人直接从中间切分查找 (O(log n))，快得多。
      * 难点 (盲区自查)：变身过程安全吗？
          * 答案：不安全！变身时不能让人读。所以引入了一个“包装箱”叫 TreeBin
          * 比喻：当链表要变树时，窗口挂出“正在装修”牌子 (`lockState`)。此时来的客人（读线程）必须在门口罚站 (`LockSupport.park`，直接休眠，不浪费CPU)，等装修完了再进。注意：这里不是自旋等待，是真睡！
  * 机制三：人太多了，怎么扩容？(协同扩容)
      * 问题：银行坐满了，需要把大厅扩大一倍（从 64 个窗口变 128 个）。如果把所有人赶出去再搬家，银行就得停业，不可接受。
      * 1.8 的神操作：“边营业，边搬家，大家一起搬”
      * 发起者：第一个发现坐满的线程，开始搬运数据。
      * 后来者：其他线程来存钱时，发现某个窗口正在搬家（有个标记 ForwardingNode），它不会傻等，而是加入搬运队伍，帮着一块搬！
      * 比喻：就像餐厅换桌子，服务员忙不过来，顾客说“没事，我自己把盘子端到新桌子上”，然后自己在新的位置坐下吃饭
      * 结果：扩容速度极快，且不影响别人存钱（读操作直接去新桌子找，写操作帮忙搬完再写）。
  * 机制四：怎么知道现在有多少人？(Size 统计)
      * 问题：如果用一把大锁锁住全场数人头，效率太低。
      * 解决：LongAdder 思想 (分段累加)。
          * 比喻：银行不只有一个总账本。它有 1 个基础账本 (baseCount) 和 一堆小账本 (CounterCell)。
          * 过程 人少时，大家试着改总账本 (CAS)。 人多冲突时，随机找一个小账本记一笔（比如你去记在 A 本，他去记在 B 本）。老板要总数时，把 总账本 + 所有小账本 加一下。
          * 代价：得到的数字是估算值（可能差几个），但在高并发下，速度比精确值重要一万倍


## 问题自测和答案   

* HashMap自测问题<a id = HahsMapQuestion></a>  
    Q1: JDK 1.8 中 HashMap 的底层数据结构是什么？什么时候会发生链表转红黑树？  
    A1:
    结构：数组 + 链表 + 红黑树。
    转树条件：必须同时满足两个条件：
    链表长度 ≥ 8。
    数组容量 ≥ 64。
    注意：如果链表长度达到 8 但数组容量小于 64，会优先触发扩容（resize），而不是转树。这是为了避免在数组较小时，哈希冲突导致的链表过长，扩容通常能显著减少冲突。  

    Q2: 为什么 HashMap 的容量必须是 2 的幂次方？如果不是会怎样？  
    A2:
    原因：为了使用位运算 hash & (n-1) 来替代取模运算 hash % n，从而提高计算索引的效率。只有当 n 是 2 的幂时，n-1 的二进制才全是 1，此时位运算结果才等同于取模。
    后果：如果不是 2 的幂，& 运算会导致某些索引位置永远无法命中（分布不均匀），大大增加哈希碰撞的概率，降低查询效率。  

    Q3: HashMap 的 Hash 算法中为什么要进行“扰动函数”处理（高位异或低位）？   
    A3:
    目的：让高位也参与运算。
    原理：数组长度通常较小（如 16, 32），索引计算只用到 hash 值的低几位。如果 key 的 hashCode() 方法设计不好，导致低位相似但高位不同，就会发生大量碰撞。
    操作：h = key.hashCode() ^ (key.hashCode() >>> 16)。通过将高 16 位右移并与低 16 位异或，混合了高低位特征，使得即使低位相同，只要高位不同，最终 hash 值也会不同，从而减少碰撞。  

    Q4: JDK 1.8 扩容时，元素是如何重新分布的？相比 1.7 有什么优化？  
    A4:
    A4:
    逻辑：不需要重新计算 hash 值。利用 (e.hash & oldCap) 的结果判断：
    结果为 0：元素留在原索引位置。
    结果为 1：元素移动到 原索引 + oldCap 的位置。
    优化：JDK 1.7 需要重新计算 hash % newCap，效率低。1.8 利用 2 倍扩容的特性，只需一次位运算即可确定新位置，且将原本的一条链表拆分成两条（低位链和高位链），避免了头插法导致的死循环问题（1.7 的 Bug）。

* ConcurrentHashMap自测问题 <a id = ConcurrentHashMapQuestion></a>
    Q5: ConcurrentHashMap 在 JDK 1.7 和 1.8 中的锁机制有什么本质区别？为什么 1.8 要改？  
    A5:
    JDK 1.7：Segment 分段锁（ReentrantLock）。将数据分成一段一段存储，每段配一把锁。默认 16 段，并发度最高 16。内存开销大（每个 Segment 都是独立对象+Lock 对象）。  
    JDK 1.8：Node 桶级锁（synchronized + CAS）。锁粒度细化到数组的每个桶（Node）。  

    改版原因：
    - 并发度提升：理论上并发度等于数组长度（默认 16，可动态扩容），远超 1.7。
    - 内存节省：synchronized 锁存在对象头中，无需额外对象；而 ReentrantLock 需要额外的 AQS 对象。
    - JVM 优化：JDK 1.6 后 synchronized 引入了偏向锁、轻量级锁，性能大幅提升，在低竞争下优于 ReentrantLock

    Q6: ConcurrentHashMap 允许 Key 或 Value 为 null 吗？为什么？  
    A6: 不允许  
    -  二义性问题：get(key) 返回 null 时，无法区分是“该 Key 不存在”还是“该 Key 对应的 Value 就是 null”。在并发环境下，如果用 containsKey 再 get 会有线程安全问题，所以直接禁止 null。
    -  复杂性：处理 null 会增加内部逻辑（如 tombstone 标记）的复杂度，影响性能。相比之下，HashMap 单线程可以处理这种二义性。

    Q7: ConcurrentHashMap 的 size() 方法是精确的吗？它是如何实现的？  
    A7: 在高并发写入时，size() 返回的是估算值，不一定绝对精确，但非常接近  

    实现：借鉴了 LongAdder 的思想。
    维护一个 baseCount 和一组 CounterCell 数组。
    更新计数时，优先 CAS 更新 baseCount；失败则随机选取一个 CounterCell 进行累加（减少热点竞争）。
    求和时：sum = baseCount + 所有 CounterCell 的值。
    这避免了单一原子变量（AtomicLong）在高并发下的 CAS 自旋瓶颈。
    
* ConcurrentHashMap TreeBin 与深层并发细节 自测问题
    Q8: 既然 Node 上已经加了 synchronized 锁，为什么还需要 TreeBin 这个包装类？直接用 TreeNode 不行吗？  
    A8: TreeBin 是 ConcurrentHashMap 中红黑树的包装类，通过 synchronized + CAS + LockSupport.park() 保证树化过程中的线程安全，避免读者看到"半棵树"。PS:**TreeBin 通过 volatile + synchronized 间接提供内存屏障效果，但它本身不是"屏障"**  
        其次:TreeBin 在Node[]里面提供了一个统一的给外部代码使用的接口，不用判断当前节点是什么类型，使用`find()`方法交给具体的实现类去处理，省略的判断类型的getInstanceof的开销，这叫**类型隔离与多态伪装**  
        补充:虽然树化过程中 `treeifyBin` 全程加锁，但是它提供了一种优雅的**等待机制**和**状态标识**  
    Q9: TreeBin 中的锁是如何实现的？是有读写锁（ReadWriteLock）吗？  
    A9：不是 ReadWriteLock，基于 `volatile int lockState` 这个对象的位运算 + `synchronized` + `LockSupport.park()`   
        写锁：通过 CAS 尝试将 lockState 设为 WRITER。失败则进入等待队列，调用 LockSupport.park() 直接挂起（不消耗 CPU 自旋）。  
        读锁：在没有写锁时，通过 CAS 增加 `READER`计数位。  
        区别：它没有重入性，也没有复杂的读写锁升级逻辑，是一种轻量级的、专门为树化过程设计的互斥机制。   
    Q10: 在 JDK 1.8 中，如果一个线程正在对 ConcurrentHashMap 进行扩容，其他线程想 put 或 get 数据，会发生什么？  
    A10: Get 操作：如果遇到 `ForwardingNode`（表示该桶正在迁移），会根据其记录的 `nextTable` 指针，直接去新表中查找数据。读操作全程无锁，性能不受扩容太大影响。  
        Put 操作 如果发现桶上是 `ForwardingNode`，该线程会加入扩容大军，调用 `helpTransfer()` 方法，帮助迁移该桶的数据到新表。迁移完成后，再在当前新表的对应位置执行 put 操作。实现了多线程协同扩容，大大缩短了扩容停顿时间，避免了单线程扩容造成的系统长时间阻塞。
* 场景与调优  
    Q11: 初始化 ConcurrentHashMap 时，如何设置参数以减少扩容次数？  
    A11:错误做法：new ConcurrentHashMap(100)。因为构造函数中的大小会自动调整为大于该值的2 的幂次方（100 -> 128），且加载因子默认 0.75，实际阈值是 128 * 0.75 = 96。放入 100 个元素时会触发扩容。正确做法：预估大小为 N，构造参数应设为 `(N / 0.75) + 1`。例如预计存 100 个，应设 `new ConcurrentHashMap(133)`（内部会转为 256，阈值 192，足够容纳 100 个）。或者直接指定初始容量为足够的 `2 的幂`。
    
    Q12: 遇到哈希攻击（大量 Key 碰撞）导致 CPU 100%，可能的原因是什么？如何解决？  
    A12:  
    原因：攻击者构造大量 hash 值相同的 Key，导致所有数据落入同一个桶。
    如果是链表：查询退化为 O(n)，遍历极慢。
    如果是红黑树：虽然查询是 O(log n)，但树化过程和锁竞争会消耗大量 CPU。  
    解决:  自定义 Hash 算法：在 Key 对象中实现更安全的 `hashCode()`，引入随机种子（类似 `JDK 8u202` 后的 String hash 随机化）。限流/防火墙：在网关层拦截异常请求。监控：监控 CHM 的桶深度，发现异常深度及时报警。

## HashMap和CurrentHasnMap的对比  
* 对比
  * | 特性 | HashMap (JDK 1.8) | ConcurrentHashMap (JDK 1.8) | 通俗比喻 |
    | :--- | :--- | :--- | :--- |
    | 线程安全 | ❌ 不安全 | ✅ 安全 | HM：大家随便进，容易撞翻货架。<br>CHM：有门禁和规则，井然有序。 |
    | 锁机制 | 无锁 | `synchronized` + `CAS` (细粒度锁) | HM：没锁。<br>CHM：每个货架格子都有智能锁，互不干扰。 |
    | Null 值支持 | Key 和 Value 都可以为 `null` | Key 和 Value 都不能为 `null` | CHM：为了防歧义（null 代表“没找到”还是“存了个空”？），禁止存空。 |
    | 迭代器 | Fail-Fast (快速失败) | Weakly Consistent (弱一致性) | HM：有人改动就立刻报错。<br>CHM：允许读到旧数据，但不报错，继续跑。 |
    | 数据结构 | 数组 + 链表 + 红黑树 | 数组 + 链表 + 红黑树 + TreeBin | 结构类似，但 CHM 多了很多并发控制的包装。 |
    | 扩容机制 | 单线程重新计算所有位置 | 多线程协同扩容 (帮忙搬运) | HM：店长一个人搬。<br>CHM：顾客也可以帮忙一起搬。 |
