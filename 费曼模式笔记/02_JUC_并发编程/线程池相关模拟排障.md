## 场景模拟：生产环境 CPU 飙升至 100%

* 第一步：定位高负载进程 :
Linux服务器输入指令top
```bash
# 模拟 top 命令输出
top - 14:30:05 up 10 days,  2:15,  1 user,  load average: 8.50, 6.20, 4.10
Tasks: 200 total,   5 running, 195 sleeping,   0 stopped,   0 zombie
%Cpu(s): 98.5 us,  1.2 sy,  0.0 ni,  0.0 id,  0.0 wa,  0.0 hi,  0.3 si,  0.0 st
MiB Mem :  15890.2 total,   2048.5 free,   8192.0 used,   5649.7 buff/cache
MiB Swap:   2048.0 total,   2048.0 free,      0.0 used.   7000.0 avail Mem

  PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
 1024 app       20   0 4520000 204800  12000 R 385.0  1.25  120:30.5 java  <-- 目标进程！CPU 385%
  888 mysql     20   0 1200000 102400   8000 S   2.0   0.64   50:10.2 mysqld
```

分析： 看到 PID 为 1024 的 Java 进程 CPU 占用率高达 385%（说明占满了近 4 个核），就是它了！

**关键动作**： 记住这个线程 PID 1055，我们需要把它转换成十六进制，因为 jstack 日志里是用十六进制表示线程 ID 的。
在 Linux 中可以用 printf "%x\n" 1055 得到 41f。

第三步：导出堆栈并分析
命令： jstack 1024 | grep -A 20 '0x41f'
目的： 查看这个线程到底在执行什么代码。

情况 A：如果是“计算密集型”任务（符合预期）
```bash
"http-nio-8080-exec-5" #25 prio=5 os_prio=0 tid=0x00007f... nid=0x41f runnable [0x00007f...]
   java.lang.Thread.State: RUNNABLE
        at com.example.service.CalcService.complexAlgorithm(CalcService.java:45)
        at com.example.controller.OrderController.submit(OrderController.java:30)
        ...
```

结论： 线程确实在跑业务代码（complexAlgorithm），说明是业务逻辑太复杂，或者数据量太大，属于正常的高负载。


情况 B：如果是“线程池”导致的死循环/资源争抢（异常）
这是你要重点关注的，如果堆栈里全是线程池的内部类：
```bash
"pool-3-thread-1" #35 prio=5 os_prio=0 tid=0x00007f... nid=0x41f runnable [0x00007f...]
   java.lang.Thread.State: RUNNABLE
        at java.util.concurrent.ThreadPoolExecutor.runWorker(ThreadPoolExecutor.java:1149)
        at java.util.concurrent.ThreadPoolExecutor$Worker.run(ThreadPoolExecutor.java:624)
        at java.lang.Thread.run(Thread.java:748)
        
        --- 或者是 ---

"pool-3-thread-1" #35 prio=5 os_prio=0 tid=0x00007f... nid=0x41f runnable [0x00007f...]
   java.lang.Thread.State: RUNNABLE
        at com.example.service.OrderService$$Lambda$123/0x0000000800.run(Unknown Source)
        at java.util.concurrent.ThreadPoolExecutor.runWorker(ThreadPoolExecutor.java:1149) <--- 卡在这里
        ...
```

分析：  
线程名：pool-3-thread-1 说明这是自定义线程池里的线程。  
堆栈：如果大量线程都卡在 ThreadPoolExecutor.runWorker，或者在 Worker.run 里无限循环。  
结论：任务耗时过长：线程池里的任务根本没结束，导致线程无法释放回池子。  
死锁/死循环：任务代码里可能有 while(true) 或者在等待一个永远不会释放的锁。  
队列堆积：配合 getQueue().size() 查看，如果队列满了，线程都在拼命消费，CPU 也会飙升。  

## 笔记总结（排查口诀）

1. top：抓出那个吃 CPU 的 Java 进程 (PID)。
2. top -Hp PID：抓出进程里最忙的那个线程 (TID)。
3. printf "%x" TID：把 TID 转成十六进制 (如 0x41f)。
4. jstack PID | grep 0x41f：看堆栈。
如果是 RUNNABLE 且在执行业务代码 -> 优化算法/SQL。
如果是 WAITING 且在 parkAndCheckInterrupt -> 死锁/锁竞争。
如果是 ThreadPoolExecutor 且 CPU 高 -> 任务太耗时/死循环/线程池配置过小导致频繁调度。
