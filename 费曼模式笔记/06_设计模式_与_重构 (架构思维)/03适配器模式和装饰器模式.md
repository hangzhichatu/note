## 适配器模式
* 一句话解释：把一个类的**接口**，转换成客户期望的另一个**接口**，让原本不兼容的类可以一起工作。（重点，通过新的实现类实现期待的接口，同时在该类里面完成老方法的改造）
* 我的实现理解，有一个老类A，现在我需要一个满足接口B的对象，那么我该怎么做？假设A里面有方法A1是 B接口对应的方法B1.那么可以这么做，声明类C，实现接口B，类C的构造函数需要传入一个老的类A的实例化对象，实现接口B1的时候，在该方法里面调用 A.A1()即可。适配器模式有时候还需要对老方法做逻辑填补(让它能够放回指定类型，实现指定的功能)，或者接口收窄与隔离（屏蔽老类的危险的功能或者不需要的方法）。
适配器模式 = 翻译官 + 包装纸 + 补丁  
翻译：把新参数翻译成老参数，把老返回值翻译成新返回值。  
包装：把老对象包起来，让它看起来像个新对象。  
补丁：在翻译的过程中，顺手修修补补（增强功能、忽略废弃功能）  
* 典型案例老式短信网关的现代化改造 ： 你接手了一个老系统，里面有一个 `LegacySmsGateway` 类（这是源角色）。它非常简陋，只有一个方法 `sendRaw(String msg)`，而且不支持重试，也不支持状态回调。  
需求：  
现在的系统要求所有的消息发送渠道必须实现两个现代标准接口（这是目标接口）：  
`ReliableSender`：可靠发送接口（要求有重试机制）。  
`StatusMonitor`：状态监控接口（要求能返回发送状态）  
`LegacySmsGateway` 类太老了，改不了源码。你需要写一个适配器，让它同时具备“重试”和“监控”的能力，也就是同时实现这两个接口。

```java
// ================= 1. 源角色（老代码，不能动） =================
class LegacySmsGateway {
    // 老式方法：只管发，不管成功失败，也不支持重试
    public void sendRaw(String msg) {
        System.out.println("📡 老式网关：正在发送原始短信 -> " + msg);
        // 模拟偶尔发送失败
        if (Math.random() > 0.5) {
            throw new RuntimeException("信号不好，发送失败");
        }
    }
}

// ================= 2. 目标接口（现代标准） =================

// 接口 A：要求可靠发送
interface ReliableSender {
    void sendWithRetry(String msg, int maxRetries);
}

// 接口 B：要求可监控状态
interface StatusMonitor {
    boolean checkStatus(String msg); // 返回是否成功
}

// ================= 3. 适配器（多接口适配） =================

// 关键点：一个类同时实现多个接口
class ModernSmsAdapter extends LegacySmsGateway implements ReliableSender, StatusMonitor {
    
    // 记录最后一次发送的状态
    private boolean lastSendSuccess = false;

    // --- 实现接口 A：可靠发送 ---
    @Override
    public void sendWithRetry(String msg, int maxRetries) {
        for (int i = 0; i < maxRetries; i++) {
            try {
                // 调用老式网关的方法
                super.sendRaw(msg);
                this.lastSendSuccess = true;
                System.out.println("✅ 重试机制：发送成功！");
                return; // 成功后直接返回
            } catch (Exception e) {
                System.out.println("⚠️ 重试机制：第 " + (i + 1) + " 次尝试失败，准备重试...");
                this.lastSendSuccess = false;
            }
        }
        System.out.println("❌ 重试机制：超过最大重试次数，放弃发送。");
    }

    // --- 实现接口 B：状态监控 ---
    @Override
    public boolean checkStatus(String msg) {
        // 这里可以查询老系统的状态，或者直接返回我们刚才记录的状态
        System.out.println("📊 监控系统：正在检查短信 '" + msg + "' 的状态...");
        if (lastSendSuccess) {
            System.out.println("📊 监控系统：状态为 [已送达]");
        } else {
            System.out.println("📊 监控系统：状态为 [发送失败]");
        }
        return lastSendSuccess;
    }
}

// ================= 4. 客户端调用 =================
public class Main {
    public static void main(String[] args) {
        // 创建适配器
        ModernSmsAdapter adapter = new ModernSmsAdapter();

        // 视角 1：把它当作“可靠发送器”使用
        ReliableSender sender = adapter;
        sender.sendWithRetry("你好，世界", 3);

        System.out.println("-------------------");

        // 视角 2：把它当作“状态监控器”使用
        StatusMonitor monitor = adapter;
        monitor.checkStatus("你好，世界");
    }
}
```
这个例子展示了适配器模式的“多态扩展能力”：继承源角色：extends LegacySmsGateway，复用了老代码的 sendRaw 能力。实现多个目标接口：implements ReliableSender, StatusMonitor。功能增强：适配器不仅仅是“翻译”语言，它还通过包装逻辑（比如 for 循环重试、记录 lastSendSuccess 变量），给老代码赋予了新功能。


## 装饰器模式
* 一句话解释：动态地给一个对象添加额外的职责，就像给礼物"包装"一样。
* 基础对象：一杯原味奶茶。
    装饰器：加珍珠、加椰果、加布丁。
    结果：你可以自由组合，得到"珍珠椰果布丁奶茶"，而不需要为每种组合单独开一个"奶茶类"。

* 代码实现逻辑 ，实现分为以下几部分， 1.基础接口，定义了所有的奶茶类。 2.基础实现，一个最简单的奶茶实现类 3.装饰器基类，它是一个抽象类，构造器方法需要传入一个奶茶类对象，然后回定义若干装饰器类需要实现的抽象方法，比如给奶茶加什么料，小料价格等。

```java
// 1. 定义一个基础接口
interface Coffee {
    String getDescription();
    double getCost();
}

// 2. 基础实现：原味咖啡
class SimpleCoffee implements Coffee {
    public String getDescription() {
        return "原味咖啡";
    }
    public double getCost() {
        return 10.0;
    }
}

// 3. 装饰器基类（关键！）
abstract class CoffeeDecorator implements Coffee {
    protected Coffee decoratedCoffee; // 持有一个 Coffee 的引用

    public CoffeeDecorator(Coffee coffee) {
        this.decoratedCoffee = coffee;
    }

    public String getDescription() {
        return decoratedCoffee.getDescription();
    }
    public double getCost() {
        return decoratedCoffee.getCost();
    }
}

// 4. 具体装饰器：加牛奶
class MilkDecorator extends CoffeeDecorator {
    public MilkDecorator(Coffee coffee) {
        super(coffee);
    }

    public String getDescription() {
        return super.getDescription() + " + 牛奶";
    }
    public double getCost() {
        return super.getCost() + 2.0;
    }
}

// 5. 具体装饰器：加糖
class SugarDecorator extends CoffeeDecorator {
    public SugarDecorator(Coffee coffee) {
        super(coffee);
    }

    public String getDescription() {
        return super.getDescription() + " + 糖";
    }
    public double getCost() {
        return super.getCost() + 1.0;
    }
}
```
客户端调用
```java
Coffee coffee = new SimpleCoffee(); // 原味
coffee = new MilkDecorator(coffee); // 加牛奶
coffee = new SugarDecorator(coffee); // 再加糖

System.out.println(coffee.getDescription()); // 输出：原味咖啡 + 牛奶 + 糖
System.out.println(coffee.getCost()); // 输出：13.0
```

装饰器模式的核心是"组合优于继承"。如果用继承，你需要写 MilkCoffee、SugarCoffee、MilkSugarCoffee... 类会爆炸。用装饰器，你可以像搭积木一样自由组合。

* 装饰器模式里面的坑点:
      *  equals 和 hashCode 失效
        这是装饰器模式最臭名昭著的问题。  
        假设你的咖啡加了牛奶，然后你想把它放进一个 HashSet 里去重：
        ```java
        Coffee coffee = new MilkDecorator(new SimpleCoffee());
        Set<Coffee> set = new HashSet<>();
        set.add(coffee);

        // 你觉得这两个应该相等吗？
        boolean contains = set.contains(coffee); // true，这个没问题

        // 但如果这样呢？
        Coffee sameCoffee = new MilkDecorator(new SimpleCoffee());
        boolean contains2 = set.contains(sameCoffee); // false！惊不惊喜？
        ```
        因为 MilkDecorator 是一个新对象，它的 hashCode() 默认是对象地址，跟原来的 coffee 不一样。即使你重写了 equals，你也得考虑"装饰器套装饰器"的复杂情况。
        怎么办:  
        如果业务场景需要比较相等性，最好在装饰器里重写 equals 和 hashCode，比较内部的 decoratedCoffee  
        或者干脆别用装饰器模式，改用组合+代理的方式，自己控制相等性逻辑。
      * 坑二：装饰器爆炸
        想象一下，你的咖啡系统越来越复杂：
        加牛奶
        加糖
        加奶油
        加香草糖浆
        去冰
        换燕麦奶
        ...
        ```java
            Coffee coffee = new OatMilkDecorator(
                new NoIceDecorator(
                    new VanillaSyrupDecorator(
                        new CreamDecorator(
                            new SugarDecorator(
                                new MilkDecorator(new SimpleCoffee())
                            )
                        )
                    )
                )
            );
        ```
        太麻烦了,而且没法维护，这个时候就要考虑建造者模式了
        ```java
        Coffee coffee = new CoffeeBuilder(new SimpleCoffee())
        .addMilk()
        .addSugar()
        .addVanillaSyrup()
        .noIce()
        .build();
        ```
