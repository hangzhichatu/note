## L - 里氏替换
* 一句话说明白 子类必须能够替换掉父类，而且程序不出错。
    生活比喻：假币识别机
    父类：钞票。
    子类：真钞、假钞。
    场景：你有一个验钞机（程序），它的设计初衷是处理“钞票”。
    违反原则：如果你把一张“假钞”（子类）放进去，验钞机崩溃了，或者把它当成了真钱花出去了，这就违反了里氏替换原则。
    符合原则：不管放进去的是真钞还是假钞，验钞机都能正确处理（识别出真假），这就是符合原则。
* 经典反面教材：正方形与长方形
    直觉：数学上，正方形是一种特殊的长方形。所以，Square 继承 Rectangle 看起来很合理。
    ```java
    // 父类：长方形
        class Rectangle {
            protected int width, height;
            public void setWidth(int w) { width = w; }
            public void setHeight(int h) { height = h; }
            public int getArea() { return width * height; }
        }

        // 子类：正方形
        class Square extends Rectangle {
            // 重写 setter，强制宽高相等
            public void setWidth(int w) { width = w; height = w; }
            public void setHeight(int h) { height = h; width = h; }
        }

        public void test(Rectangle r) {
        r.setWidth(5);
        r.setHeight(4);
        // 预期面积：20
        // 实际面积：16 (因为如果是Square，高被宽强行改了)
        System.out.println(r.getArea()); 
    }
    ```
    继承要非常谨慎！ 只有当子类完全符合父类的行为特征时，才使用继承。如果不确定，宁可不用继承。

## I - 接口隔离原则
* 一句话解释：不要强迫类去实现它不需要的方法。接口要小而美，不要大而全。
* 违反原则（万能遥控器）：
    你买了一个“超级遥控器”，上面有100个按钮（开电视、开空调、开灯、开飞机...）。
    现在你要控制一个简单的台灯。厂家强迫你买这个超级遥控器，结果你拿到手，99个按钮对台灯都没用，而且很大很重。
    符合原则（专用开关）：
    台灯配一个简单的“开关”接口（只有开/关）。简单、专注。
* 样例代码:工人接口
    ```java
            interface Worker {
            void work(); // 工作
            void eat();  // 吃饭
            void sleep(); // 睡觉
        }
    ```
    这样不好，如果实现工人接口的类对象没有吃饭睡觉的功能就会有问题，必须要强制抛出方法无效的异常了
    ```java
            class Robot implements Worker {
            public void work() { /* 机器人干活 */ }
            public void eat() { /* 报错！机器人不吃饭！ */ throw new RuntimeException("Unsupported"); }
            public void sleep() { /* 报错！机器人不睡觉！ */ throw new RuntimeException("Unsupported"); }
        }
    ```
    重构案例:
    ```java
    interface Workable {
        void work();
    }

    interface Eatable {
        void eat();
    }

    // 人类实现所有接口
    class Human implements Workable, Eatable {
        public void work() { /* ... */ }
        public void eat() { /* ... */ }
    }

    // 机器人只实现它需要的接口
    class Robot implements Workable {
        public void work() { /* ... */ }
        // 机器人不需要实现 eat()，代码更干净
    }
    ```

## D - 依赖倒置原则
* 核心概念拆解
    高层模块：复杂的业务逻辑（比如 OrderService 订单服务）。  
    低层模块：具体的细节实现（比如 MySQLDatabase 数据库操作，EmailSender 邮件发送）。  
    抽象：接口（比如 Database 接口，MessageSender 接口）。  

* 一句话说明白，业务层的代码比如写获取数据库的时候，不要直接写我要依赖xxx类的方法，而是写我要依赖实现了DataBase接口的方法，这样做，业务层想换数据库的实现类的话，就不用修改业务层的代码了
* 错误与正确的解析: OrderService（高层）直接 new MySQLDatabase()（低层）后果：OrderService 被死死绑定在 MySQL 上。如果你想换 Oracle 数据库，必须修改 OrderService 的源代码。
    * 依赖倒置（正确的依赖方向）:
    1.OrderService 依赖 Database 接口（抽象）。
    2.MySQLDatabase 也依赖 Database 接口（实现抽象）。
    3.依赖倒过来了：高层和低层都听“抽象”的话。


## SOLID 全景图
| 原则 | 核心思想 | 一句话口诀 |  
| :--- | :--- | :--- |  
| S - 单一职责 | 一个类只做一件事 | “各司其职，不要越界” |  
| O - 开闭原则 | 对扩展开放，对修改关闭 | “加功能靠加类，不靠改代码” |  
| L - 里氏替换 | 子类不能破坏父类逻辑 | “儿子能替老爸干活，且不出乱子” |  
| I - 接口隔离 | 接口要小而专 | “不要强迫类实现不需要的方法” |  
| D - 依赖倒置 | 依赖抽象，不依赖具体 | “面向接口编程，别面向实现” |  

* 回答阐述:SOLID 是面向对象设计的五大基石，目的是降低代码耦合度，提高可维护性。
    首先是单一职责，让类职责清晰，避免牵一发而动全身。
    其次是开闭原则，这是核心目标，让我们能通过扩展而不是修改来增加功能。
    里氏替换规范了继承的使用，避免子类破坏父类逻辑。
    接口隔离让我们避免臃肿的接口，让依赖更轻量。
    最后是依赖倒置，它是实现开闭原则的关键手段，通过面向接口编程，解耦高层和低层模块。”
