## 策略模式
* 一句话解释：把一堆复杂的算法，分别封装成独立的类，让它们可以互相替换。
* 具体实现: 考虑这样一个场景，双十一的时候促销所有物品包邮，平时的时候正常邮寄价格要怎么做，才能保证后续如果需要新增新的邮寄价格逻辑的时候尽量少的修改代码？
    糟糕的实现:写一大堆if-esle判断逻辑，把不同的策略写入到同一个类中。
    优化思路:解耦，把不同的策略单独封装到不同的策略类里面去，由更上层的业务类来决定使用哪种策略。
    代码实现:
    第一步：定义策略接口
    ```java
    // ShippingStrategy.java
    public interface ShippingStrategy {
        double calculate(double weight, double volume);
    }
    ```
    第二步：实现具体策略
    ```java
    // NormalStrategy.java (平时)
    public class NormalStrategy implements ShippingStrategy {
        public double calculate(double weight, double volume) {
            return weight * 5.0;
        }
    }

    // FreeStrategy.java (包邮)
    public class FreeStrategy implements ShippingStrategy {
        public double calculate(double weight, double volume) {
            return 0.0;
        }
    }
    ```
    第三步：在业务中使用（上下文）注意这里的时候业务代码使用的是实现了策略类接口的类的名字，这样更上层传入的具体的实现类可以不用修改业务层的代码
    ```java
    // OrderService.java
    public class OrderService {
        private ShippingStrategy strategy;

        // 可以在运行时动态切换策略！
        public void setStrategy(ShippingStrategy strategy) {
            this.strategy = strategy;
        }

        public void checkout(double weight, double volume) {
            double cost = strategy.calculate(weight, volume);
            System.out.println("运费是: " + cost);
        }
    }
    第四步：客户端调用
    ```java
    OrderService order = new OrderService();

    // 平时
    order.setStrategy(new NormalStrategy());
    order.checkout(10, 1); // 输出 50.0

    // 双十一到了，切换策略
    order.setStrategy(new FreeStrategy());
    order.checkout(10, 1); // 输出 0.0
    ```
* 自我思考，在上述代码实现里面，分了四步，但是可以这样划分  客户端调用层，该层是组装各种条件的层   业务层，该层主要是各种相对固定的业务逻辑会根据客户端调用的时候使用的不同策略，自动去找特定的实现类，策略接口定义和策略实现类，这里策略接口给业务层一个固定的入口避免业务层的代码依赖于某个具体的策略实现类，策略实现类它可以动态的拓展，只需要在拓展后再客户端调用层表明需要使用该策略即可。

* 代码实现，需要支持策略模式的话，代码实现这块需要做的内容有三块（除去客户端调用以外），需要做 核心业务代码支持，策略模式接口，策略模式实现类
  
## 观察者模式

* 一句话说明白:一个对象状态改变，自动通知所有依赖它的对象。典型例子是公众号被观察者（Subject）：公众号。
观察者（Observer）：粉丝。
机制：公众号发文章（状态改变），所有关注的粉丝都会收到推送（自动更新）。公众号不需要知道粉丝具体是谁，也不需要一个个去打电话通知。

* 实例代码参考:股票价格变动通知
第一步：定义观察者接口
```java
// Observer.java
public interface Observer {
    void update(double price);
}
```
第二步：定义被观察者接口
```java
// Subject.java
import java.util.ArrayList;
import java.util.List;

public class Stock {
    private List<Observer> observers = new ArrayList<>();
    private double price;

    // 注册观察者（粉丝关注）
    public void attach(Observer observer) {
        observers.add(observer);
    }

    // 设置价格（触发通知）
    public void setPrice(double price) {
        this.price = price;
        // 价格变了，通知所有人
        notifyAllObservers();
    }

    private void notifyAllObservers() {
        for (Observer observer : observers) {
            observer.update(price);
        }
    }
}
```
第三步：实现具体的观察者
```java
// MobileApp.java (手机端)
public class MobileApp implements Observer {
    public void update(double price) {
        System.out.println("📱 手机App收到通知：股价变更为 " + price);
    }
}

// WebPage.java (网页端)
public class WebPage implements Observer {
    public void update(double price) {
        System.out.println("💻 网页收到通知：股价变更为 " + price);
    }
}
```
第四步: 运行
```java
Stock stock = new Stock();
stock.attach(new MobileApp());
stock.attach(new WebPage());

stock.setPrice(100.0); 
// 输出：
// 📱 手机App收到通知：股价变更为 100.0
// 💻 网页收到通知：股价变更为 100.0
```

* 观察者模式实现要点，被观察对象需要实现通过观察者的功能，并且需要显示的将观察者添加到被观察者的通知列表里面去。被观察者需要实现预先定义好的观察者接口提供通知方法给被观察者调用
* 这就是“高内聚，低耦合”的极致体现。股票类只负责算价格，通知的事情交给观察者接口。以后如果要加“短信通知”，只需要写个 SmsObserver 并注册进去，股票类完全不用改。


## 如何回答相关内容
* 面试题 1：策略模式和 if-else 相比，优势在哪里？
回答思路：
解耦：把算法从业务逻辑中剥离出来。
扩展性：符合开闭原则，增加新策略不需要修改原有代码。
可维护性：避免了复杂的条件判断语句，每个策略类职责单一。
* 面试题 2：观察者模式和发布/订阅模式有什么区别？
回答思路：
观察者模式：通常是同步的，被观察者直接调用观察者的方法（如上面的代码示例）。
发布/订阅模式：通常有一个中间的“消息代理”（如 Redis Pub/Sub, Kafka），发布者和订阅者互不认识，通过中间件异步通信。
* 面试题 3：你在项目中哪里用过这些模式？
回答思路（结合练习）：
“在电商项目中，计算运费和优惠券折扣时，我使用了策略模式来应对多变的促销规则。”
“在订单系统中，当订单状态变更（支付成功、发货）时，需要通知库存系统和用户，我使用了观察者模式来实现这种一对多的通知机制。”
