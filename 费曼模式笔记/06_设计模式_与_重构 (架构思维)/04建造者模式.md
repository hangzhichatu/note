## 建造者模式

* 将一个复杂对象的构建与它的表示分离，使得同样的构建过程可以创建不同的表示。具体实现上会有一个专门的builde类，有各种构造方法，最后执行build方法可以返回一个的需要的对象。
* **想象你去快餐店点餐（比如赛百味）。**
* **产品** **：三明治。**
* **建造者** **：服务员。你不需要自己进厨房做，而是告诉服务员：“我要全麦面包（步骤1），加牛肉（步骤2），不要酸黄瓜（步骤3）”。**
* **指挥者（Director）** **：店长。他可能会定义一个“经典套餐”，这个套餐固定了步骤1、2、3，你直接点套餐就行，不用一步步说。**


| 角色                         | 职责                                                            | 形象理解                    |
| :--------------------------- | :-------------------------------------------------------------- | :-------------------------- |
| Product (产品)               | 最终要生成的复杂对象。                                          | 那个做好的三明治。          |
| Builder (抽象建造者)         | 定义构建步骤的接口（如 `buildPartA()`,`buildPartB()`）。    | 菜单上的选项标准。          |
| ConcreteBuilder (具体建造者) | 实现 Builder 接口，负责把零件组装起来，并返回产品。             | 那个听你指挥的服务员/厨师。 |
| Director (指挥者)            | （可选） 负责安排构建顺序。它不关心具体造什么，只关心步骤顺序。 | 店长/套餐制定者。           |


* 解决了什么问题:
  为了解决“**构造函数爆炸”** **和** **“代码可读性差”** **的问题。**
* 场景1 创建用户，假设一个用户有很多字段 `name`, `age`, `email`, `address`, `phone`, `vipLevel`... 如果是在学习这个设计模式前的我来做的话，我可能会制定一个有非常多的参数构造函数，那么问题来了，参数太多就很难记，如果还需要对输入做校验的话，构造函数的逻辑会非常复杂。
  或者，在对象创建后使用setAttribute的方法来设置相关属性，但是这样做的问题是，对象存在一段时间是没有完成构造的会有风险。
* ```java
  public class Computer {
      private String cpu;
      private String ram;
      private String disk;

      // 私有构造，强制通过 Builder 创建
      private Computer(Builder builder) {
          this.cpu = builder.cpu;
          this.ram = builder.ram;
          this.disk = builder.disk;
      }

      @Override
      public String toString() {
          return "Computer [cpu=" + cpu + ", ram=" + ram + ", disk=" + disk + "]";
      }

      // 静态内部类 Builder
      public static class Builder {
          private String cpu;
          private String ram;
          private String disk;

          public Builder() {}

          public Builder cpu(String cpu) {
              this.cpu = cpu;
              return this; // 返回 this 支持链式调用
          }

          public Builder ram(String ram) {
              this.ram = ram;
              return this;
          }

          public Builder disk(String disk) {
              this.disk = disk;
              return this;
          }

          // 关键步骤：构建并返回对象
          public Computer build() {
              // 这里可以做参数校验，比如 cpu 不能为空
              if (cpu == null) throw new IllegalArgumentException("CPU is required");
              return new Computer(this);
          }
      }
  }
  ```

  使用案例

  ```java
  public class Client {
      public static void main(String[] args) {
          // 1. 自定义组装
          Computer gamingPC = new Computer.Builder()
                  .cpu("Intel i9")
                  .ram("32GB")
                  .disk("1TB SSD")
                  .build();
          System.out.println(gamingPC);

          // 2. 也可以封装一个 Director 类来提供预设配置
          Computer officePC = ComputerDirector.createOfficePC();
          System.out.println(officePC);
      }
  }
  ```
* 优势劣势

  * 优势：封装性好:将复杂对象的构建逻辑封装在 Builder 内部，客户端不需要知道内部细节,解耦，构建代码与业务代码隔离，不可变性：通过builder创建的对象可以在完成后标记为final，保证线程安全，可读性高，链式调用一目了然。
  * 劣势：代码量增加:需要多写一个Builder类，同时如果对象简答的话这么做是画蛇添足。
* 小技巧 Lombok组件（除了Data注解外，Lombok还提供@Builder注解）

  ```java
  import lombok.Builder;

  @Builder // 加上这个注解，Lombok 会自动生成 Builder 类、build() 方法等
  public class User {
      private String name;
      private int age;
      private String email;
      // ...
  }

  // 使用
  User user = User.builder()
          .name("张三")
          .age(18)
          .email("test@example.com")
          .build();
  ```


* 建造者模式还可以把很多初始化参数的校验给放到Builder类中进行:
  * 基础字段校验
    **虽然可以在** `setXxx()` **方法里做简单的非空校验，但在** `build()` **里做****最终兜底**是非常安全的。
  * 关联校验跨字段校验**很多业务规则涉及** **多个字段之间的关系** **，这些逻辑无法在单个** `setXxx()` **方法中完成，必须等所有参数设置完毕后，在** `build()` **中统一判断**
  * 业务数据预处理根据配置参数计算默认值，或者进行数据格式化**例子****：如果用户没传** `createTime`，在 `build()` **里自动设置为** `new Date()`。
