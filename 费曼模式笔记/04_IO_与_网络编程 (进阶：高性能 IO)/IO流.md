## IO流，数据的搬运工
* 基础概念
      * 字节流，他说最基础的流 (`InputStream` / `OutputStream`) ，它是搬运工，搬运最基础的0和1，不管里面是图片、视频还是乱码文本。它是所有流的基类场景： 处理非文本文件（图片、音频）、网络数据传输。
      * 字符流，在字节流的基础上套了一层"解码器"，专门处理人类可读的文本，解决中文乱码的问题
* 性能优化：缓冲流 (Buffered Stream)
      * 每次读写都直接操作磁盘，就像每次只买一根葱都要跑一趟菜市场，磁盘 IO 太慢了
      * 解决方案`BufferedInputStream` / `BufferedWriter` 
      * 原理： 在内存中开辟一块“缓冲区”（默认 8KB）。读的时候一次性从磁盘拉取 8KB 到内存，后续读取直接从内存拿；写的时候先攒够 8KB 再一次性写入磁盘。
      * 中级考点： 为什么 BufferedWriter 写入后文件可能是空的？（因为数据还在内存缓冲区，必须调用 flush() 强制刷入磁盘）。
* 资源管理try-with-resources
      * 规范： 凡是涉及到 IO 流、数据库连接、Socket 连接，必须关闭，否则会导致“文件句柄泄漏”，最终系统崩溃。
      * 最佳实践： 别再用 finally { close() } 了，太啰嗦且容易写错。请使用 Java 7 的语法糖：
      ```java
      // 自动关闭，前提是对象实现了 AutoCloseable 接口
        try (FileInputStream fis = new FileInputStream("data.txt");
            BufferedInputStream bis = new BufferedInputStream(fis)) {
            // 业务逻辑
        } catch (IOException e) {
            // 异常处理
        } 


## 核心概念

* 在深入了解前，有几个概念需要厘清。
* 两个阶段，**IO的操作本质**，任何一次网络读取（比如 `read()`），在底层其实都经历了两个阶段：
      * 等待数据就绪（Waiting）： 网卡收到数据 -> 拷贝到内核缓冲区。这个阶段通常很慢，因为要等网络传输。
      * 数据拷贝（Copying）： 把数据从内核缓冲区 -> 拷贝到用户缓冲区（你的 Java 变量里）。
      * 用自己话来书就是，阶段一：点菜后等厨师做菜（数据从网络到内核）。阶段二：服务员把做好的菜端到你桌上（数据从内核到用户）。
* 阻塞对比非阻塞
      * 阻塞的话，在第一个阶段，等菜的时候，你什么都不能干你傻站在柜台前，什么也不能干，直到菜好。
      * 非阻塞，你点完菜，拿到一个震动取餐器。你可以去玩手机（处理其他任务），震动响了（数据就绪）你再去拿
* 同步 vs 异步（最容易混淆！）
      * 同步： 你必须亲自去柜台拿菜（阶段二必须由你参与）。
      * 异步： 你不仅拿了震动器，还要求服务员直接把菜端到你座位上（阶段二由系统帮你做，做完通知你）。

## 五种IO模型（需要背诵）

* 阻塞IO  
      * 场景你在柜台办业务，柜员（线程）一直为你服务，直到办完。如果前面排队，你就一直等。
      * java实现 `ServerSocket.accept(), InputStream.read()`
      * 缺点： 一个连接一个线程。连接多了，线程把内存撑爆，CPU 切换线程累死
* 非阻塞 IO —— 瞎忙活
      * 场景： 你不想等，每隔 1 秒问柜员：“好了吗？好了吗？”。柜员没空理你，你只能一直问
      * Java 体现： `SocketChannel.read()` 返回 -1 或 0。
      * 缺点： 轮询太浪费 CPU，就像苍蝇一样嗡嗡叫。
* IO 多路复用 —— 现代高性能基石（重点！）
      *  场景： 银行大堂经理（Selector）。你不用去柜台排队，而是拿个号坐大厅。大堂经理手里有个本子（注册表），记录着谁办完了。经理喊：“101 号可以了！”，你才去柜台。
      *  核心： 一个线程（经理）管理成千上万个连接（客户）
      *  Linux 实现： select（老一代，有连接数限制）、poll（改进版）、epoll（王者，Linux 下性能极高）
      *  Java 体现： Java NIO 的 Selector。
* 信号驱动 IO —— 较少见
      * 场景： 你留了电话，银行办好了给你发短信（SIGIO 信号）。缺点： 信号处理复杂，不稳定。
*  异步 IO —— 终极形态
         *  场景： 海底捞服务。你下单后去睡觉，服务员把菜做好、端上来、甚至帮你涮好，最后拍醒你说：“老板，吃吧”
         *  Java 体现： Java AIO (AsynchronousSocketChannel)。
         *  现状： 在 Linux 下实现并不完美，性能往往不如 NIO，所以目前主流框架（如 Netty）依然主要基于 IO 多路复用（NIO）。


| 模型 | 阻塞阶段 | 谁负责搬运数据 (内核->用户) | 形象比喻 | Java 对应 |  
| :--- | :--- | :--- | :--- | :--- |  
| 阻塞 IO | 两个阶段都阻塞 | 用户线程 | 柜台死等 | `ServerSocket.accept()` |  
| 非阻塞 IO | 仅第二阶段阻塞 | 用户线程 | 不停问“好了吗” | `SocketChannel.read()` (轮询) |  
| IO 多路复用 | 阻塞在 `select/epoll` | 用户线程 | 大堂经理叫号 | `Selector.select()` |  
| 信号驱动 | 基本不阻塞 | 用户线程 (在信号函数中) | 短信通知 | (极少用) |  
| 异步 IO | 全程不阻塞 | 内核 | 海底捞服务 | `AsynchronousSocketChannel` |  

## 给中级开发的进阶提示
Q1 :Epoll 是同步还是异步？
A1 这是一个经典坑。Epoll 是同步的！为什么？因为 epoll_wait 返回后，你还需要自己调用 read() 去把数据从内核拷贝到用户空间。这个 read 依然是同步阻塞的（虽然数据已经就绪，拷贝很快）。真正的异步是内核帮你拷贝。  
Q2 :零拷贝 (Zero Copy)
A2:既然 IO 瓶颈在于“拷贝”，那么 sendfile 或 mmap 这种技术，允许数据直接从内核缓冲区传输到网卡，不经过用户空间，这就是 Netty 高性能的另一个秘诀。  
Q3:Reactor 模型  
A3: 理解了 IO 多路复用，下一步就是理解 Reactor 模式（单 Reactor 单线程、单 Reactor 多线程、主从 Reactor）。Netty 就是典型的主从 Reactor 多线程模型。  s
